# PRD Quality Review — Hexalith.Memories

## Overall verdict
The PRD still has a real thesis, named trade-offs, and unusually concrete NFRs, pipeline, compliance, and licensing substance for an older BMad format. What does not hold is a single ship contract: "MVP" names both a CLI proof-of-thesis prototype and a launch checklist that includes MCP, EventStore causality, and a `dotnet add package` onboarding path the feature table deferred. At launch / chain-top stakes, with architecture, epics, UX, and months of sprint changes already downstream of this document, those forks will keep generating the wrong stories unless the PRD picks one increment and phases the rest.

## Decision-readiness — thin
A March decision-maker could have acted: proof-of-thesis before integration surfaces, physical isolation and cases "from day one," fusion as a dedicated spike, MCP as a 4-week fast-follow with an explicit pull-forward if the prototype is unadoptable, and a graph-axis fallback that repositions the product. Those are stated as decisions, not "considerations." What a decision-maker cannot do *now* is execute the ship checklist without choosing which layer of the document is authoritative. The body has been patched toward implementation (RRF, Google-only embeddings, OpenBao, published packages, `TenantProvisioningWorkflow`) while the gates, hero journey, and resource line still describe the March greenfield bet. There are zero Open Questions, `[ASSUMPTION]` tags, or `[NOTE FOR PM]` callouts; remaining tensions were edited into coexistence rather than left visible.

### Findings
- **critical** "MVP" means two incompatible ship contracts (§ Success Criteria › MVP Go/No-Go Gate vs § MVP Feature Set vs § Phase 1.5) — The go/no-go table is titled "MVP" and requires three hard gates plus "at least 2 of 3 soft gates," including "MCP end-to-end integration works" and "Causal chain completeness ≥95%." Phase 1 explicitly excludes those surfaces: "Journey 1 … partial: CLI-only, no EventStore zero-code flow"; MCP and EventStore sit in Phase 1.5. The same table's hard onboarding gate is operationalized in User Success as "Time from `dotnet add package` to first successful search result," which is the EventStore path, while NFR31 operationalizes <30 minutes as a "README … on a clean machine with Docker." A ship review cannot tell whether Phase 1 is allowed to complete without MCP/EventStore, or whether "MVP go/no-go" secretly means launch-including-1.5. *Fix:* Split into a Phase 1 thesis gate (hybrid NDCG, isolation, CLI onboarding) and a launch gate (MCP, EventStore, causal completeness); point the <30 min hard gate at one onboarding path.
- **high** Fusion algorithm is two different decisions (§ MVP Strategy & Philosophy, § Risk Mitigation Strategy vs § AI Reliability and Trust Boundaries, NFR24) — Sequencing still treats fusion as "BM25 normalization + cosine + graph proximity weighting" and lists "Three normalization problems (BM25 unbounded → 0-1, cosine native 0-1, graph proximity custom decay) must each be solved and documented before fusion weighting begins." Domain and NFR24 have already chosen "Weighted RRF over available axis rankings" / "deterministic weighted reciprocal-rank fusion," and hybrid explain "exposes weighted reciprocal-rank contribution so raw BM25 magnitude is not fused directly." Anyone pushing back on score fusion will find both answers. *Fix:* Declare RRF (or weighted scores) as the decision; demote the three-normalization paragraph to historical context or a rejected alternative.
- **medium** Case membership is specified without an identity model (§ Journey 4, FR28–FR29 vs Service Communication Model) — Journey 4 and FR28/FR29 require `memories case add-member --user tomas` and member add/remove. The communication model says "Per-user identity | Not in MVP — tenant-level isolation sufficient." `ingested_by` is a "mandatory MVP field," which is a provenance string, not membership. *Fix:* Either defer FR28/FR29/Journey 4 to Phase 2 with the briefing feature, or define the MVP member as an unauthenticated identifier and state what enforcement exists.
- **low** License is a public trust commitment and still a recommendation (§ Open-Source Licensing) — "Hexalith.Memories license: Apache 2.0 **(recommended)**" sits next to a README sentence the PRD wants treated as a promise: "We will not change to a restrictive license." *Fix:* Record Apache 2.0 as the decision, or list the remaining blocker.

## Substance over theater — adequate
The earned core is not furniture: NFR1–NFR31 have targets, conditions, verification, and phase tags; the edge-type table distinguishes `caused_by` from `correlated_with` with a concrete failure mode; the compliance section refuses "just infrastructure" and limits tenant delete and telemetry; licensing names SSPL/AGPL implications instead of a vibe. Journeys 1, 2, 5, 7, and 9 actually constrain CLI, isolation, and agent behavior. The overweight is the surrounding cast: six named humans plus an LLM Agent, ten journeys, and an Innovation section that partly restates the thesis.

### Findings
- **medium** Several personas/journeys do not drive an MVP (or even Phase 1.5) decision (§ User Success, Journeys 4, 6, 8, 10) — Marcus's success criterion is "Brief me on this case … Within 5 minutes," but onboarding briefing is Phase 2. Priya never uses Memories; she consumes a Phase 2 REST app. Journey 6 is explicitly Phase 3. Journey 10 is "project infrastructure … tracked separately." They read thorough; they do not change scope, gates, or FRs. *Fix:* Keep Alex / Kenji / LLM Agent as load-bearing; mark the rest as vision illustrations or move them out of Success Criteria.
- **low** Novelty claims that the rest of the PRD does not need (§ What Makes This Special, § Innovation & Novel Patterns) — "No competitor offers this" (team-scoped collaborative memory) and "Interpretive Infrastructure (Positioning Innovation)" do not add a testable bet beyond the three-axis kill switch and the isolation NFRs. The competitor table is specific enough; the category-creation language is not. *Fix:* Keep the table; drop uniqueness superlatives unless Discovery named a disconfirming competitor.

## Strategic coherence — adequate
There is a thesis, and it is repeated as a kill switch: "if hybrid retrieval doesn't outperform single-axis on 80%+ of benchmark queries … the product direction must be re-evaluated." MVP features 1–7 follow that bet (axes independently, then fusion spike, then a scored benchmark suite). The fast-follow is justified as adoptability, not as more thesis. What breaks the arc is that the document's opening sells a different product than the thesis MVP proves, and the kill-switch methodology is narrower than the claim it supposedly validates.

### Findings
- **high** The kill switch is partly tautological (§ Executive Summary vs § Measurable Outcomes › The Three-Axis Kill Switch) — Front matter says hybrid must outperform single-axis "on 80%+ of benchmark queries (scored by result relevance against ground truth)." The protocol then restricts the suite to "5–10 queries requiring all three axes." A set constructed to need all three axes cannot falsify "three-axis is the right product"; it can only catch a fusion implementation so bad it loses on queries designed for it. Solo-dev fallback to "automated A/B scoring if reviewers unavailable" further softens the independent-reviewer protocol. *Fix:* State the population (representative mix vs thesis-stress queries), keep 80% only for the chosen population, and make the reviewer fallback a documented downgrade of gate confidence.
- **medium** Hero differentiators are not the MVP bet (§ What Makes This Special vs § MVP Feature Set / Phase 2) — The specialness pitch is "The memory server that understands causality" via EventStore zero-code, plus "Team-scoped collaborative memory" (discussions, diffing, briefings). EventStore is Phase 1.5; discussions/diffing/briefings are Phase 2. MVP actually bets on hybrid retrieval plus non-retrofittable isolation. A reader of the first two pages will prioritize the wrong proof. *Fix:* Lead the exec summary with the Phase 1 proof (hybrid + isolation + CLI); treat causality and collaboration as sequenced bets with their own gates.
- **medium** Isolation is both un-deferrable and deferrable (§ MVP Strategy & Philosophy vs § Resource Risks) — Philosophy: cases and multi-tenancy "from day one (architectural decisions that can't be retrofitted)." Resource fallback: "Cases and tenant isolation deferred to fast-follow … 4 features, ~13-18 stories." If isolation cannot be retrofitted, the fallback is not a fallback; it is a different architecture. *Fix:* Strike the fallback or reclassify isolation as retrofittable with an explicit cost.

## Done-ness clarity — thin
An engineer can take NFR1–NFR31, the ingestion state machine, edge taxonomy, and `--explain` score semantics to a test plan. They cannot take FR1–FR74 the same way. The older one-liner FR shape is acceptable only where nearby tables supply consequences; too many FRs either span later phases with no tag, or refuse the decision that would make "done" checkable. Downstream story creation will over-build Phase 1 or under-specify recovery, identity, and CLI.

### Findings
- **high** Functional requirements are not increment-scoped (§ Functional Requirements vs § MVP Feature Set / CLI Specification) — Seventy-four FRs, one phase tag (FR71: "Phase 2 unless a later sprint change…"). MCP (FR54), EventStore (FR59–FR62), case members (FR28–FR29), annotations (FR37), `memories status` (FR10–FR11), batch directory ingest (FR3), and export (FR71) sit in the same flat list as MVP search/ingest. CLI copy says MVP commands are `ingest`, `search --explain`, `case create/delete`, `tenant create/delete/verify`, and that `status`, `handlers`, and batch directory ingestion are Phase 1.5 — while Journey 9's MVP climax is `memories ingest ./sample-claims/` and NFR4 requires MVP graph-traversal latency with no MVP `traverse` command. *Fix:* Tag every FR with Phase 1 / 1.5 / 2 / 3 (or "not a product FR") so extract does not depend on tribal crosswalk.
- **high** Several FRs have no single testable consequence (§ FR13, FR31, FR43, FR57; soft gate "Case model correctly scopes memory") — FR13: "handles partial backend write failures with defined recovery behavior (rollback or retry to achieve consistency across all axes)" — rollback and retry are different products; "defined" is not a definition. FR31: "health indicators." FR43: "prevents configuration changes that would create data inconsistency without explicit operator acknowledgment." FR57: "discover available actions from any system state." The go/no-go soft gate "Case model correctly scopes memory" is the same adjective problem at ship-checklist level. *Fix:* Pick rollback *or* retry for FR13; replace health/inconsistency/discover with observable outputs; replace the case soft gate with a isolation/ownership test (FR32/FR33/NFR8 already almost are that test).
- **medium** Latency "done" disagrees with itself (§ User Success vs NFR1–NFR3 vs NFR7) — LLM Agent success wants "Search-to-response time at 10 concurrent queries/tenant | <200ms cached, <2s cold." NFR3 wants hybrid p95 <1s at 10K units with no cache distinction. NFR7's "cold start" is service boot within 60s, not query cold. *Fix:* One latency budget per surface (cached/uncached/hybrid) and point User Success at those NFR IDs.

## Scope honesty — thin
Omissions are *mostly* listed (Phase 2/3 bullets, Journey 6/10 scope notes, "Thesis-only MVP is not adoptable," SSPL/AGPL, tenant-delete cross-reference limitation, telemetry "is *not* a tamper-evident audit trail"). That is more honest than a silent backlog. It is not honest enough for a green-light-to-build PRD: there is no Non-Goals section, no `[NON-GOAL for MVP]` on REST/briefing/Python clients/per-unit ACLs, and open-item density is **zero** at launch stakes. The dangerous omissions are the ones the front of the document still performs as in-scope.

### Findings
- **high** Tensions were smoothed instead of opened (document-wide) — No Open Questions, no `[ASSUMPTION]`, no `[NOTE FOR PM]`, no Assumptions Index. The remaining forks (what "MVP" means, RRF vs weighted scores, members without identity, <30 min path, isolation fallback) are exactly the callouts that section is for. At these stakes, empty open-item machinery is a blocker, not cleanliness. *Fix:* Add a short open-item list that names each fork and the owner; do not invent resolved answers in prose.
- **high** Journey scope notes instruct the wrong increment (§ Journey 2, § Journey 9, § Journey Requirements Summary) — Journey 2: "They must be explicitly included in MVP Feature #3 (EventStore Integration) or this journey overpromises." MVP Feature #3 is "Three-Axis Search"; EventStore is Phase 1.5 Feature #1. Journey 9 is listed as **full** MVP, then climaxes with "Alex publishes a test event to the DAPR topic — it appears in the case within seconds." Coverage check still names "Primary user success path: Journey 1" without repeating the feature table's "partial: CLI-only." *Fix:* Re-bind each journey to a phase; delete or rewrite the Journey 2 feature-number instruction; strip DAPR publish from Journey 9 or move it to 1.5.
- **medium** No Non-Goals section where it would do work (§ Phase 2 / Phase 3 vs hero copy) — Phase lists exist, but "Every feature is accessible through both MCP … and CLI," "Both interfaces are first-class citizens," and Marcus/Priya success metrics still read as near-term. *Fix:* A Non-Goals block that names MCP/EventStore/REST/briefing/members as non-goals *for Phase 1*, with the 4-week pull-forward as the only exception.

## Downstream usability — thin
This is chain-top (already fed UX, architecture, epics, sprint changes), so extract quality matters more than for a standalone PRD. IDs are contiguous (FR1–FR74, NFR1–NFR31, Journeys 1–10) and MCP tool names are stable (`search_memory`, `ingest_content`, `traverse_relations`, `get_case_info`). What extract cannot trust is vocabulary or increment. There is no Glossary; the same nouns shift meaning; several "source of truth" pointers already leave the PRD.

### Findings
- **high** Domain nouns collide without a glossary (chain-top extract risk) — "Confidence" is query-result relevance (composite/RRF), per-field metadata confidence, *and* edge-type default confidence; the PRD correctly says scores are "NOT factual accuracy" but FRs still say "composite confidence scores." "Audit" is NFR/FR67 "for audit purposes" and Journey 5's "audit log," while Compliance says this "is *not* a tamper-evident audit trail." "Three-axis" sits beside an `axis=nl` fourth score in the Evidence Packet table. "Member" implies identity the communication model forbids. *Fix:* A short Glossary that pins memory unit, case, tenant, axis (and whether `nl` is an axis), Evidence Packet, confidence (three kinds), audit/telemetry, member; then align FR/NFR wording to those terms.
- **medium** Authoritative shape has already moved out of the PRD (§ Evidence Packet, § Package Distribution) — Evidence Packet "concrete shape is owned by `Contracts.V1` (see Architecture)." Package inventory defers to `tools/release-packages.json` and describes "9 published NuGet packages" plus a "compatibility-only" Redis package. UX and architecture can no longer source-extract the contract from this PRD alone; they will fight it. *Fix:* Either freeze PRD-owned names/IDs and say implementation SoT lives elsewhere, or add an addendum that records post-architecture decisions so the PRD is not a palimpsest.

## Shape fit — adequate
Developer Tool / API Backend is the right class; the load-bearing shape is the capability spec (CLI matrix, pipeline, packages, NFR tables, kill switch), not a consumer multi-stakeholder product. That half fits. The other half is a ten-journey narrative template wrapped around a solo-originally OSS server, still labeled Greenfield while the package section reads like a shipped inventory. Chain-top rigor on IDs and gates is warranted; UJ density at this level is not.

### Findings
- **medium** User-journey density is consumer-product shaped (§ User Journeys) — Ten journeys, including an end-beneficiary who never touches the API (Priya) and a contributor-experience arc (Dani). For this product type, Alex (CLI), Kenji (tenant ops), and the LLM Agent integration path are enough; Journey 7 even admits it is "the system interaction pattern rather than a human narrative," which is the correct shape. *Fix:* Treat Journeys 1, 2, 5, 7, 9 as normative; demote the rest to appendix illustrations.
- **medium** Classification and resource model were not updated when the body was (§ Project Classification, § Resource Requirements vs § Package Distribution / Implementation Sequencing) — Still "Greenfield," "Solo developer. Estimated 22-32 stories." The same document lists published packages, a compatibility-only Redis facade, Aspire AppHost, and `TenantProvisioningWorkflow` as if they were already the system. Downstream will mis-size work and mis-read brownfield constraints. *Fix:* Reclassify as brownfield/in-progress (or "greenfield with implementation underway"), drop or update the solo/story estimate, and date-stamp which sections are still March intent vs patched fact.
