## What Went Well

1. Tenant lifecycle became workflow-backed.
   Story 5.1 added `TenantProvisioningWorkflow`, tenant registry state, per-backend provisioning activities, verification, compensation, and tenant endpoints. Story 5.2 added destructive deletion as a resumable workflow with idempotent backend cleanup and batched FalkorDB deletion.

2. The isolation model stayed physical.
   RediSearch and Redis Vector use tenant-namespaced indexes. FalkorDB uses a dedicated graph database per tenant. The implementation stayed aligned with the architecture's hard rule that graph isolation is database-level, not label-level.

3. Tenant state became enforceable at the API boundary.
   `TenantStatusGuard` grew from deletion protection into shared validation for active-only and existence-only paths. Story 5.4 corrected the `TENANT_NOT_FOUND` status mapping and applied registry validation to partially protected endpoints.

4. Isolation verification became an operator-facing diagnostic.
   Story 5.3 added `TenantIsolationVerifier` and structured result contracts. It checks index existence, syntactic and semantic leakage, graph structural isolation, input validation, and orphaned databases while reporting backend unavailability as check failures rather than crashes.

5. Corruption detection was added below the endpoint layer.
   Story 5.4 added `TenantMismatchMonitor` and `CaseService` mismatch checks. The user-facing behavior remains 404, while operators get a Critical `TENANT_MISMATCH` signal if stored data claims a different tenant than the request path.

6. Tenant operations became visible.
   Story 5.5 changed `GET /api/tenants` to return enriched summaries, added configuration views, exposed index health, memory-unit counts, `lastActivityAt`, `reindexRequired`, and display-name updates with structured operational logging.

7. Embedding provenance reached the memory unit.
   Story 5.5 carried `embeddingModel` through ingestion, indexing, graph indexing, and memory-unit reads. That gives future audit and reindex flows the provider/model evidence they need.

8. Degraded read behavior was tightened.
   Story 5.6 added typed 503 responses for single-axis backend failures, graph unavailability, and total hybrid failure. Hybrid partial failure remains a 200 degraded response when at least one enabled axis succeeds.

## Challenges

1. Gate 2 evidence relied too heavily on skipped Aspire fixtures.
   Stories 5.1, 5.3, 5.4, 5.5, and 5.6 all contain deferred integration coverage. Story 5.2 carried stronger integration coverage, but the epic as a whole still needs executable cross-component proof before the isolation gate should be treated as fully accepted.

2. Physical isolation and authorization were easy to conflate.
   Epic 5 validated tenant IDs and guarded registry state, but full identity-to-tenant authorization remains deferred. `deferred-work.md` tracks `Story-9.3-MemoriesServerAuthN` because Memories Server still needs a cross-cutting authN/authZ retrofit.

3. Some product language outpaced MVP infrastructure.
   The PRD described audit-trail behavior. Story 5.5 correctly narrowed that to structured operational logs for MVP and pinned field names for a future durable audit store.

4. Tenant listing introduced an intentional pattern shift.
   Earlier tenant lifecycle work used workflows for state changes. Story 5.5 added direct registry update from an endpoint for display-name changes. The implementation used CAS and logging, but this pattern should stay rare and deliberate.

5. DAPR and Aspire boundaries shaped the test strategy.
   DAPR API token behavior is runtime-owned, and several integration paths need the AppHost fixture. Unit tests can pin logic, but they cannot prove the full sidecar, token, and backend behavior.

6. Degradation semantics needed careful distinction.
   Story 5.6 had to separate partial hybrid degradation from total backend unavailability, graph backend unavailability from graph query timeout, and missing indexes from transient backend failure.

7. Tenant lifecycle and case lifecycle remain coupled risks.
   Epic 4 and prior retros identified case deletion and dedup lifecycle concerns. Epic 5 improved tenant-level deletion and guard behavior, but lower-level lifecycle carry-forwards still affect the trust story around deletion and re-ingestion.

## Key Lessons

1. Tenant isolation is not a single feature.
   It spans provisioning, deletion, search, ingestion, graph traversal, configuration, tenant registry state, actor state, endpoint validation, and backend failure semantics.

2. Physical separation is necessary but not sufficient.
   Separate indexes and graph databases reduce leakage risk, but registry validation, mismatch monitoring, and verification endpoints are what make failures observable.

3. Operator diagnostics must degrade instead of crashing.
   Isolation verification, tenant summaries, and search degradation all need to report unavailable infrastructure explicitly. A diagnostic surface that fails closed without context is not useful to operators.

4. Runtime-owned security needs runtime proof.
   DAPR API tokens and sidecar behavior cannot be fully proven by unit tests. The project needs stable fixture coverage for sidecar-level checks.

5. Integration deferrals should have a single owner and a gate.
   Epic 5 created many skipped scenarios. The next quality move is not adding more placeholders; it is converting the existing ones into a reliable Gate 2 execution set.

6. Deletion is an isolation feature.
   Tenant deletion is not cleanup only. It prevents stale data, cross-tenant confusion, and lifecycle drift across Redis keys, indexes, graph databases, registry entries, and future actor state.

7. Configuration changes are data-integrity events.
   Embedding provider/model/dimension updates can invalidate existing vectors. Story 5.5 correctly treats breaking changes as explicit operator acknowledgments rather than casual settings updates.

## Significant Discovery Check

Epic update required: yes for Gate 2 exit criteria, not because Epic 5's direction was wrong.

The planning assumption that physical isolation plus endpoint enforcement would satisfy Gate 2 is directionally sound, but Epic 5 revealed that the acceptance evidence must be stricter than story status. The project needs an explicit Gate 2 sign-off checklist that treats deferred integration fixtures, tenant auth posture, graph metadata, gap markers, and deletion/re-ingestion edges as acceptance items.

Significant changes to carry forward:

1. Gate 2 requires executable isolation proof, not only unit coverage and skipped integration scaffolds.
   Impact: Stories with skipped Aspire scenarios cannot be used alone to claim hard-gate completion.

2. Memories Server authN/authZ is a separate cross-cutting security story.
   Impact: Epic 5 proves tenant ID isolation and DAPR token setup, but not full caller-to-tenant authorization on the Server surface.

3. Graph metadata and gap markers remain tenant-sensitive.
   Impact: traversal checks should inspect returned nodes, connected IDs, edge metadata, and gap identifiers.

4. Operational logs are not a durable audit trail.
   Impact: product language and future compliance work should distinguish MVP operational logging from Phase 2 audit storage.

## Team Agreements

- Tenant isolation changes require evidence across all three backends, not only one happy-path endpoint.
- Graph responses are security-sensitive because metadata and gap markers can leak relationships even when node payloads are absent.
- DAPR token configuration is channel security; it is not tenant authorization.
- `TENANT_MISMATCH` must stay internal-facing and operator-visible, with user responses staying non-leaky.
- Skipped integration tests are acceptable only when they are tracked as gate debt with an owner.
- Configuration updates that affect indexed data require explicit integrity handling.
