### Blocking defects

**F1 — Current-set retained-byte recovery cannot succeed on a GitHub runner. CONFIRMED, reproduced.**

What happens:

- `verify_tagged_deployment` (`tools/container-publication-contract.py:578-598`) rebuilds the tagged renderer inputs with `git show <tag>:<path>` and `write_text`. That produces blob bytes, which are LF.
- It then byte-compares the re-rendered deployment with the retained one (`:597`).
- The release run renders from a checkout. Under `* text=auto eol=crlf` (`.gitattributes:2`), the checkout materializes `deploy/kubernetes/base/config/redis-stack.conf` as CRLF, because `git check-attr` reports `eol: crlf`.

Evidence:

- The published v4.0.0 deployment (release evidence `artifacts/deployment/hexalith-memories-production.yaml:289,293`) embeds `"appendonly yes\r\n…"` and names the ConfigMap `redis-stack-config-444ff7t4hh`.
- Reproduction: `kubectl kustomize deploy/kubernetes/overlays/production` gives `redis-stack-config-444ff7t4hh` with CRLF input and `redis-stack-config-tfmk6ftkcm` with LF input.
- So every current-set recovery would fail closed with "Retained deployment differs from the tagged renderer".

Why the fixtures miss it:

- `partial_release_recovery_test.py:108` copies a local working tree in which the file is LF (0 CRs), so both sides render LF.
- Nothing tests `verify_tagged_deployment` with attribute-applied bytes.

The failure is safe: nothing is published wrongly. But the 30.5 AC "publishes only the missing members" cannot be met live.

- *Source:* edge-case-hunter lens; reproduced by the parent.
- *Instance:* fix now (action A1).
- *Prevention:* fixtures for hash-bound or rendered artifacts must take their inputs through the same Git attribute path as CI, for example `git archive`.

**F2 — The privileged production recovery job runs mutable `@main` Builds code. CONFIRMED.**

What happens:

- `recover-partial-release.yml` declares `environment: production`, `id-token: write`, `contents: write` and `issues: write` (`:64-73`), and the job receives the Zot secrets.
- It runs `Hexalith/Hexalith.Builds/Github/initialize-dotnet@main` (`:120`, `:167`) and `initialize-build@main` (`:250`, `:253`).
- The call at `:167` runs after the "Stage trusted recovery tooling" step.
- `CiTestInventoryTests.cs:1132` and `:1140` codify the moving ref: they accept `initialize-build@main` and reject `initialize-build@ae77d569…`.

Why it matters:

- This contradicts the epic Technical Decision "Pin shared GitHub callers to an approved … SHA … do not use a moving ref" (`epic-30-context.md`).
- Any push to Builds `main` executes inside a job that can mint a NuGet Trusted Publishing key and write to the registry.

How it happened (cross-story causal chain):

- The 30.3 review deferred regenerating `epic-30-context.md` because its rewrite in `637eaa1b` had dropped "never `@main`" and other binding constraints (`deferred-work.md:6033-6037`).
- The deferral's trigger, "30.4 is created", fired, and nobody acted on it.
- 30.5 (`e201f169`) then added `environment: production` and `id-token: write` to a job that still used `@main`.

- *Source:* aggregate views and the adversarial and edge-case lenses; re-checked by the parent.
- *Instance:* fix now (action A2).
- *Prevention:* a deferral whose trigger is "next story created" must block that story's creation, not wait in the ledger. A privileged-job action-pin rule belongs in the inventory test, not an allow-list of `@main`.
