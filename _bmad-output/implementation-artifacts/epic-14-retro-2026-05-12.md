## What Went Well

1. The epic stayed aligned to deferred-work IDs.

   Each story had a clear set of targeted IDs. Story records identify what was resolved, accepted, or carried forward, with evidence. That made the epic auditable rather than a loose cleanup pass.

2. Review patches found real defects before closure.

   Examples include invalid bash PID expansion in CI, absolute-path handling in package validation, forced-refresh OIDC races, Redis wait behavior still using broad key enumeration, and missing required-field enforcement in the deferred-work parser.

3. The team preserved scope discipline.

   Stories were narrow even when adjacent tempting work existed. The untracked solution file in Story 14.5 was removed rather than normalized into scope, and submodule discipline remained explicit.

4. Validation evidence was specific.

   Story records name focused test counts and commands: story-scope tests, release-package fixtures, `CiTestInventoryTests`, Server.Tests, migration tests, fake-server tests, and the Ollama end-to-end lane after the AppHost endpoint fix.

5. Governance improved without rewriting history.

   Story 14.5 avoided a broad historical register migration. It added a forward-looking schema and migrated the target set only, which gave tooling a stronger contract without churn.

## Challenges

1. Deferred work had become unevenly structured.

   Before Story 14.5, tooling had to infer meaning from prose tokens like `baseline`, `release lane`, or heading formats. That worked until it became fragile. The new field schema fixes the pattern for future active entries.

2. Several risks were cross-cutting rather than local.

   Security, release, and migration issues touched tests, docs, workflows, helper scripts, and production code. The stories handled this, but the scope needed repeated clarification to avoid silent expansion.

3. Some hardening required infrastructure proof.

   Story 14.4 could not close cleanly until the Ollama end-to-end lane actually passed. The AppHost endpoint launch-profile fix was outside the original file scope, but it was the minimal change needed to prove the required integration path.

4. The codebase still carries consciously open risks.

   Not every deferred ID was closed. Examples include stale-tag preflight (`S11-FC`), TLS policy for non-loopback token endpoints (`13.2-RV4`), provider/model/dimension registry hardening (`13.1-RV6` and related provider work), migration-vs-ingestion coordination (`13.6-RV1`), and shared repository-root helper cleanup (`13.7-RV4`).

5. Broad validation can be environment-sensitive.

   Story 14.4 needed temporary SDK setup and Aspire topology diagnosis before the E2E lane passed. Story records handled this honestly by separating compile/focused evidence from runtime integration evidence until the latter was actually green.

## Significant Discoveries

1. Governance is executable architecture.

   Story-scope checks, release inventory validation, deferred-work schema, and sprint-status conventions are not paperwork. They directly shape whether future work remains auditable and safe.

2. Deferred IDs need lifecycle semantics.

   `resolved`, `accepted`, and `carried-forward` are different outcomes. Story 14.5 made that distinction machine-checkable for structured entries and human-readable for planning.

3. Security hardening benefits from realistic examples.

   Redaction tests became stronger when they asserted against actual bearer tokens, JSON token fields, Google keys, AWS-shaped keys, HTTP Basic credentials, and secret-name references.

4. Release correctness depends on inventory, not trust.

   Schema-backed package inventory and explicit packable/non-packable accounting make release behavior reviewable before semantic-release and NuGet publishing are involved.

5. Integration fixtures are product infrastructure.

   The Ollama E2E path exposed an AppHost endpoint assumption. Fixing it improved the credibility of the provider migration evidence, not just a test.

## Preparation For The Next Work

No Epic 15 definition was found in `epics.md` or `sprint-status.yaml`. Preparation therefore applies to the next planning item that touches release, provider, migration, or governance work:

- Start from the open and carried-forward deferred IDs, not from memory.
- Treat provider/model/dimension changes as migration events.
- Require integration proof for fixture or provider changes that claim operational readiness.
- Keep release and sprint-status evidence linked, not embedded as long inline status narratives.
- Preserve root-level submodule discipline and do not initialize nested submodules unless explicitly requested.

## Team Agreements

- Every deferred item closed by future work needs evidence, not just discussion.
- `accepted` means an intentional risk decision; `carried-forward` means a named future trigger or artifact owns it.
- Story-scope and release guardrails are product infrastructure and should receive tests when behavior changes.
- Security tests should use realistic sensitive values and prove those values do not leak.
- Integration-test fixture fixes should preserve default paths and keep opt-in provider modes explicit.
- Sprint-status history should remain a navigation layer, not a full transcript.
