# Architecture Spine — Hexalith.Memories

> **Current McpCli disposition (Story 5.11 candidate):** The proprietary CLI/MCP phases, ingress topology and installation commands below describe retained compatibility. There is no promised generic migration or diagnostics surface. No Memories operation is enrolled in the current shipped McpCli cohort. Forwarded per-user HTTP authority is necessary but insufficient for retirement; tenant/user/administrative authorization, semantics, release and rollback evidence remain. PS14 stays owner-held local tooling in all four modes, never counted retired.


**Release decision, 2026-11-20.** Phase 1 remains **no-go**. The Administrator stewards the G1 corpus. Two independent reviewers, a frozen corpus, and a qualifying run are still needed. The default search and the enrolled CLI journey also lack qualifying evidence. L1–L3 remain unevaluated. [PRD release decision](../../prd.md#release-decision-record)


## Design Paradigm

**Shared environment ownership.** Hexalith.Platform operates shared local, CI and hosted environments through the Hexalith.Builds runner. Memories supplies the services, hosting declarations and probes. The local retention run and the conditions for reopening Production qualification are recorded under AD-17.

Hexalith.Memories is a **technical platform module**, not a domain module. It uses event-sourced CQRS with ports-and-adapters: Hexalith.EventStore accepts domain mutations, Dapr workflows coordinate durable projection work, Redis and FalkorDB hold rebuildable query models, and public surfaces depend on versioned contracts and client packages. Memories owns its reusable services, ServiceDefaults/Aspire integration packages and module declarations. Hexalith.Platform owns the shared AppHost composition, infrastructure and local/CI/hosted environment lifecycle through the supported Builds runner; Memories deployment assets are conformance inputs to that composition.

Logical dependencies point inward to contracts and ports. The current physical EventStore integration assembly is mixed; only its `Domain/` namespace is the dependency-pure domain center.

```mermaid
flowchart LR
    Surfaces[CLI · MCP · Web host · REST clients] --> Contracts[Contracts.V1 and Client ports]
    Platform[Hexalith.Platform composition and lifecycle] --> Hosts[Memories services · reusable hosting packages]
    Hosts --> Contracts
    Hosts --> Application[Application services · workflows · actors]
    Application --> Domain[EventStore domain commands and events]
    Application --> Ports[Search · graph · state · secret · AI ports]
    Adapters[Redis · FalkorDB · Dapr · OpenBao adapters] --> Ports
    Domain --> Contracts
```

Rules below are the adopted target architecture. Where current code differs, the rule remains binding and the difference is implementation work, not a competing decision. Where a rule is not yet mechanically enforced, the rule or its ledger row says so; an unenforced rule is still binding but is a weaker guarantee. The Current Alignment Gaps ledger is the index of outstanding enforcement obligations, and the index is itself a rule: **a rule that names an owner, a store, a state vocabulary, a principal, or any other mechanism the architecture has not yet defined carries a ledger row naming that mechanism**, and a reader may treat an obligation absent from both the rule text and the ledger as not yet governed. A spine revision that adds such a rule without its row is incomplete; the reviewer gate found that omission in each of the three preceding passes, which is why the obligation is stated here rather than left to review.

## Invariants & Rules

### AD-1 — Treat Memories as a reusable technical platform [ADOPTED]

- **Binds:** All projects, packages, hosts, deployment assets, and consuming products.
- **Prevents:** Domain consumers depending on orchestration hosts or copying platform composition into product code.
- **Rule:** Consumers use published contracts, clients, and Aspire integration packages and never reference AppHost or Server; dependency-pure domain namespaces contain no orchestration, host, or provider-SDK concerns even when a brownfield assembly also contains integration code. Memories owns reusable services, hosting packages and declarations; Hexalith.Platform composes them in its AppHost and owns environment provisioning, readiness, run ownership and cleanup through Builds. For Production commands and replay, Hexalith.Platform supplies the external Hexalith.EventStore gateway endpoint, configures the deployment route to the Memories DomainService and owns operational readiness. Memories owns its native Server, DomainService image, SDK handlers, route declarations and consumer-side qualification. Its qualification evidence must exercise the authenticated gateway-to-DomainService route for each of the three declared domains. Reusable ServiceDefaults/Aspire packages do not transfer that lifecycle ownership to Memories.

### AD-2 — Keep EventStore as domain mutation truth [ADOPTED]

- **Binds:** FR75, case, MemoryUnit, annotation, deletion, tenant lifecycle, rebuild, restore, and release evidence flows.
- **Prevents:** Redis, FalkorDB, workflow state, or package topology becoming an accidental second system of record, and an availability restore being mistaken for an authoritative rebuild.
- **Rule:** Accept domain mutations through Hexalith.EventStore before reporting success, then rebuild derived stores from authoritative events; keep domain truth, Phase 1.5 CloudEvent indexing/causal integration, and source-versus-package evidence as three distinct contracts. Recovery keeps three inputs distinct: authoritative EventStore replay is the only rebuild that may set projection truth; shared Redis/FalkorDB projections and tenant-keyed coordination state have no operational backup-restore path and recover through that replay; application export restore is an import subject to normal ingestion rules. A historical or future derived-store snapshot that lacks AD-16 tenant-key protection is a purge target, never an availability shortcut. AD-16's erasure constraints override every recovery input, and authoritative replay, any admitted tenant-key-protected restore, and application import each consult AD-21's erased-tenant register before admitting a record and fail closed when it is unavailable.

**Recovery admission.** A pre-write refusal permits a retry only on a demonstrably clean, active target with the original live tenant ID and matching configuration. If writes may have occurred or verification fails, pause intake, preserve the partial state and keep the target offline. DW-733 requires a disposable live-tenant drill with final counts, searches on every required axis and an unaffected control tenant. An erased or uncertain origin remains fenced. [Restore stop conditions](../../../../docs/operations/backup-restore.md#rollback-and-stop-conditions)

### AD-3 — Complete source-versioned projections as one logical outcome [ADOPTED]

- **Binds:** FR6, FR13, FR75, ingestion status, retries, reconciliation, syntactic indexes, vectors, graph projections, checkpoint invalidation, concurrent tenant erasure, and query degradation.
- **Prevents:** Partial fan-out being exposed as complete, stale acknowledgements completing a newer revision, a legitimate new-epoch reprojection being suppressed as stale, a late write overwriting newer projected content or recreating tenant data after erasure has fenced it, a deliberately invalidated checkpoint being read as work never attempted, a write carrying a non-active tuple being dropped into a resource its phase never defined, or ingestion completeness being confused with query availability.
- **Rule:** One Dapr-state projection coordinator owns a durable checkpoint for each `(tenantId, caseId, memoryUnitId, schemaGeneration, embeddingConfigurationEpoch)`. Its current work is identified by `(sourceVersion, attemptRevision)`. The first value is the authoritative EventStore revision. The second is a monotonically increasing revision issued by that checkpoint’s coordinator. Ordinary retries and restarts reuse the pair. Every success or failure carries the pair issued before the work began.

**Starting and invalidating work.** On a newer source version, or detected projection loss or inconsistency at the current version, one ETag/CAS advances the attempt revision, preserves or advances the source version, and clears all three axis acknowledgements. Invalidation also records `reprojectionRequired` and its reason. It expects the previous version and attempt, so repeating the same invalidation has no effect. The durable record lets a restarted coordinator resume the outstanding attempt. A missing record means first use only when continuity of the coordinator store and the current generation establishes that the checkpoint was never created.

**Coordinator loss.** When an established checkpoint disappears or may have rolled back, stop dispatch and acknowledgement counting for its scope. Report repair pending. To reuse the same generation, recover a proven upper bound on every attempt revision already issued for that checkpoint, including in-flight work, then CAS a new revision above that bound with all acknowledgements empty. A surviving target's last observed revision alone cannot prove that bound. If issuance history is uncertain, recover by authoritative replay into a fresh, never-reused AD-14 schema/epoch pair under the applicable migration and admission rules. Only fresh confirmations in that pair can establish completion. Until verification and cutover, the affected status stays pending or failed with recovery guidance.

**Target write fence.** For each checkpoint identity, every axis maintains a durable target-local fence ordered first by source version and then by attempt revision. The coordinator authorizes installation of the current pair. Installation may advance the fence or confirm it idempotently. A superseded installation cannot lower it. Each projection upsert, delete and tombstone atomically compares its own pair with the installed fence in the operation making the mutation visible. Only an exact match may write. The fence survives loss or deletion of the document. Ordinary work cannot create or reset a missing fence. If an established target loses the fence itself, the adapter closes admission to writes and fence installations for that scope. Recovery must drain or revoke all prior write and installation authority, verify that no old operation can still commit, then obtain the current pair from the coordinator and durably install it before reopening. If that proof is unavailable, the target stays closed.

**Completion.** After its current fence is installed, an axis writes or verifies the projection for this source version under that fence. Only this observation can acknowledge the issued attempt. A coordinator CAS counts each axis once and only against the exact current pair. Delayed writes, successes and failures from older attempts cannot displace repaired data or supply completion evidence. Only all three current syntactic, vector and graph acknowledgements permit `Indexed` and clear `reprojectionRequired`. Otherwise the persisted state remains `indexing` with the relevant reason or records actionable failure. Status, case activity and counters publish the same transition. Use the V1 wire vocabulary in Consistency Conventions.

**Projection scope.** Each schema generation and embedding epoch has its own checkpoint and derived document for the unit. The active pair and each declared AD-14 rebuild or staging pair write disjoint documents. Undeclared pairs produce an actionable out-of-generation failure. Public ingestion status follows the tenant’s active pair. Other pairs report only migration progress. Queries read through the AD-10/AD-14 lease. AD-14 retirement removes the retired documents, checkpoints and target fences only after readers have drained and late writers and installers have been fenced out.

- **Concurrent-erasure fence:** Every projection activity captures AD-16's tenant lifecycle write generation when its work is admitted. Every target fence installation or recovery, syntactic, vector, graph, derived-document-tombstone, and checkpoint write presents that generation and compares it atomically with the target's writable generation in the same backend operation that would make the write visible; a separate lifecycle read followed by a write does not satisfy this rule. A stale or closed generation rejects the write without mutating projected state. Where a target cannot provide that atomic comparison, its adapter must instead prove that the tenant-scoped write authority has been revoked before AD-16 begins purge.

A managed-source refresh exposes only the published version across retrieval axes. The read path refuses a changed publication window that it cannot verify. This visibility check supplies no missing axis acknowledgement.

### AD-4 — Give workflows, activities, actors, and idempotency distinct roles [ADOPTED]

- **Binds:** FR75, Dapr orchestration, retries, actor state, concurrency, replay, external I/O, duplicate suppression, and durable state content.
- **Prevents:** Nondeterministic replay, actors used as queues, duplicate side effects, secrets or tenant content in workflow history, and transient Redis reservations becoming durable truth.
- **Rule:** Workflows are deterministic process managers, activities are bounded idempotent I/O operations, and non-reentrant actors serialize only tenant or global stateful concerns. Capture immutable non-secret configuration plus its epoch at start and retain secret references only. Workflow history and activity payloads carry identifiers, references, and non-secret configuration only: tenant content and content-derived material — extracted text, embeddings, snippets — are read at execution time from the **tenant content store** and are never persisted into workflow history or actor state. That store is a named tenant resource, not a property: AD-6 provisions and erases it with the tenant's other resources, its contents are written under the tenant key so AD-16 crypto-shredding reaches them, AD-16 names it in its enumerated purge targets, access to it derives tenant authority under AD-5 like any other tenant resource, and its capacity is an AD-18 tenant quota. An activity that cannot resolve it fails closed rather than falling back to a payload. Scope V1 `IdempotencyToken` by tenant, case, and command/operation; scope CloudEvent identity by tenant, case, validated `source`, and `id`. `source` and `id` are externally supplied and are therefore validated at the ingress trust boundary against a declared bounded character set, length-bounded, and canonicalized there exactly once in a stated form (scheme and host lowercased, no other change); thereafter they are compared ordinally with no further normalization. Because neither is issued under AD-23's grammar, neither is composed into a key in raw form — AD-23's injective-composition rule governs how they enter one. The shipped reservation key hashes `id` and omits `source`, so it does **not** implement this identity and remains an alignment gap. Use the adopted identity for durable EventStore/workflow duplicate suppression and make every projection an idempotent upsert for AD-3's tuple; a legitimate reprojection under a new schema generation or embedding-configuration epoch is not a duplicate and is never suppressed. Redis preflight is a fail-open admission optimization with a finite TTL. A CloudEvent preflight hit without confirmed durable acceptance yields a retryable outcome. Each successful acquisition stores its own fresh, opaque token. Every failure or cancellation cleanup, including cleanup after an uncertain write, atomically compares the stored token and deletes only a matching reservation. An acquisition token is distinct from the stable operation identity and is never reused on retry. TTL bounds cleanup when ownership cannot be confirmed.

For URL ingestion, logs and case activity identify work by its unit or workflow ID throughout enqueue, fetch, retry, duplicate and failure paths. The fetcher receives the original URL, and the deduplication identity preserves it within tenant and case scope. The durable workflow needs a reference to retrieve that value under the content rule above. DW-732 covers display and scoped identity. The history gap is recorded below.

### AD-5 — Derive tenant, case, and caller authority server-side [ADOPTED]

- **Binds:** NFR8-NFR11, external APIs, MCP, Dapr ingress and pub/sub delivery, tenant/case access, Redis, FalkorDB, background and resumed durable work, system and operator principals, and the operator artifact. Identifier issuance and key composition are AD-23's.
- **Prevents:** Request fields, envelope fields, case membership, key prefixes, graph labels, channel tokens, or a caller-selected app identity from serving as authorization; two writers of one authorization decision; a privileged principal that authorizes work while being derivable from nothing; and an exempt class of work that no mechanism binds to a tenant.
- **Rule:** Treat issued tenant and case IDs as validated opaque tokens and compare them with `StringComparison.Ordinal`, without case folding or Unicode normalization after issuance; AD-23 owns what makes them safe to compare that way. The native REST and compatibility CLI/MCP paths preserve validated bearer tenant and subject authority. The shared Gateway calls under workload authority and forwards no user credentials. Before enrolling an operation that needs a user, demonstrate its authenticated tenant and user authorization, including denied access, on the selected transport. A caller-supplied tenant or actor value cannot satisfy this requirement. Trusted internal calls additionally require deny-by-default Dapr mTLS/access-control policy and app-token channel protection, then satisfy three independent checks — an app ID present in the allowlist, an explicit grant for the requested tenant, and that tenant being currently `Active` in AD-6's lifecycle state machine — any one of which failing closed. **One deployment-time artifact, the operator artifact, carries three operator-controlled identity, privilege, and routing facts plus their revocation bound** — the app-ID-to-`system:*` allowlist, the per-operator-scoped-app-ID list of lifecycle operations each may invoke, and the exact authenticated pub/sub channel-identity tuple `(subscribing component, topic, authenticated publisher)` to candidate-tenant routing map — with exactly one writer, the operator, held in AD-15's operator secret scope rather than in ordinary configuration or component YAML, versioned, and changed only through a reviewed and observable procedure. The allowlist and operation list grant principal identity and privilege; the routing map selects a candidate tenant but never grants tenant authority. An absent app ID fails closed with no default principal; grants are enumerated and any wildcard requires its own architecture decision. **An operator principal is an ordinary authenticated identity marked operator-scoped in that artifact** — a human operator's OIDC issuer-plus-subject or an allowlisted workload app ID, authenticated by the same mechanisms as every other principal, carrying no tenant claim by construction. Because it carries none, NFR8's principal-driven verification is extended to cover it: the isolation suite authenticates as an operator principal and asserts that every non-exempt operation it attempts against a tenant is refused. The per-tenant grant that pairs with the allowlist is a tenant resource whose sole writer is AD-6's lifecycle workflow. Its **membership at provisioning is an explicit app-ID set in the tenant's AD-6 lifecycle evidence, authorized by the initiating operator principal and limited to app IDs already present in the operator artifact's allowlist**, then materialized by verified provisioning; adding or removing an app ID on a live tenant is an AD-6 grant-amendment lifecycle operation and not an edit to the operator artifact; and every grant is revoked as a completion condition of AD-16 erasure. **Revocation propagates within 60 seconds:** the versioned AD-5 operator artifact is the authoritative home of `revocationMaxAgeSeconds = 60`; a revoked grant, removed allowlist entry, or withdrawn operator authority stops authorizing within 60 seconds of its committed or published change. No cached authorization decision, session, or in-flight durable work established under superseded authority outlives that window; long-running activities refresh authority or stop before it expires, and unavailable freshness proof fails closed. A longer value requires a new architecture decision. AD-15 uses the same bound for rotated credentials. Dapr pub/sub ingress derives tenant authority from the delivery channel and never from the envelope: **the receiving component or topic is bound to one candidate tenant, or the operator artifact maps the delivery's authenticated channel identity — the subscribing component and topic, and the publisher identity Dapr authenticated — to one candidate tenant. Admission then applies the same allowlist, explicit per-tenant grant, and `Active` lifecycle checks as any trusted internal call. No field the publisher sets may select or authorize the tenant, and `source` is a publisher-set envelope field:** a routing map keyed on `source` lets a publisher choose the tenant it writes into and is forbidden by this decision's own *Prevents*, whatever its matching rule. The shipped `TenantEventRoutingOptions.SourceToTenantMap` is exactly such a map and is an alignment gap, not an implementation of this rule. Channel-identity tuple lookups are exact and ordinal; an envelope tenant that differs from the authorized candidate tenant is rejected rather than ingested, a delivery whose channel resolves to no tenant is rejected, and the resolved tenant must pass all three internal-call checks. Work with no human caller — workflows, activities, actors, reminders, data repair, replay, and migration — carries an explicit tenant authority captured at initiation, revalidates it against the tenant's lifecycle state on every resume and at each activity boundary, and fails closed when the tenant is not `Active`, is erased, or is absent from the initiating principal's grant; captured configuration is not authority. **Exactly three exemptions from that fail-closed exist, and no other decision may add a fourth without amending this list.** (1) AD-6 lifecycle workflows and (2) AD-16 erasure act on their own subject's lifecycle state, so they revalidate the lifecycle state for that operation. After shredding, only the AD-16 verifier may use its generation-bound platform preparation to finish the same deletion, subject to the operator and lineage checks below. Each such workflow is authorized by an operator principal; is **scoped at initiation to exactly one tenant identifier recorded in its lifecycle evidence, which it may not change on resume or retry**; revalidates that operator principal — not the tenant — at every resume and activity boundary and fails closed when its authority has been withdrawn; and reaches **only the operations the operator artifact enumerates**, which are exhaustively: tenant provisioning and tenant-resource creation, tenant verification, lifecycle repair, grant amendment, per-tenant credential rotation, tenant-resource migration setup and retire, access-telemetry partition provisioning and revocation of ordinary access at erasure handoff, tenant deactivation, tenant deletion, and AD-16 erasure including tenant-content-store erasure and generation-bound completion. Every other call such a workflow makes satisfies all three internal-call checks. **No enumerated operation may create, re-provision, or restore any resource for a tenant present in AD-21's erased-tenant register**, and an enumerated operation that cannot reach the register fails closed. The exemption travels with the calling principal and never with the request: a receiving service recognizes a lifecycle call from the authenticated caller identity mapped through the operator artifact — never from a header, flag, or field the caller sets, which `Prevents` forbids — accepts it only for an enumerated operation, only from an app ID the artifact marks operator-scoped, and only when its authenticated workflow-instance scope reference resolves to the same single tenant identifier recorded in the lifecycle evidence; the request tenant must equal that bound tenant. It applies all three internal-call checks to every other call from that same identity. An all-tenant grant remains a wildcard requiring its own architecture decision and is not created by this clause. (3) AD-17 retention accounting, including acknowledgement of a handoff for the single tenant in `Deleting`, post-erasure TTL expiry, removal of the empty retained partition and its locator, and the separate purge receipt, is authorized by Platform Operations' own operator-scoped principal and is bounded in AD-17. Adding an operation or an exemption to this list is an architecture decision, not a configuration change. Dapr channel authentication never replaces tenant authorization.

- **Platform bootstrap boundary:** AD-21 genesis creation is a one-time platform operation under AD-15's authenticated deployment-bootstrap identity and secret scope, not a tenant-scoped call or a fourth lifecycle exemption. That identity has no tenant-data, tenant-resource, export, or tombstone capability; ordinary deployment and Server startup can verify an existing genesis only. The AD-15 deployment bootstrap scope records an expected `populationId` and one-time consumed grant outside EventStore; genesis creation is permitted only for a first-ever population while that grant is unconsumed, and uncertainty fails closed. A missing or mispointed prior lineage may never be treated as a fresh population by a routine restart. A clean-room population after total lineage loss requires a separate architecture decision on disjoint identity issuance.

### AD-6 — Make tenant lifecycle the sole resource owner [ADOPTED]

- **Binds:** Tenant provisioning, verification, repair, deactivation, deletion, the tenant lifecycle state machine, operator authorization of lifecycle work, the AD-21 erased-tenant register consult, indexes, graphs, backend identities and credentials, per-tenant grants, the tenant content store, the access-telemetry partition, and cleanup.
- **Prevents:** Startup or ingestion hot paths implicitly creating tenant resources and leaving unowned partial resources behind; an erased tenant identifier being re-issued or its resources re-created by repair; and a lifecycle state that authorizes work while no decision enumerates it.
- **Rule:** Perform tenant resource changes only in explicit, idempotent, observable, bounded lifecycle workflows with verification, compensation, and resumable cleanup. **AD-6 owns the tenant lifecycle state machine and is its sole writer.** Its states are the `Contracts.V1` `TenantStatus` values — today `Provisioning`, `Active`, `Deleting`, `Failed`, `CompensationFailed`, extended additively under AD-12 with `Deactivated` and with `Erased`, which is terminal and irrevocable — and that enum is the single definition site for the vocabulary; no decision, surface, or store defines a parallel one. Every transition except terminal `Erased` is an AD-2-committed domain event on the `memories-tenants` stream and is committed **before** the resources it authorizes are touched. `Erased` is derived only from AD-21's irreversible platform tombstone; no event is appended to the shredded tenant stream after completion. Because AD-16 crypto-shredding destroys the tenant key, a content-free projection of each tenant's identifier, current state, and transition time is mirrored onto AD-21's platform partition for post-shred observability. **That projection never authorizes a request:** every admission of ordinary ingress or a tenant-content read for a non-erased tenant reads its authoritative committed `memories-tenants` state and requires `Active`; an unavailable authoritative read fails closed. Each product read holds its own bounded lease from the tenant's query-admission gate. At admission it binds the tenant lifecycle generation and one active pair (schema generation, embedding epoch) and holds that lease through the last response byte. AD-14 cutover keeps the admitted pair readable until the lease drains. Erasure revocation stops egress even for a leased pair. No cached copy held by the tenant configuration actor or lagging platform mirror supplies authority. The `Erased` state is set **from** AD-21's register rather than beside it — the register remains the sole authority on erasure and the state machine reads it — so the two can never disagree. Provisioning is authorized by an operator principal under AD-5 and **consults AD-21's erased-tenant register before issuing a tenant identifier**, failing closed when the register is unavailable, unreadable, or older than the newest erasure it records; provisioning and lifecycle repair refuse any tenant in `Deleting` or `Erased`, so no compliant repair can re-create an erased tenant's ACL principal, graph, telemetry partition, or grant. Redis uses a per-tenant ACL principal resolved server-side; FalkorDB selects a separate tenant database/graph; AD-6 provisions the isolated AD-4 tenant content store and erases it under AD-16. It also provisions the AD-17 telemetry principal or partition. During erasure it closes ordinary access and hands the retained opaque records to Platform Operations. AD-17 governs final partition removal after expiry. Other paths require an `Active` verified tenant and never create infrastructure implicitly.

- **Legal transitions:** New identifiers enter `Provisioning`; `Provisioning` may enter `Active` only after resource verification, or enter `Failed`, `CompensationFailed`, or `Deleting`. `Failed` and `CompensationFailed` may return only to `Provisioning` through authorized repair, or enter `Deleting`. `Active` may enter `Deactivated` or `Deleting`; `Deactivated` may return to `Active` only through verified reactivation, or enter `Deleting`. `Deleting` may resume in place without changing its write generation and reaches `Erased` only from AD-21's irreversible tombstone; it never returns to an authorizing state. `Erased` has no outgoing transition. Every other transition fails closed. The first commit entering `Deleting` advances the tenant lifecycle write generation and fences ordinary writes; retries preserve that generation, and no failure status restores admission. Before that commit, the lifecycle workflow durably closes the tenant's serialized AD-4/Dapr query-admission gate and waits for every bounded in-flight tenant-content response to end or for its sender to acknowledge cancellation and no further egress. All product readers that may emit tenant content acquire their own request permit before the authoritative `Active` read and pin one active read pair before fan-out. The permit covers all subreads and egress through the last response byte. On erasure revocation, the sender stops all subsequent egress and acknowledges cancellation before the lifecycle workflow can proceed. A cutover lease cannot override that fence. A lost or unavailable gate fails closed, every sender must stop before emitting another byte when it cannot renew its permit, and absence of gate state alone is never evidence that an admitted sender has drained; a failed Deleting commit may reopen the gate only after an authoritative `Active` read with unchanged lifecycle generation and confirmed permit reconciliation. The gate is coordination, never lifecycle authority. The same authoritative tenant-lifecycle stream owns AD-16's release-intent begin/end/cancel records: release begin requires `Active`, and `Deleting` cannot commit until every active intent has a terminal record. A cancel record is admitted only after the egress sender has stopped and acknowledged that no later bytes can leave, or its egress capability has been revoked and that revocation is confirmed; a mere cancel request is not terminal. Dapr transfer leases mirror those records for coordination and do not authorize release.

### AD-7 — Enforce case ownership across case and tenant query scopes [ADOPTED]

- **Binds:** FR32-FR34, MemoryUnit ownership, case-scoped and tenant-wide search, graph seeds/paths, annotations, mutations, deletion, Evidence Packets, and G4.

Default weights are `0.30/0.35/0.35`. `nl` is a fourth ranked axis and not a rerank: when requested and configured for Phase 1.5 event units it is canonicalized, competition-ranked, and contributes at weight `0.20` inside the same weighted sum, default-off, entering the denominator only when it returned results, appearing in Evidence Packet axis health and in explain output under the wire name `nl`, and selectable through the axis-control parameter; where NL is inactive it is reported as an excluded axis rather than omitted. ### AD-14 — Evolve schemas and providers with phase-qualified tenant migrations [ADOPTED · ratified 2026-09-12]

- **Binds:** Embedding provider/model/dimension, index and key families, graph/search replacement, reindexing, provider strategies, and the MVP/Phase 2/Phase 3 migration boundary.
- **Prevents:** Destructive in-place changes, mixed embedding dimensions, partial tenant activation, provider SDK leakage, and an unphased rule silently rebaselining MVP onto a contract the product has not funded.
- **Rule:** Migration obligations are phase-qualified and no phase's evidence satisfies another's. In **Phase 1 / MVP**, FR43 permits only a tenant-scoped, explicitly acknowledged degraded rebuild of rebuildable projections. **That rebuild allocates a new `embeddingConfigurationEpoch` and writes under it, and activates it atomically for the tenant when its verification succeeds** — it is the sole writer permitted to target the new epoch, ordinary ingestion continues under the epoch that is active until the moment of activation, and the tenant's reported ingestion state follows the current active pair and each AD-10 query reads only its leased pair, so the rebuild never flips a tenant's whole corpus into `indexing` and never mixes two embedding spaces under one epoch. Activation is a single AD-2 commit. After the superseded pair’s outstanding read leases drain, the tenant migration workflow’s resumable retire step deletes its documents and checkpoints and verifies removal. The command discloses impact and progress, fails closed on incomplete verification, preserves authoritative EventStore truth, and never claims zero downtime; the query gap between allocation and activation is exactly the degradation FR43 requires it to acknowledge. In **Phase 2**, embedding provider/model/dimension and index-schema changes use versioned create-backfill-verify-switch-retire migrations with disjoint active and staging resources and a full-tenant reindex before atomic activation, with no availability break. In **Phase 3**, backend replacement uses the same staged cutover at the adapter boundary. **Every phase in which a non-active generation or epoch may be written declares what that write targets, for every store AD-3's fence covers — syntactic index, vector index, graph, and tombstones — and AD-3 rejects only a write that matches no declared pair.** Phase 1 declares exactly one: the rebuild epoch above, which needs no separate resource because AD-3 makes the epoch part of a document's identity. What is **Phase 2 and Phase 3 only, by explicit statement rather than by silence**, is the disjoint-staging-*resource* machinery — separate index families, graphs, and key families created by create-backfill-verify-switch-retire; Phase 1 neither has nor needs them, and no rule may read their absence as leaving a Phase 1 write without a target. Across all phases, keep embedding and LLM implementations behind strategy ports; projection evidence carries the active configuration epoch and activities resolve secret references at execution time so rotation can retry safely. The active schema generation and embedding-configuration epoch are tenant-lifecycle domain facts committed through AD-2 before any projection may cite them; the tenant configuration actor caches and serializes access to them and is never their source of truth. **Every consumer of the active `(schemaGeneration, embeddingConfigurationEpoch)` — AD-3's status projection, AD-10's axis selection, and every projection activity — resolves it through that actor and through no other path**; the cached value is invalidated synchronously as part of the AD-2 activation commit and before that commit is reported complete, so no two consumers observe different active epochs for one tenant at one instant, and a consumer that cannot resolve the value fails closed rather than assuming the previous epoch. No MVP implementation or completed historical migration is retroactively claimed to meet the Phase 2/3 contract.

**Query leases during cutover.** Within an authorized AD-6 query permit, the tenant configuration actor serializes lease registration with activation. Admission captures the active pair and durably registers that pair against the permit before any adapter reads. A cutover admits new queries only to the new pair. Queries already holding a lease retain the old pair’s resources until the last response byte or confirmed cancellation with no further egress. The actor reconciles outstanding leases before retirement after a restart. Uncertain lease ownership blocks retirement, and a sender unable to confirm its lease or permit stops emitting bytes. A lease grants access to a resource version only within the tenant’s continuing authorization. AD-6 deletion closes admission and drains or cancels readers; AD-5 revocation and AD-16 erasure take precedence.

- **Phase 1 cutover protocol:** The tenant migration workflow owns create, backfill, authoritative-tail catch-up, verification, activation, and resumable retire. It projects every EventStore mutation and deletion through a recorded tenant-wide high-water mark into the declared rebuild epoch, verifies each memory unit's source version and tombstone parity across all axes, then briefly fences tenant command acceptance while it catches the final tail. The AD-2 activation commit checks that no accepted authoritative mutation lies beyond the verified mark and atomically switches the tenant epoch; if parity or the mark changed, activation fails closed and the old epoch stays active while catch-up retries. After activation and lease drain, the workflow verifies removal of old documents and checkpoints. This bounded cutover interruption is part of Phase 1's acknowledged degradation and earns no Phase 2 zero-downtime credit.

### AD-16 — Complete tenant erasure through crypto-shredding [ADOPTED]

- **Binds:** Tenant provisioning, tenant deletion, the tenant lifecycle write generation, EventStore payloads, all projections, the AD-4 tenant content store, durable workflow history and actor state, caches and derived artifacts, application export bundles, access telemetry and its tenant-representation mapping, operational logs/traces/metrics, backups/restores, replay, per-tenant grants, tombstones, and tenant-ID reuse.

- **Rule:** Tenant deletion completes only after every target under source-platform custody has a verified disposition. Every populated location holding tenant content or derived material requires physical purge or cryptographic unreadability as assigned below. Empty or inapplicable targets require the inventory evidence in the verification rule. The default outcome is **physical purge**. Its closed physical target set is product projections; the AD-4 tenant content store's live data; durable workflow history and activity payloads; actor state; caches; derived artifacts including embeddings and index terms; source-held export staging and retained copies as governed below; AD-17's tenant-keyed principal-token mapping; and the coordination records and projection epochs in the clarification below. The closed cryptographic-unreadability target set is authoritative live EventStore tenant payloads and qualified authoritative backups protected exclusively by the destroyed tenant key; no other content-bearing target uses that outcome. For every physical target, the purge list and verification list are identical: a target purged by obligation but absent from the enumeration is a gap, and adding a content-bearing store adds it here in the same change.

A global backup key, restore refusal alone, or a retention date without tenant-key destruction does not satisfy this exception.
- **Prepare before destruction.** After the fences below have closed, the erasure workflow reads the committed `Deleting` event and verifies its revision and lifecycle write generation. A conflicting preparation keeps deletion pending. It binds the full target inventory, fence acknowledgements, required key versions, target classifications, and opaque verification references. Keep each ciphertext sample available under an opaque locator for the post-shred check in its approved target or tenant-key-protected verification custody. Include any held verification copy in the inventory and its disposal evidence. The preparation record and subsequent receipts contain no keys, payloads, ciphertext or content-derived fingerprints.

Afterwards verify that its ciphertext is unreadable because those keys were destroyed. Distinguish permanent destruction from key-service outage or a denied verifier. For an empty live target or backup class, record independently repeatable evidence of zero tenant records or ciphertext over its complete fenced scope. Recheck empty and inapplicable outcomes against the same fenced inventory at final verification. A class never provisioned or used requires authoritative inventory and configuration evidence of inapplicability, including the absence of retained copies in the backup catalogue. Missing, stale, incomplete or inaccessible evidence keeps deletion pending. Every target receives an explicit outcome.
- **Resumable completion.** Before shredding, persist the verified physical outcomes, completed telemetry handoff and pre-shred verification references as content-free receipts bound to the preparation identity. Destroy issued tenant keys with an idempotent request for those exact versions. After interruption, revalidate the erasure operator and live platform lineage, read the matching preparation and receipts, and reconcile the key provider’s durable result before retrying. If provisioning never issued a key, require authoritative key inventory and verified empty or inapplicable cryptographic targets. The preparation proves the committed generation solely for finishing this deletion after its tenant stream becomes unreadable. It grants no other access. Record the post-shred verification outcomes, then compare-and-append the single content-free completion/non-reuse tombstone to the register. It records the preparation identity, closed inventory, outcomes and completion time. A lost acknowledgement or competing append causes a reread: a matching tombstone completes the retry once, a different identity fails closed, and an unrelated revision advance permits retry with the new expected revision after revalidation. An absent or mismatched preparation after destruction keeps the workflow pending. Only the tombstone establishes `Erased`.

Every EventStore restore, projection-store restore, application export re-import, and authoritative replay consults it before admission and refuses to rehydrate a record whose tenant appears there, regardless of payload readability. An unreadable restored payload is quarantined, never rehydrated.
- **Export bundles:** FR71 export is a custody transfer. The source stages a complete, self-contained portable JSON bundle or recipient-encrypted bundle under the tenant key, with an authenticated origin tenant, `populationId`, register sequence, and payload-integrity proof in the delivered artifact; the platform bundle index retains only content-free opaque bundle identity and signed origin/issuance metadata, never a bare payload digest, content-derived authenticator, or source-key escrow. First-byte release begins external custody of every byte delivered, while the source retains an in-flight obligation until completion or cancellation. Source-held staging, retained copies, and release leases remain purge-and-verification targets. - **Closed purge-set clarification:** The enumerated purge and verification targets include every active, staging, and retired projection epoch and every tenant-keyed coordination record the platform inventories: preflight and durable duplicate-suppression records, AD-23 digest-collision reservations, failed-unit registries, import and export-release leases, the AD-6 query-admission gate, its permits and their AD-14 read leases, tenant and derived-store write fences, migration and rebuild state, and projection checkpoints, whether stored through Dapr state or an approved direct-Redis exception. - **Concurrent-erasure fence:** The AD-6 commit that enters `Deleting` also advances a per-tenant lifecycle write generation and closes ordinary admission. Every tenant-scoped writer to an enumerated purge target captures that generation at admission and, at the operation that makes data visible, either satisfies the target-local atomic comparison required by AD-3 or has already lost tenant-scoped write authority through confirmed credential revocation. Before purge, the erasure workflow obtains a durable fence acknowledgement from every target; an unavailable or unfenced target leaves the tenant in resumable `Deleting`. Cancellation and draining of previously admitted projection and other fenced writes are best-effort cost controls, never completion evidence; the export-release leases named above are different and must complete or cancel before final purge. ### AD-21 — Hold platform-scoped authority outside every tenant key [ADOPTED · ratified 2026-09-12]

- **Binds:** Platform bootstrap ordering, tenant-population identity, erased-tenant register ordering and disaster continuity, the export-bundle index, erasure completion evidence, AD-17 retention purge completion, the shred-surviving projection of AD-6's lifecycle states, tenant provisioning, authoritative replay, every restore path, and export re-import.

- **Rule:** Platform-scoped authority — facts that must outlive every tenant and remain readable after tenant crypto-shredding — lives on the **platform-tenant EventStore partition** `memories-platform`, never under a tenant key, never encrypted under one, never crypto-shredded, and never carrying tenant content or content-derived authenticators. Each population has three distinct append-only streams on this partition. The erased-tenant register holds its genesis and terminal tombstones. The `erasure-work` stream holds AD-16 preparations and verification receipts. The `retention-purge` stream holds AD-17 handoff, verified-empty and purge-completion receipts. The platform partition stores the content-free export-bundle index and AD-6 lifecycle-state projection in their own separate streams. Only genesis and combined completion/non-reuse tombstones advance the dedicated register sequence. Erasure preparation changes no lifecycle state. The descriptive mirror cannot authorize post-shred completion.
- **Register lineage and availability:** Only the AD-15-scoped authenticated platform-bootstrap identity may create the register's genesis marker, and only for a first-ever population before any tenant is provisioned, using the expected immutable `populationId` in a one-time deployment bootstrap grant held outside the new partition. Genesis append and durable consumption of that grant form the bootstrap completion procedure; an uncertain or already consumed grant forbids retrying genesis against an empty partition. Ordinary Server and deployment startup may only verify the configured prior marker and continuity, never create them. A clean-room new population after lineage loss is not an automatic bootstrap route and remains deferred until a separate decision proves a disjoint identifier namespace. The register's EventStore stream revision is its sole monotonic sequence, and only the live lineage maintained through the qualified EventStore continuity protocol is authoritative. Availability is a positive fact: the genesis marker and expected `populationId` must read back from that live lineage, its stream continuity must be proven, and the partition must be reachable and readable. An absent or mismatched marker, unreachable partition, read error, copied or application-restored stream, unexplained sequence gap, or uncertain lineage is **unavailable**, never an empty register. No application backup restore, empty replacement, counter advance, record from another platform stream, or operator assertion establishes continuity.
- **Continuity failure posture:** While the register is unavailable, tenant provisioning, tenant deletion, authoritative replay, EventStore restore, projection-store restore, and export re-import fail closed and remain operator-visible and resumable; no path substitutes a cached or derived copy. If the authoritative lineage is irrecoverably lost, those operations remain unavailable indefinitely for that tenant population. A clean-room new population is not recovery and is forbidden until a separate architecture decision supplies a provably disjoint identifier namespace; it cannot admit the lost population's restores, imports, or authority claims. Recoverable total-lineage loss requires the Deferred independently durable full tombstone mirror; a high-water-only witness is insufficient because it cannot reconstruct a missing tombstone.
- **Authorization and writers:** Reading and writing platform authority is authorized per record type rather than per partition. The partition grants append rights separately for each record type and stream: only the AD-15-scoped platform-bootstrap identity may append the one-time genesis marker under the unconsumed first-ever bootstrap grant; only the operator-authorized AD-16 erasure workflow may append generation-bound preparation and verification receipts in the erasure-work stream and the combined completion/non-reuse tombstone in the register; only AD-6's lifecycle workflow may append a lifecycle-state projection record; only the tenant-authorized export operation may append its own bundle-index record; and only AD-17’s Platform Operations principal may write retention handoff, verified-empty and purge-completion receipts in the separate retention-purge stream. Erasure work records are readable only by the bound erasure workflow and its scoped verifier. The erasure workflow may verify its own handoff acknowledgement by opaque receipt identity. Neither work stream changes the register revision. The export principal acquires no tombstone or lifecycle authority. No principal may append outside its record type, and the partition enforces the confinement. EventStore append-only semantics prevent an application principal from altering or deleting a tombstone. Reads of bundle-index records are limited to the tenant-authorized export/import operation and the enumerated erasure verifier; register, lifecycle, and purge records each have their own enumerated consult paths and scoped operator readers, so partition access alone grants no cross-record read.

Every consult path treats any tombstone for an identifier as permanently erased and refuses provisioning, replay, restore, and import for that identifier; there is no restored-issuability state. Same-population import verifies the delivered bundle's signed origin and payload-integrity proof and never substitutes a requested target tenant for the origin when checking the tombstone. Admission requires the live lineage's population identifier to match, its sequence to be at least the artifact's, and the origin tenant identifier to have no tombstone; an artifact ahead of the live sequence makes the register unavailable rather than advancing it. Register times are descriptive evidence and never admission-control inputs, and access telemetry does not participate in the decision. The platform scope is the set of deployments that can serve one tenant population: every environment, replica, and disaster-recovery site that may admit a restore, import, or provisioning for it uses the same logical register lineage, and inability to reach that lineage means unavailable rather than empty.

### Identifier Grammar V1 (AD-23; normative)

| Class | Issued form | Validation and issuance |
| --- | --- | --- |
| Tenant ID | `[abcdefghjkmnpqrstvwxyz][0123456789abcdefghjkmnpqrstvwxyz]{19}` | Exactly 20 lowercase Crockford characters, starting with a letter; platform-issued from a cryptographic random source and collision-checked against issued IDs and AD-21 tombstones. Issuance requires AD-21's live register lineage; this V1 grammar permits no replacement population after lineage loss. |
| Case ID | `[0-7][0-9A-HJKMNP-TV-Z]{25}` | Canonical 26-character uppercase Crockford ULID, as issued by the current case component; an alternate case or noncanonical leading digit is rejected. |
| `MemoryUnitId` | `[0-7][0-9A-HJKMNP-TV-Z]{25}` | Target for every new unit after Story 34.36. Issue the same canonical ULID on workflow replay. After the coordinated reset, validation rejects alternate case, noncanonical leading digits and pre-reset forms. |

Lowercase `u` is the **only reserved component delimiter** and appears in none of the issued alphabets. Each composite key family registers a fixed, versioned tag that excludes `u`, a fixed component arity and class order, its destination naming scheme, and **one immutable codec and exact byte encoding for each component position**: issued form, reversible Crockford, or SHA-256/Crockford with a collision reservation. Builders cannot select a codec at runtime under the same tag; changing a codec or byte encoding allocates a new family tag and migrates existing keys. The builder emits `tag + u + component1 + u + component2 + ...` for the registered arity; the tag and delimiter make family and component boundaries unambiguous. A non-issued component is length-bounded and uses only its family-registered codec: reversible lowercase Crockford without `u`, or a canonical 52-character lowercase Crockford encoding of a SHA-256 digest with a tenant-keyed canonical-value reservation. The digest input includes the component class and exact validated canonical bytes. SHA-256 output is read as a big-endian unsigned 256-bit integer, zero-left-padded to 260 bits, and encoded as exactly 52 lowercase Crockford base32 digits. Reversible encoding begins with a four-digit lowercase hexadecimal byte length (0–65535), followed by most-significant-bit-first lowercase Crockford base32 of those bytes; only the final digit is zero-right-padded, and decoding rejects a length or pad-bit mismatch. Each registered family specifies the component's validated canonical-byte encoding, with ASCII bytes for CloudEvent `source` and `id` after their ingress rules. The reservation rejects a second canonical value with the same digest before any key use, so no admitted inputs alias; the reservation is an AD-16 purge target. No component truncates an identifier, digest, or composite key to satisfy a destination limit. Random collision checks are against the current live population only and do not prove disjointness from a lost population: after AD-21 lineage loss, V1 tenant issuance is forbidden. A future clean-room population requires a separate ratified architecture decision allocating a provably disjoint namespace and amending this grammar before any issuance.

A key family composed into a 63-character Kubernetes label or PostgreSQL identifier keeps all fixed affixes and separators around one 20-character tenant ID within **42 bytes**; a family with more components checks the complete rendered name against the destination's limit and uses a shorter registered tag or a scoped lookup when needed. The issuing component tests each actual destination — Kubernetes resource names, Redis ACL patterns and keys, FalkorDB graph/database names, Dapr component names, OpenBao secret paths, SQL identifiers, and object-storage key segments — for valid syntax, byte length, case stability, and round-trip non-collision. Each family registers a golden vector for every component codec before first key use, including byte and key output. A scheme's stricter limit governs when it is below 63 bytes. A family tag is allocated before first use and never repurposed for a different arity, class order, codec, or byte encoding.

CloudEvent `source` is an ASCII RFC 3986 URI-reference of **1–2048 bytes**, with valid percent escapes; only its scheme and host are lowercased at ingress, with no other rewriting or Unicode normalization. CloudEvent `id` is **1–256 visible ASCII bytes** (`U+0021`–`U+007E`), kept byte-for-byte. Invalid or overlong values are rejected before AD-4 duplicate admission. Both values enter composed keys only through the encoding or collision-checked digest rule above, not as raw delimiters. Other external components — `IdempotencyToken`, principal identifiers, and handle scopes — declare a bounded byte length in their owning contract before composition and use the same rule. Every import, migration, CloudEvent envelope, and other trust boundary validates issued identifiers on read; pre-grammar identifiers require the AD-23 legacy sweep and collision resolution, never a silent lowercase conversion.

## Direct Redis Exception Registry

Direct Redis search/vector/index operations are ordinary provider data-plane adapter work. The only coordination-state exception to Dapr is:

| Port and operations | Required primitive | Failure posture | Scope and evidence |
| --- | --- | --- | --- |
| REST and CloudEvent admission reservations, including `IPreflightDedupStore` | Atomic `SET NX` with a finite TTL and a fresh acquisition token. Atomic compare-and-delete on release. | Reservation fails open to AD-4 durable suppression. A stale cleanup is a no-op. An unavailable owner check leaves cleanup to TTL. | Each preflight family has a registered AD-23 tag disjoint from durable dedup and from the other intake family. Today REST uses `ingest-reserve:`. EventStore shares `dedup:` with durable dedup and hashes the CloudEvent `id` without its `source`. The ledger records key-family, identity and release gaps. |

Registries, leases, fences, mappings, and migration coordination use Dapr state. A later `AD-n` may add a row only when it also names the **single** coordination store for the protected resource — no resource may be guarded by primitives in two stores, and a new row guarding an already-guarded resource must migrate the existing guard in the same decision — and states its primitive, failure posture, tenant/key scope, and test evidence. Mutual-exclusion primitives (leases, fences, locks) **fail closed**; only admission optimizations with a durable fallback may fail open. Every row declares its reserved Redis key prefix, which no other row may claim, and **a row's protected resource is named at the granularity of the durable artifact it guards** — a store, index, graph, or key family — never at the granularity of an operation, so two rows cannot describe one artifact at different altitudes and evade the already-guarded test. The unregistered coordination key families the alignment ledger records are migrated to Dapr state or given rows with reserved prefixes as part of closing that row.
