## What Went Well

1. The epic solved the original operational blind spot.

   Story 9.3 could report handler state from `SourceToTenantMap`, but that did not prove a projection consumer was actually bound. Story 16.1 added the missing route-to-projection-binding check while preserving existing stale, unhandled, and version-mismatch diagnostics.

2. Runtime authority was treated carefully.

   The new provider contract distinguishes `Unknown`, `NonAuthoritative`, `Authoritative`, and `Unavailable` postures. That kept deployments without registry data from receiving noisy warnings.

3. Tenant isolation remained central.

   The matcher and provider path operate within the selected tenant/application boundary. Cross-tenant binding evidence is not exposed as a broad inventory, and the story explicitly treated tenant scope as a trust boundary.

4. Contract changes stayed additive.

   The new mismatch category was added without required top-level JSON fields, without breaking existing property names, and without changing CLI severity filtering semantics.

5. Review pressure improved the implementation before closure.

   The code review resolved provider-failure logging, null snapshot binding handling, tenant mismatch logging, cancellation behavior, dot-vs-slash normalization, CLI output assertions, deterministic ordering, and default-provider tests.

## Challenges

1. Matching semantics needed more design than the original gap suggested.

   Route prefixes, aggregate tokens, event names, wildcard behavior, event-version suffixes, dot/slash differences, duplicate bindings, and deterministic ordering all had to be centralized. This was necessary but easy to underestimate.

2. EventStore discovery reuse was not automatic.

   `DiscoveryResult.Projections` existed as a useful concept, but the story could not safely treat it as runtime-bound projection authority without a narrow adapter and proof. The final design kept the contract repository-owned.

3. The diagnostic boundary required restraint.

   A matching projection binding proves declared binding coverage only. It does not prove liveness, lag, replay progress, subscription health, or successful consumption. The story had to prevent that overclaim in code, tests, and docs.

4. Review found several small normalization edges.

   `16.1-CR1` through `16.1-CR8` record whitespace-only patterns, trailing separators, backslash event names, Unicode casing, cosmetic empty event keys, structured tenant-leakage assertion depth, multi-slash test depth, and wildcard suffix test depth.

5. Sprint status needed manual cleanup.

   The story was done, but the epic row still read `in-progress`. This is a small tracking issue, not a delivery issue, and it is corrected as part of retro close-out.

## Significant Discoveries

1. A routing declaration is not a runtime binding.

   `SourceToTenantMap` remains useful, but it cannot prove tenant application projection code is bound. The new diagnostic closes that semantic gap only when registry authority is explicit.

2. Unknown posture is a feature, not a weakness.

   Defaulting to quiet `Unknown` or `Unavailable` behavior prevents the detector from generating false confidence or false warnings in deployments that have not opted into authoritative registry evidence.

3. Tenant scope must shape diagnostics, not just data queries.

   Warning payloads, logs, snapshots, and CLI output all need tenant-aware sanitization discipline. The story reinforced that tenant isolation includes observability and operator-facing evidence.

4. Operator diagnostics need liveness boundaries.

   The feature can say "declared binding coverage exists" or "configured route lacks an authoritative binding." It must not imply projection health until a separate health/lag signal exists.

5. Normalization should remain centralized.

   The matcher became a project asset. Future work should extend that matcher rather than duplicating route/event comparison rules across docs, tests, CLI, or detector logic.
