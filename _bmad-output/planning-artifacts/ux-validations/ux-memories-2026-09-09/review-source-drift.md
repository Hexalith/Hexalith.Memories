# Source Drift Review — Hexalith.Memories

## Overall verdict

**Broken as a current downstream contract.** The May UX artifact still carries the right product intent—recoverable trust, explicit scope, inspectable evidence, graceful degradation, and a deferred FrontComposer/Fluent web surface—but it is not synchronized with the change-controlled September PRD. One ambiguity is security-critical: cross-tenant and unauthorized states can be interpreted as confirmable scope expansions instead of fail-closed refusals. Phase ownership, CLI/MCP grammar, confidence semantics, ingestion state, RRF/graph behavior, journeys, and traceability also need reconciliation before architecture, stories, schemas, or UI work source from this document.

## Scope and method

Reviewed the legacy contract at `_bmad-output/planning-artifacts/ux-design-specification.md` and its referenced `_bmad-output/planning-artifacts/ux-design-directions.html`. The current `_bmad-output/planning-artifacts/prd.md`, including working-tree content, and `_bmad-output/planning-artifacts/.memlog.md` were treated as the current decision record. All UX-frontmatter inputs were checked: the PRD, product brief, Kreuzberg research, root project context, FrontComposer project context, and EventStore project context were available; the listed Commons project-context path does not exist. Older brief/research material was used as historical context only where the current PRD or memlog had superseded it.

The review compared source identifiers and precedence, product phases and delivery surfaces, command/tool grammar, evidence semantics, ingestion and memory lifecycle, security boundaries, retrieval/fusion behavior, journeys, and downstream requirement coverage. Severity reflects downstream impact, not repair effort.

## Critical findings

### C1. Cross-tenant and unauthorized states are modeled as warnings or confirmable expansion

- **UX:** The contract permits a missing, ambiguous, or unauthorized scope to “block or warn” (`ux-design-specification.md:L133`, `ux-design-specification.md:L426`), groups cross-tenant and unauthorized evidence with states that merely require deliberate confirmation (`ux-design-specification.md:L565`), and offers “switch tenant” / “request permission” after failed scope validation (`ux-design-specification.md:L656-L660`). The generic scope pattern again treats unauthorized or scope-expanding actions as confirmable (`ux-design-specification.md:L1035-L1037`).
- **Current source:** A tenant is an authorization boundary, while a Case is not an authorization principal (`prd.md:L82-L93`). Provenance and authorization bind to the authenticated principal and tenant claims; membership is metadata (`prd.md:L570-L572`). NFR8 requires every cross-tenant read, search, traverse, and ingest attempt to be rejected or constrained to the authenticated tenant, regardless of request IDs (`prd.md:L1123-L1130`). The CLI has no ambient `tenant switch`; `--tenant` names the requested tenant and claims authorize it (`prd.md:L875-L875`).
- **Impact:** A consumer could implement a warning banner, confirmation dialog, or tenant selector that exposes the existence or metadata of another tenant’s evidence, or that implies confirmation can authorize a cross-tenant action. That violates the zero-leak hard gate.
- **Fix:** Split scope behavior into explicit classes. Same-tenant cross-case search may use an allowed query/filter and deliberate confirmation where required; tenant-claim mismatch, unauthorized source, missing authenticated scope, and cross-tenant access must fail closed before retrieval and reveal no restricted evidence. A different tenant requires a new authorized identity/session, not confirmation. State explicitly that membership does not grant access and add the NFR8 principal-driven negative paths to every affected journey/component.

## High findings

### H1. Source provenance is stale, partially broken, and has no override order

- **UX:** Frontmatter marks the UX complete on 2026-05-16 and lists seven `inputDocuments` (`ux-design-specification.md:L1-L13`). `references/Hexalith.Commons/_bmad-output/project-context.md` at line 11 does not exist. The UX does not cite the current decision memlog or say how newer change control overrides the March brief.
- **Current source:** The PRD is explicitly change-controlled and updated 2026-09-08 (`prd.md:L1-L5`, `prd.md:L29-L41`). The older brief still claims ingest-from-anywhere, EventStore “zero-code,” full CLI/MCP feature parity, physical indexes as the security guarantee, and a 5–10-query thesis test (`product-brief-Hexalith.Memories-2026-03-22.md:L15-L23`); the memlog explicitly overrides the phase split, feature parity, isolation boundary, fusion, ingestion owner, identity, and onboarding clock (`.memlog.md:L26-L38`).
- **Impact:** Automated source extraction can fail on the missing file or silently revive superseded brief decisions because the UX presents all inputs without precedence or reconciliation.
- **Fix:** Replace the legacy list with a resolvable `sources:` manifest that names the current PRD and decision log, records revision/updated dates, and labels the brief and research as historical inputs. Remove or repair the missing Commons path. Add a short reconciliation record for every inherited brief claim that the PRD superseded.

### H2. The UX component roadmap collides with the product phase register

- **UX:** The document correctly says the MVP is CLI-first, MCP/EventStore are Phase 1.5, and web is future (`ux-design-specification.md:L99-L113`), but its own “Phase 1/2/3” component roadmap places Source Citation Stack, Retrieval Axis Breakdown, and Graph Path Summary in Phase 2; Agent Packet Inspector in Phase 2; and Case Activity Trail plus Operator Health Matrix in Phase 3 (`ux-design-specification.md:L927-L948`). It also says the MVP requires CLI-visible Evidence Packet semantics (`ux-design-specification.md:L578-L582`).
- **Current source:** Product phases are canonical: MVP FR1–FR22, FR24–FR52, FR55–FR57, FR63–FR70, FR72–FR74 plus Phase 1 CLI rows; MCP/EventStore-specific FRs are Phase 1.5 (`prd.md:L967-L977`). Origin attribution and explain are MVP, tenant verification is a Phase 1 hard-gate surface, case activity is an MVP FR, MCP inspection is Phase 1.5, and briefing/diffing are Phase 2 (`prd.md:L223-L267`, `prd.md:L1006-L1019`, `prd.md:L1021-L1045`). The Web host is a conformance specimen, not an activated product surface (`prd.md:L709-L720`).
- **Impact:** Downstream planning can defer MVP trust/operations semantics, pull MCP into the wrong increment, or mistake web-component construction for product phase acceptance.
- **Fix:** Rename the UX roadmap to unambiguous **web-composition waves**, then add a separate product-phase/surface matrix. For each component, distinguish contract semantics required in Phase 1 CLI/JSON, Phase 1.5 MCP, Phase 2 application UI, and future visual implementation. Mirror the PRD phase and delivery-status registers rather than assigning new phase numbers.

### H3. CLI examples use obsolete grammar and an eliminated tenant-switch model

- **UX:** The primary mechanics example is `memories search "…" --case … --explain`, without the `search query` subcommand, `--tenant`, or `--query` option (`ux-design-specification.md:L422-L424`). The static Command First mock uses a second pseudo-grammar, `search claims-q1: … --explain` (`ux-design-directions.html:L647-L655`). Recovery offers “switch tenant” (`ux-design-specification.md:L656-L660`).
- **Current source:** Every journey must use `memories search query --tenant <t> --query "<q>" [--case <c>] [--axis <a>] [--explain]` (`prd.md:L297-L300`). Global options and requested-tenant behavior are fixed, and there is no `tenant switch` (`prd.md:L871-L881`). The Phase 1 CLI table is the command/phase/delivery source of truth (`prd.md:L877-L900`); the memlog records that CLI reality removed tenant switch (`.memlog.md:L53-L55`).
- **Impact:** Tests, documentation, prototypes, empty-state copy, and command launchers derived from the UX will generate commands that do not parse or that misrepresent authorization.
- **Fix:** Replace every command sample and command-like recovery action with the exact CLI-table grammar, including required tenant/query options and correct subcommands. Label currently stubbed verbs as unavailable rather than presenting them as executable. Remove tenant-switch language and describe re-authentication or an explicitly authorized requested tenant.

### H4. MCP request/response grammar is invented in prose instead of bound to the versioned contract

- **UX:** The mechanics call describes `search_memory` with `tenant`, `case`, `query`, `budget`, and “expansion preferences” (`ux-design-specification.md:L422-L424`), while the journey changes that to “token budget” (`ux-design-specification.md:L684-L703`). The Agent Packet Inspector requires field-name alignment but supplies no mapping or schema version (`ux-design-specification.md:L895-L904`); its mock invents `evidenceStrength`, a numeric `sources` count, and `nextAction` (`ux-design-directions.html:L709-L740`).
- **Current source:** The named Phase 1.5 tools are `search_memory`, `ingest_content`, `traverse_relations`, and `get_case_info`, with `token_budget` in the examples (`prd.md:L341-L353`, `prd.md:L411-L432`). The capability matrix limits MCP to agent work while CLI remains the operational superset (`prd.md:L845-L869`). The concrete Evidence Packet shape is `Contracts.V1`/architecture-owned (`prd.md:L549-L562`), and FR54/FR58 require typed Phase 1.5 tool schemas (`prd.md:L1059-L1066`). The PRD prose itself still alternates `axis` and `axes` (`prd.md:L416-L421`), so prose is not safe as schema authority.
- **Impact:** An agent client or inspector can ship incompatible input names, accept server-controlled scope incorrectly, or render fields that do not exist in the versioned response.
- **Fix:** Add a per-tool schema mapping sourced directly from the active MCP/`Contracts.V1` definitions: tool name, phase, request fields, server-controlled fields, response type, error type, token-budget behavior, and expansion-handle shape. Resolve `axis` versus `axes` in the owning contract and reference that identifier/version; do not create wire names in UX prose or mocks.

### H5. Default explain behavior is contradictory and the cited UX requirement does not exist

- **UX:** Every Evidence Packet is required to contain retrieval axes and an explain summary (`ux-design-specification.md:L83-L95`); explanation is automatic after a search (`ux-design-specification.md:L115-L125`), and retrieval axes/confidence limits are included by default (`ux-design-specification.md:L225-L233`). Elsewhere, Retrieval Axis Breakdown is limited to “search explain mode” (`ux-design-specification.md:L851-L860`). No `UX-DR7` identifier exists anywhere in the UX file.
- **Current source:** Explain mode is an explicit `--explain` option that exposes score semantics and weights (`prd.md:L549-L568`, `prd.md:L1006-L1019`); the CLI row also marks it optional (`prd.md:L879-L883`). Open Question 3 records the unresolved choice between opt-in explain and the UX’s always-present compact trust fields, but cites the nonexistent `UX-DR7` (`prd.md:L1197-L1205`).
- **Impact:** Implementers cannot tell whether every default result must pay the explain payload/latency cost, what compact trust fields remain visible without `--explain`, or which acceptance criterion resolves the conflict.
- **Fix:** Give the UX rule a stable identifier or replace the PRD citation with an exact section anchor, then resolve the decision through change control. Until resolved, distinguish always-present trust fields (scope, origin, relevance label, freshness/degradation, recovery) from opt-in per-axis ranks, weights, matched terms, and graph detail; mark the latter explicitly open rather than simultaneously mandatory and optional.

### H6. “Confidence” conflates relevance, metadata, edge strength, and evidence-health labels

- **UX:** The UX says confidence represents evidence strength/retrieval quality (`ux-design-specification.md:L83-L89`), then defines `supported`, `partial`, `disputed`, and `insufficient` as confidence states beside freshness, evidence health, and scope (`ux-design-specification.md:L539-L563`, `ux-design-specification.md:L818-L837`). Source citations also carry an unnamed “confidence” (`ux-design-specification.md:L862-L871`). The mock uses “Strong/Medium evidence” plus `Evidence 0.91/0.68` and raw-looking axis bars (`ux-design-directions.html:L513-L542`); it labels a `caused_by` edge “Confidence 0.87” and “inferred from causation ID” (`ux-design-directions.html:L680-L703`).
- **Current source:** The glossary distinguishes **relevance confidence**, **metadata confidence**, and **edge confidence** (`prd.md:L78-L94`). Hybrid scores are weighted RRF relevance contributions, not factual confidence; metadata confidence is per field/origin; edge confidence follows an edge taxonomy (`prd.md:L547-L597`). A `caused_by` edge from explicit CausationId defaults to 1.0, while AI-inferred similarity is a `references` edge and is never auto-promoted (`prd.md:L583-L597`). FR63–FR65 preserve these separate nouns (`prd.md:L1075-L1081`).
- **Impact:** The UX can mislabel ranking scores as evidence truth, assign invalid edge semantics, or serialize presentation-only sufficiency states as contract confidence.
- **Fix:** Define separate presentation bindings for `relevanceConfidence`, metadata field origin/confidence, edge type/confidence, evidence health, freshness, and scope. Rename `supported/partial/disputed/insufficient` to an explicitly presentation-owned **evidence sufficiency** taxonomy with source-backed thresholds or rules. Every numeric relevance display must say “relevance, not verified fact”; update the mock’s edge to a contract-valid edge type/default.

### H7. Ingestion labels omit the durable projection stage and treat retry as a state

- **UX:** Alex’s onboarding flow shows `queued → extracting → embedding → indexed`, omitting projecting and terminal failed (`ux-design-specification.md:L616-L633`). The roadmap describes `pending, failed, retried, indexed` as tracker states (`ux-design-specification.md:L943-L947`). The global loading grammar switches back to `queued, extracting, embedding, indexing` and mixes ingestion stages with graph traversal, tenant verification, and consistency repair (`ux-design-specification.md:L996-L1005`).
- **Current source:** The one product vocabulary is `pending → extracting → embedding → projecting → indexed`, with `failed`; `Queued` and `Indexing` are wire-enum spellings mapped to `pending` and `projecting`, while retry/dead-letter/repair are detail fields (`prd.md:L82-L94`, `prd.md:L814-L839`). `indexed` is emitted only after search, vector, and graph projections acknowledge the same EventStore source version; EventStore acknowledgement is the durable commit and projections are rebuildable (`prd.md:L816-L838`, `prd.md:L990-L1004`). The memlog records the Workflow/EventStore override and the vocabulary reconciliation (`.memlog.md:L30-L32`, `.memlog.md:L53-L56`).
- **Impact:** UI, CLI copy, tests, and agent recovery can disagree with the persisted contract, incorrectly show a unit as indexed before all projections acknowledge it, or model retry/repair as impossible enum values. It also blurs an incompletely projected unit with a query degraded because a backend later becomes unavailable.
- **Fix:** Adopt the PRD labels as UX terms and document the `Contracts.V1` display mapping. Show `projecting`, terminal `failed`, attempt count/last error/dead-letter/repair as details, and the EventStore durable-commit boundary. Model search-backend degradation separately from ingestion completion. Add the NFR36 delayed-embedding state and NFR16 rebuild/progress recovery path.

### H8. Retrieval behavior does not commit weighted RRF or the graph auto-seeding rule

- **UX:** Retrieval “normalizes and fuses” syntactic, semantic, and graph scores without naming the algorithm (`ux-design-specification.md:L422-L430`). Retrieval Axis Breakdown specifies a “normalized score” and generic contribution (`ux-design-specification.md:L851-L860`), and the mock displays independent 0.82/0.91/0.76 bars without saying whether they are single-axis magnitudes or hybrid rank contributions (`ux-design-directions.html:L537-L542`). The UX has no occurrence of `RRF`, reciprocal rank, or graph auto-seeding.
- **Current source:** Weighted reciprocal-rank fusion is the decision; raw BM25, cosine, and graph-proximity magnitudes are not fused (`prd.md:L43-L49`, `prd.md:L547-L560`, `prd.md:L1159-L1165`). With no explicit start node, hybrid auto-seeds graph traversal from the union of the top five syntactic and top five semantic candidates at depth ≤2; `--from` replaces auto-seeding (`prd.md:L158-L166`, `prd.md:L1006-L1019`). The magnitude-blend approach was explicitly rejected (`prd.md:L213-L221`, `.memlog.md:L15-L16`, `.memlog.md:L30-L31`).
- **Impact:** Designers and implementers can display incomparable raw scores as additive evidence, omit graph contribution from ordinary hybrid queries, or write acceptance tests for the superseded magnitude-fusion model. This directly affects the thesis gate.
- **Fix:** State deterministic weighted RRF and distinguish single-axis scores from hybrid per-axis rank contributions in every packet/table/mock. Show which axes participated, their ranks/contributions/weights, and any excluded axis. Add auto-seeded versus explicit-start graph provenance and the depth rule to the search flow; reference architecture for numeric defaults rather than owning them in UX.

### H9. The five UX flows do not cover or faithfully identify the ten source journeys

- **UX:** The flow section contains only Alex zero-to-evidence, Alex weak/empty recovery, LLM Agent MCP consumption, Kenji verification/recovery, and Marcus briefing (`ux-design-specification.md:L614-L770`). Alex zero-to-evidence combines file/sample ingest with a generic package/AppHost path (`ux-design-specification.md:L616-L648`); the debug flow has no handler mismatch or replay (`ux-design-specification.md:L650-L682`); the MCP flow covers agent consumption but not Alex’s configuration journey (`ux-design-specification.md:L684-L712`); and Kenji’s flow omits the authenticated-tenant mismatch/access-telemetry beat (`ux-design-specification.md:L714-L743`). None carries a source Journey ID or product phase.
- **Current source:** The PRD defines J1–J10 and an explicit coverage map (`prd.md:L297-L519`). J1 is the Phase 1.5 EventStore package/subscription/causal path (`prd.md:L301-L317`), while J9 is the Phase 1 file/URL empty-state path (`prd.md:L460-L474`). J2 requires handler mismatch and replay (`prd.md:L321-L337`), J3 is Alex wiring MCP (`prd.md:L341-L353`), and J5 includes tenant-claim mismatch and access telemetry (`prd.md:L377-L389`). J6 (backend migration), J8 (application end beneficiary), and J10 (contributor) have no UX flow at all (`prd.md:L393-L458`, `prd.md:L478-L492`).
- **Impact:** Story generation can merge the two onboarding clocks, lose launch-gate behaviors, skip identity failure evidence, omit future-surface constraints, and treat source journeys as covered when only a thematic fragment exists.
- **Fix:** Mirror `J1`–`J10` names verbatim and include the source phase on every flow. Split current Alex onboarding into J9 Phase 1 and J1 Phase 1.5; complete J2, J3, and J5; add J6 and J8 as phase-qualified future flows; explicitly classify J10 as infrastructure/non-product if it remains outside UX. Each flow needs the named protagonist, numbered sequence, climax beat, and applicable failure/recovery path.

### H10. There is no information-architecture closure or FR/NFR traceability contract

- **UX:** The document names four task views (`ux-design-specification.md:L569-L574`), seven custom components (`ux-design-specification.md:L816-L916`), and navigation variants (`ux-design-specification.md:L985-L994`), but has no Information Architecture section, no surface inventory with phase/owner, and no mapping from source journeys or requirements to surfaces and states. A mechanical scan finds zero `FRn`, `NFRn`, `Journey n`, or `UX-DRn` identifiers in the UX file.
- **Current source:** The PRD says FR1–FR74 are phase-qualified and delivery-qualified (`prd.md:L967-L988`), provides the CLI/MCP/DAPR capability matrix (`prd.md:L845-L869`), and makes the CLI surface table the command/phase/delivery source of truth (`prd.md:L871-L900`). Its journey coverage map explicitly assigns phase and purpose (`prd.md:L496-L519`).
- **Impact:** A downstream consumer cannot prove that every stated need lands on a surface, every surface has a journey, every active requirement has states, or every deferred capability remains deferred. Naming similarity can masquerade as coverage.
- **Fix:** Add an IA/closure matrix with one row per surface: canonical name, product phase, delivery state, audience, entry point, source journey IDs, FR/NFR IDs, component patterns, required states, and exit/recovery. Add a requirement trace table for all active UX-bearing FR/NFRs and explicitly classify infrastructure-only or deferred items. Define stable UX decision IDs for any rule the PRD cites.

## Medium findings

### M1. A surface-neutral Evidence Packet overpromises synthesized answers and universal actions

- **UX:** The core packet may contain ranked results, a synthesized answer, or both (`ux-design-specification.md:L83-L95`), and its recovery menu includes graph traversal, scope broadening, ingestion status/retry, isolation verification, repair, export, and detailed narrative (`ux-design-specification.md:L422-L436`, `ux-design-specification.md:L565-L567`). Recovery is said to be contract-backed and consistent across CLI, MCP, and web (`ux-design-specification.md:L677-L682`).
- **Current source:** The Phase 1 product is CLI search/results; MCP is a Phase 1.5 agent subset; application-facing REST UI, briefings, discussion, and diffing are non-goals until Phase 2 (`prd.md:L43-L57`, `prd.md:L99-L108`, `prd.md:L248-L267`). Tenant management, diagnostics, status, consistency, export, and handlers are intentionally not MCP capabilities (`prd.md:L845-L869`).
- **Impact:** A shared envelope can be mistaken for identical functionality on every surface, causing narrative generation or operator actions to be pulled into the wrong phase/tool.
- **Fix:** Define Evidence Packet projection profiles by surface and phase: Phase 1 CLI human/table/JSON search result; Phase 1.5 MCP agent response; Phase 2 briefing/application composition; operator diagnostic result. Keep semantic field meanings shared, but include only actions supported on that surface and label synthesized narrative as a phase-qualified composition, not a universal packet guarantee.

### M2. Freshness labels have no threshold, transition, or contract-version binding

- **UX:** `current`, `aging`, `stale`, and `unknown` are defined as stable freshness labels (`ux-design-specification.md:L558-L563`, `ux-design-specification.md:L1043-L1050`) and are required throughout components, but the UX never states who owns thresholds, how a unit transitions, or how unknown/degraded sources recover.
- **Current source:** NFR33 requires authoritative thresholds, transitions, disclosure, recovery actions, and versioning in the Evidence Packet contract, activated per surface (`prd.md:L1182-L1189`). The PRD currently records the mechanism as implemented but without a verification run (`prd.md:L1098-L1107`). File/URL ingestion latency has a separate NFR36 state/timing contract (`prd.md:L1191-L1195`).
- **Impact:** Surfaces can assign different freshness labels to the same unit or confuse evidence age with ingestion latency or relevance confidence.
- **Fix:** Reference the owning versioned freshness contract and provide a presentation mapping only. Until thresholds are committed, mark the labels as unresolved rather than “stable.” Specify transition announcements and recovery per surface, and keep NFR33 evidence age separate from NFR36 ingestion progress and relevance confidence.

### M3. Activity and operator language implies permission history and audit guarantees the product disclaims

- **UX:** Inspiration calls for “audit-friendly trails” (`ux-design-specification.md:L252-L258`); the tenant verification flow promises timestamp and “audit context,” including recovery audit context (`ux-design-specification.md:L714-L743`); Case Activity Trail includes “permission changed” as a state (`ux-design-specification.md:L906-L915`).
- **Current source:** “Access telemetry” is explicitly not a tamper-evident audit trail, and case membership is attribution metadata rather than authorization (`prd.md:L78-L93`, `prd.md:L535-L545`). FR67 preserves the access-telemetry term (`prd.md:L1075-L1081`), while NFR34 requires an owner, TTL, purge progress, and accepted-debt handling without upgrading it to an audit trail (`prd.md:L1182-L1189`).
- **Impact:** Operator/UI copy can create a compliance promise the platform does not make and can represent membership changes as access-control changes.
- **Fix:** Use **access telemetry context** and state the integrity/retention limitation at the inspection boundary. Rename `permission changed` to the actual event (for example, membership metadata changed or tenant-claim authorization denied), and defer audit-trail/ACL concepts to the phase that owns them.
