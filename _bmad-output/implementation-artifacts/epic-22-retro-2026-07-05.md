## What Went Well

1. **The epic stayed narrow per audit finding.**
   Each story preserved the preceding retrieval guardrails instead of reopening adjacent concerns. This kept pagination, traversal, fusion, case scope, recall, and NL completion understandable as separate changes.

2. **RRF removed a fragile scoring assumption.**
   Story 22.4 stopped treating BM25, vector similarity, and graph proximity as directly comparable magnitudes. Rank-based fusion is deterministic, bounded, testable, and no longer depends on corpus statistics for hybrid ordering.

3. **Case and tenant boundaries remained visible.**
   Stories 22.3 and 22.5 added key validation and path-wide case predicates. Story 22.4 preserved case attribution through fusion. These changes carried forward the security/data-integrity work from Epics 20 and 21.

4. **Review caught real defects and evidence gaps.**
   Reviews fixed missing scoped-key validation, empty graph response query drift, missing timeout propagation, latency logging semantics, stale evidence tables, File List omissions, stale comments, and insufficient NL adapter coverage.

5. **Story 22.7 completed stranded capability without changing defaults recklessly.**
   `axis=nl` is usable through REST, CLI, and MCP, and hybrid can explicitly include NL. Default hybrid behavior remains stable unless callers opt into NL.

## Challenges

1. **File List and evidence hygiene recurred across the epic.**
   Multiple reviews corrected omitted files, stale evidence statuses, or changed automation artifacts. The pattern is process debt, not an isolated miss.

2. **Validation environment behavior was inconsistent.**
   Some integration proof executed in one implementation context, while review contexts hit Docker socket or NuGet-signature blockers. The story notes handled this transparently, but the project still needs a crisp validation-lane convention for retrieval and ingestion work.

3. **Raw Redis response parsing was a hidden edge.**
   Story 22.6 uncovered RESP2/RESP3 differences in scoped KNN parsing. Story 22.7 evidence indicates the syntactic raw path now handles RESP3 too, but this class of issue should stay on future raw-command checklists.

4. **Planning docs lagged implementation semantics.**
   PRD, architecture, CLI, MCP, EventStore, and README text still described older three-axis or weighted-average assumptions after implementation moved to RRF and exposed NL.

5. **Full solution validation still has an unrelated AppHost/EventStore dependency conflict.**
   Story records repeatedly show the non-retrieval AppHost duplicate assembly issue blocking full solution proof. That cannot be treated as a retrieval regression, but it does constrain confidence for upcoming ingestion work.
