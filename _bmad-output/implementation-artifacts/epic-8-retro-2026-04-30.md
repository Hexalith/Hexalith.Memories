## What Went Well

- Story 8.1 made health semantics explicit. Backend failures degrade readiness without ejecting every pod from service rotation, while DAPR sidecar failure remains a true liveness concern.
- The health response shape is operator-readable and capability-aware. `BackendCapabilityCatalog` maps backend checks to affected capabilities, preventing vague "backend down" diagnostics.
- Story 8.2 created a real consistency surface: verification workflow, repair workflow, per-unit inspection, REST endpoints, client methods, CLI commands, source-generated contracts, and operator docs.
- The consistency repair design used re-verification before mutation. That kept repair actions tied to current backend state rather than stale verification snapshots.
- Story 8.3 delivered portable export through streaming JSON instead of buffering full tenant state in memory. The schema is versioned and intentionally shaped for future import without shipping restore prematurely.
- Story 8.4 converted Epic 7 telemetry claims into deployed-topology evidence. The Tier-3 tests verify CLI-to-server trace continuity and access audit events through the Aspire shape.
- Story 8.5 closed the known Story 8.4 follow-up instead of letting a soft-skip become permanent. Redis and FalkorDB spans now participate in the trace proof.
- Documentation and tests reinforced each other. Several docs gained cross-links, and the telemetry instrumentation inventory is now backed by a parity test.
- Review close-outs were substantive. Each story records review fixes, accepted deferrals, and the validation evidence that allowed it to close.

## Challenges

- Epic 8 repeatedly touched shared infrastructure surfaces: `Program.cs`, `ServiceDefaults`, `MemoriesClient`, CLI command wiring, source-generated JSON contexts, and integration fixtures. That made small changes high blast-radius.
- Health semantics required careful trade-offs. `Degraded` readiness preserves hybrid-search availability, but capability-specialized workloads still need clear operator guidance when their backend is unavailable.
- Consistency repair exposed deeper ingestion-path debt. Semantic re-indexing from syntactic state still has a follow-up path, and later Epic 9 work added more consistency note behavior that needs runbook alignment.
- Export shipped with honest limitations. The streaming implementation is strong, but some service-level and endpoint-level guard tests from the original test inventory remain deferred.
- Telemetry testing is topology-sensitive. Story 8.4 needed a hybrid capture model, activity breadcrumbs, audit readers, and careful count-first assertions to avoid vacuous green tests.
- Redis OTEL instrumentation required accepting a prerelease package and supply-chain hardening. The team contained that with central pinning, package-source mapping, signature validation, and a dated deferred-work review trigger.
- FalkorDB speaks Redis protocol, which created semantic ambiguity in telemetry tags. Story 8.5 had to add `FalkorDbSemanticAttributeProcessor` rather than accepting misleading `db.system=redis` tags for graph work.
- Several useful follow-ups remain outside Epic 8: export telemetry, export rate limiting, export service guard tests, consistency note/runbook refinement, and topology-specific trace expansion for later MCP work.

## Key Insights

1. Operational features need separate signals. Health, consistency, export, telemetry, and audit are related, but collapsing them into one "ops" surface would hide failure modes.
2. Deferral is acceptable only when it has a named owner, artifact, and re-open trigger. Story 8.4 to 8.5 is the positive example.
3. A diagnostic surface is a contract. Health JSON, consistency results, export schema, CLI outputs, audit events, and trace attributes now need compatibility discipline.
4. Deployed-topology evidence catches what unit tests cannot. The CLI-to-server trace and Redis span assertions are examples of claims that needed the real shape.
5. Operator docs are part of safety. Readiness behavior, repair safety, export limitations, and telemetry verification all need clear runbooks because misuse can create false confidence.

Epic 9 depended on Epic 8 in concrete ways:

- Event ingestion and dual embedding rely on operational health signals to distinguish service failure from capability degradation.

## Commitments

- Treat health, consistency, export, telemetry, and audit surfaces as compatibility contracts.
- Keep operational docs tied to executable behavior.
- Avoid permanent soft-skips; every deferral needs a re-open trigger.
- Keep destructive repair actions explicit and re-verified.
- Use source-generated JSON coverage for contract records.
- Require deployed-topology evidence for trace and audit claims that cross process boundaries.
