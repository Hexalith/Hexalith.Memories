## What Went Well

- The team extended the existing `IngestionWorkflow` rather than creating new workflow variants. URL fetch, directory batching, rate limiting, failed-unit persistence, and restart durability all built on the same core pipeline.
- Security boundaries were treated as first-class requirements. Story 6.1 included SSRF protection, path canonicalization, empty production directory allow-list defaults, and redacted logging.
- Per-tenant concerns were kept explicit. Story 6.2 separated tenant rate ceilings and tenant extraction gates, avoiding shared hot paths where one tenant could dominate another.
- Recovery became operator-visible. Story 6.3 added failed-unit persistence, failed-unit listing, memory-unit failure details, and re-ingestion endpoints.
- Durability claims were backed by validation. Story 6.4 configured Redis persistence explicitly and added restart-focused integration coverage.
- Documentation tracked the operational model: `docs/operations/rate-limiting.md`, `docs/operations/failure-recovery.md`, and `docs/operations/pipeline-persistence.md`.

## Challenges

- Several early Epic 6 integration tests were intentionally skipped because the AppHost and integration fixture were not ready enough to support deterministic end-to-end validation.
- Story 6.1 accepted a Dapr retry limitation where some non-retryable URL fetch errors still consumed the standard retry path. That was documented, but it is still operationally inefficient.
- Story 6.2 introduced application-level jitter because the Dapr Workflow retry policy surface did not expose the needed jitter control. The implementation avoided a custom retry loop, but the compromise should stay visible.
- Story 6.3 added a large amount of recovery surface in one story: retry policies, failed-unit registry, counter actor, memory-unit endpoint, and re-ingestion endpoints. The scope was justified, but it created review density.
- Story 6.4 exposed that durable Redis changes alter test isolation assumptions. Unique tenant and case IDs became important, and some cleanup gaps remain deferred.
- AppHost and integration project baseline issues appeared in multiple story notes. The team handled them as known constraints, but they created friction for confidence gathering until Story 6.4.

## Key Insights

1. The ingestion pipeline is strongest when every new capability is expressed as a workflow activity, actor state, or backend idempotency rule, not as a separate orchestration model.
2. "Done" for resilience work means behavioral proof. Story 6.4 changed the quality bar by validating restart behavior instead of relying on architectural intent.
3. Operator visibility is part of reliability. Failed-unit persistence, clear failure details, and re-ingestion endpoints made failures actionable.
4. Documentation should land with operational capabilities. Epic 6 docs now explain the actual runtime contract instead of leaving operators to infer it from code.
5. Integration-test infrastructure is a dependency, not a side concern. Earlier skipped tests were acceptable only because later work closed the most important evidence gaps.

## Significant Discovery Check

No discovery from Epic 6 requires changing the Epic 7 direction. Epic 7 was the correct follow-on because the ingestion capabilities needed a polished developer surface.

For the current project state, the more relevant discovery is post-MVP: reliability claims should stay tied to executable validation. That aligns with the already-scaffolded Epic 12 focus on release and operations foundation.

## Commitments

- Treat Dapr Workflow and actors as the canonical orchestration and state model for ingestion resilience.
- Keep failed ingestion recoverable and visible rather than relying on logs alone.
- Avoid introducing custom persistence mechanisms unless the existing architecture is proven insufficient.
- Maintain operations documentation alongside runtime behavior.
- Prefer concrete validation artifacts for reliability claims.
