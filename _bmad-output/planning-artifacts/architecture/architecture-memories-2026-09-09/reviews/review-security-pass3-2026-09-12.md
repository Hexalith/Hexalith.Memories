Both prior passes found the same defect class: *an obligation stated without the clause that makes it discharge*. ### SEC3-01 — critical — The lifecycle exemption binds its holder to no tenant, is self-widening under AD-6, and is the mint for the grants every other authorization path consumes

**Spine:** `:92` (the exemption; the three internal-call checks; "The per-tenant grant that pairs with it is a tenant resource whose sole writer is AD-6's lifecycle workflow"; "grants are enumerated with any wildcard requiring its own architecture decision"), `:96` (AD-6 *Binds*: "Tenant provisioning, verification, repair, deletion, indexes, graphs, backend identities and credentials, **per-tenant grants**, the access-telemetry partition, and cleanup"), `:98` (AD-6 *Rule*: "Perform tenant resource changes **only** in explicit, idempotent, observable, bounded lifecycle workflows"), `:152` (AD-15: "rotation of a tenant data-plane credential is an AD-6 lifecycle operation"), `:146` (AD-14 staging resources). **Requirement:** `prd.md:1141` (NFR8, MVP hard gate), `prd.md:1107` (FR74: repair "cannot cross tenants").

**What a compliant implementation permits.** The background-work clause bounds ordinary durable work three ways: an explicit tenant authority captured at initiation, revalidation against active tenant state at every resume and activity boundary, and grant containment. The exemption removes the second and the third and replaces them with "revalidate against the tenant lifecycle state machine." A state machine constrains **which state** a tenant is in; it does not constrain **which tenant** the workflow may act on. The first bound — "carries an explicit tenant authority captured at initiation" — is a property of the *tenant grant* the exemption just discarded, and the operator principal that replaces it "grants principal identity and **never tenant scope**." The result is a class of durable, resumable, long-lived work with **no tenant-scoping mechanism of any kind**. Pass 2's four bounding clauses (one-tenant pinning, unchangeable on resume, operator-principal revalidation at each boundary, and revocation ordering) were all dropped in adoption.

**Scenario 1 — grant minting.** AD-6's lifecycle workflow is the *sole writer* of per-tenant grants (`:92`, `:96`). It is now exempt from tenant-active revalidation and from grant containment, and it is authorized by a principal type the spine does not define (SEC2-15). A lifecycle workflow resumed or re-triggered with a different tenant identifier in its captured input satisfies every remaining check: the state machine reports that tenant is in some lifecycle state, and no grant is required. It writes a grant pairing an existing `system:*` app ID with that tenant. From that point ordinary internal calls pass all three checks legitimately. The exemption is therefore not merely a bypass of tenant authorization — it is the **mint** for the tokens the rest of AD-5 consumes, and it is the only path in the architecture that can create them.

**Scenario 2 — NFR8 cannot see it.** `prd.md:1141` specifies the verification method as an "automated suite driven by *principals*, not ids: authenticate as tenant A, then search, ingest, and traverse with `--tenant B`." The exempt principal has **no tenant claim by construction** — that is what makes it exempt. There is no "tenant A" to authenticate as. The MVP hard gate for zero cross-tenant leakage therefore has no test that reaches the one principal class the architecture just placed outside tenant scoping, and a green G2 run says nothing about it.

**Scenario 3 — the exemption widens as AD-6 is honoured.** AD-6 requires that tenant resource changes happen **only** in lifecycle workflows. AD-5 exempts lifecycle workflows. The two together mean the more faithfully AD-6 is implemented, the more work sits inside the exemption. Enumerating what can claim it today from AD-6's own *Binds* line and its cross-references:

1. Tenant provisioning — intended.
2. Tenant deletion — intended.
3. AD-16 erasure — intended.
4. Tenant **verification** — on active, healthy tenants.
5. **Lifecycle repair** — named in the exemption's own rationale, and colliding by name with the data repair that `:92`'s background list requires to revalidate and that FR74 requires to be tenant-bounded. Two operations, one word, opposite rules.
6. Per-tenant credential **rotation** — AD-15 `:152` states it is an AD-6 lifecycle operation, on an active tenant.
7. Per-tenant **grant** creation and revocation — scenario 1.
8. **Indexes and graphs** — AD-6 *Binds* names them, and AD-14's create-backfill-verify-switch-retire migration creates per-tenant staging index families and graph resources. Either migration is an AD-6 lifecycle workflow, and therefore exempt — contradicting `:92`'s background list, which names "migration" as work that must revalidate — or it is not, and it violates AD-6's "only in lifecycle workflows."
9. The **access-telemetry partition** — `:98`, `:164`, row `:340`.
10. "**cleanup**" — AD-6 *Binds*, undefined.

**Scenario 4 — no expiry.** The exemption states no revalidation of the *operator* principal. A lifecycle workflow initiated by an operator whose authority is subsequently revoked continues indefinitely on captured authority, because the only revalidation specified is against the lifecycle state machine. AD-15 `:152` bounds exactly this for credentials ("no connection or client established under a superseded credential outlives that bound"); the exemption creates the same exposure for authorization and bounds nothing.

**Closing text (AD-5 *Rule*, replacing the exemption sentence).** *"AD-6 lifecycle workflows and AD-16 erasure are the one exception, and it is bounded here. Such a workflow is authorized by an operator principal, is scoped at initiation to exactly one tenant identifier that it may not change on resume or on retry, revalidates that operator principal — not the tenant — at every resume and activity boundary and fails closed when the principal's authority has been withdrawn, and revalidates its subject against the tenant lifecycle state machine rather than against tenant-active. The exemption reaches only the enumerated operations of AD-6 and AD-16 for that one tenant; every other call the workflow makes satisfies all three internal-call checks. Writing a per-tenant grant is admissible only inside a provisioning workflow for the tenant that workflow is scoped to. AD-16 erasure revokes the per-tenant grant only after the register carries completion evidence. The exemption is itself an enumerated, versioned artifact: adding an operation to it is an architecture decision."*

### SEC3-02 — high — The exemption does not survive the internal-call boundary, so SEC2-01's provisioning deadlock is intact and the two available escapes are both forbidden

**Spine:** `:92` ("Trusted internal calls additionally require deny-by-default Dapr mTLS/access-control policy and app-token channel protection, then satisfy three independent checks — an app ID present in the allowlist, an explicit grant for the requested tenant, and that tenant being currently active and verified — any one of which failing closed"; the exemption, whose grammatical subject is *workflows*), `:91` (*Prevents*: "**Request fields**, envelope fields, case membership, key prefixes, graph labels, channel tokens, or a caller-selected app identity from serving as authorization"), `:98`, `:164`, row `:340`.

**A compliant implementation permits this.** Provisioning is not self-contained. `:98` and `:164` require the lifecycle workflow to create the access-telemetry partition, which lives in a separate service (`Hexalith.Memories.AccessTelemetry*`, `:244`) reached by an internal call. The exemption is written about the calling workflow's own revalidation; the three checks are written about the receiving call. Nothing joins them. The receiver sees an authenticated app ID and a tenant, and must fail closed on check 2 (no grant yet exists — it is what provisioning creates) and check 3 (the tenant is not yet active and verified).

**Scenario.** An implementer has exactly three options. **(a)** The caller sets a flag on the request — `X-Lifecycle-Operation: provision` — and the receiver relaxes the checks. **Closing text (AD-5 *Rule*, after the three-check sentence).** *"The exemption above travels with the calling principal, not with the request: a lifecycle call is recognized by the receiver from the authenticated caller identity mapped through the operator artifact, never from a field the caller sets. ### SEC3-06 — high — CloudEvent `source` is outside the single-case grammar and outside the reserved delimiter, so an untrusted publisher can collide the durable duplicate-suppression key

### SEC3-15 — low — "Single-case" does not say which case, and the two systems the clause was written for disagree

**Spine:** `:92` ("one documented bounded ASCII grammar that is **single-case** — so no downstream system that folds case can collapse two distinct identifiers into one"; the exclusion list names "Kubernetes object names" and, newly, "SQL identifiers"), `:189` (Conventions row, not updated for single-case), `:224` (PostgreSQL as the access-telemetry store).

**Consequence.** Kubernetes object names are DNS-1123 and must be lowercase; unquoted identifiers fold to lowercase in PostgreSQL and to **uppercase** under the SQL standard. A grammar that chose uppercase would satisfy "single-case" literally and produce invalid Kubernetes object names for every per-tenant resource. Since the grammar document does not yet exist (SEC3-09), the choice is unmade and the clause does not constrain it. The Conventions row at `:189` restates the identifier rule without the single-case property, so the two statements of the same invariant already differ.

**Closing text (`:92`).** *"…that is **lowercase** — chosen so that identifiers are valid unchanged as DNS-1123 Kubernetes object names and as unquoted PostgreSQL identifiers, and so no downstream system that folds case can collapse two distinct identifiers into one."* Mirror the property into `:189`.

### SEC3-16 — low — The single-case guarantee spans only the population issued under the grammar, and the legacy sweep does not name case-variant resolution

**Spine:** `:92` (single-case binds **issuance**), row `:339` (convergence: "Enumerate and remediate pre-grammar identifiers, validate on read at every trust boundary including import, and re-run G2 against legacy fixtures rather than fresh ones" — no mention of case). **Requirement:** `prd.md:1141` (NFR8 verification is re-run "when Epic 24 closes").

**Consequence.** A tenant `Acme` provisioned before 2026-09-12 and a tenant `acme` provisioned after it are both legal in their own regimes and ordinally distinct in .NET, and they collapse to one object in Kubernetes and in an unquoted PostgreSQL identifier — the AD-17 telemetry partition being the concrete case (`:98`, `:164`, `:224`). Tenant `Acme`'s access telemetry lands in tenant `acme`'s partition. Row `:339`'s remediation is written about grammar conformance, and a legacy identifier that is *fully conformant except for case* passes any character-based check. The collision is created by the amendment, since before single-case both would have been rejected or both accepted under the same rule.

**Closing text (row `:339` convergence).** *"…including case-variant resolution: no two identifiers in the platform may differ only by case after the sweep, and a legacy identifier whose lowercase form collides with an issued identifier is re-issued rather than normalized."*
