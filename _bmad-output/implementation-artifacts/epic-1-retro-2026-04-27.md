## What Went Well

1. The architecture spine landed incrementally.
   Story 1.1 created the solution, Aspire AppHost, DAPR sidecar wiring, Redis Stack, FalkorDB, ServiceDefaults, and submodule detection. That gave every later story a concrete execution base.

2. Contracts became a stable shared language.
   Story 1.2 established MemoryUnit, GraphEdge, metadata, error response, enum serialization, and JSON round-trip tests. Later stories extended Contracts.V1 instead of bypassing it.

3. Risky integrations were wrapped behind focused activities.
   Kreuzberg extraction, embedding generation, and indexing each shipped as DAPR workflow activities with direct tests and clear exception propagation.

4. The graph safety boundary was introduced early.
   `IGraphQueryBuilder` and `GraphQueryBuilder` prevented raw Cypher construction from leaking into activities. Review findings tightened edge labeling, duplicate relationship handling, tenant graph checks, and injection resistance.

5. Story reviews improved the implementation materially.
   Review findings caught real issues: metadata not persisted into indexes, inconsistent tenant validation, index dimension drift, compensation failure context loss, raw graph query construction, request size enforcement, and API-key caching scope.

6. Provider configuration adapted to current platform reality.
   Story 1.7 moved from the deprecated Google model reference to configurable `gemini-embedding-001` defaults, while preserving 768-dimension compatibility and reindex warnings.

## Challenges

1. Validation responsibilities drifted until review forced consolidation.
   Story 1.6 had duplicated and inconsistent validation across the API endpoint and workflow activity. The fix introduced centralized ingestion validation and JSON option alignment.

2. Cross-backend consistency required more care than initial tasks implied.
   The workflow needed tracked compensation, post-index failure rollback, failure details, consistency checks, and dedup persistence ordering. These were not optional details; they are the core of FR6 and FR13.

3. Some requirements were accepted by story status before evidence was complete.
   Story 1.6 still has an unchecked review patch for sidecar-restart resume evidence. The implementation may be correct, but the evidence is not captured in the current integration coverage.

4. Index creation inside indexing activities is known technical debt.
   Story 1.5 documents that `FT.CREATE` inside each indexing activity is acceptable for MVP but should move to tenant provisioning. This affects Epic 2 because search stories must rely on stable schema assumptions.

5. Documentation and planning artifacts have naming drift.
   The implemented canonical index names are `{tenantId}:memories:idx` and `{tenantId}:memories:vec`. Some planning text still references older `{tenantId}:syntactic` and `{tenantId}:semantic` names. Epic 2 search work should use the implemented names.

6. Byte payloads in workflow state remain an accepted MVP constraint.
   Stories 1.3 and 1.6 both document inline byte payloads in DAPR workflow state. This is acceptable for the current scope but should not be forgotten as ingestion volume grows.

## Key Lessons

1. Put system invariants in one place.
   Tenant ID shape, metadata confidence, payload size, and JSON options should be enforced by shared validators or composition-level configuration, not repeated ad hoc.

2. "Done" needs evidence for operational behavior.
   Durable workflow resume, compensation, and consistency behavior need explicit tests or recorded verification. A design assumption is not enough for reliability requirements.

3. Safety interfaces are valuable when they enforce a real boundary.
   `IGraphQueryBuilder` was justified because it prevents unsafe Cypher patterns. This is a good example of an interface that exists for correctness, not speculative extensibility.

4. Review findings should feed planning, not just patches.
   Epic 1 reviews exposed patterns that Epic 2 must account for: schema naming, backend availability, score provenance, and graph query safety.

5. Config changes need operational state.
   Story 1.7's `ReindexRequired` flag is the right shape: provider and dimension changes cannot be treated as simple mutable settings.
