## What Went Well

1. **The Epic 18 preflight (re-verify every cited anchor against live code) paid for itself repeatedly.**
   The charter mandated re-verifying each story's cited code anchors before implementing, because three of the seven Parties asks (MEM-1, MEM-4, MEM-7) were partly based on stale assumptions. That mandate caught real divergence: 18.1 proved the reported `AddHexalithEventStore` "redis-parameter drift" was a stale submodule pin, not a live API; 18.4 found two live-code discrepancies — `EventStoreDedupKey.Build` is keyed on `cloudEventId`, not `sourceUri` (despite a misleading parameter name and doc comment), and `RedisPreflightDedupStore.TryReserveAsync` maps an in-flight marker to `FailOpen`, not `Duplicate` — either of which would have shipped a non-functional race fix had the story been implemented literally; 18.7 and 18.8 found **zero** production drift, which was the correct, money-saving outcome (no code change needed).

2. **Doc↔code drift guards, not prose, made every contract enforceable.**
   The repo deliberately has no markdown linter; instead each published contract is tied to code by a content-asserting xUnit test. The technique matured across the epic: 18.1 used a compile-time project-resolution guard plus reflection over anchor types; 18.2 added bidirectional constant ties (`EventIngestionController.TopicEnvVar`/`.PubSubName`) and source↔doc cross-checks; 18.3 derived the guarded route list directly from `Program.cs` `app.MapX(...)` literals and added a 45-route count tie (the strongest guard); 18.6 read `SaveDedupKeyActivity.cs`/`DedupKeyBuilder.cs`/`SourceUriMemoryUnitLookup.cs` to assert `expiry: null`, the dedup key shape, and the lookup's reuse of `DedupKeyBuilder.BuildKey`. These guards failed red on real gaps (18.5's two unmapped error-catalog codes; 18.6's doc↔code ties), proving they were live, not decorative.

3. **Release discipline was exact.**
   Only 18.4 was a `feat`, and it was scrupulously additive — the existing 8-parameter `IngestAsync` signature was preserved byte-for-byte (adding an optional parameter would have been binary-incompatible on a `virtual` method) and a new overload added alongside, with the `HXL001` experimental marker removed non-breakingly. Every other story committed `docs:` / `test:`. This keeps the one semantic-release MINOR cleanly separable so it can be cut before Parties pins the SDK.

4. **Reuse-not-duplicate held as a design rule.**
   18.5 exposed the source-URI lookup over the *existing* permanent dedup record (`dedup:{tenantId}:{caseId}:{SHA256(sourceUri)}`) as the authoritative index rather than introducing a parallel store. 18.8 found the cross-module event-intake implementation already existed (from Epics 9 and Stories 18.2/18.3) and was verify-only on the ops docs, closing just the one missing developer-doc gap. The source-of-truth split stayed clean: deployment literals in `deployment-configuration.md`, routing semantics in `eventstore-integration.md`, ACL surface in `route-surface.md`, each cross-linking rather than copying.

5. **Subtle correctness calls were reasoned, not guessed.**
   18.5 inverted the fail-open posture for reads versus writes on purpose: the ingest path fails *open* on a Redis outage (ADR 9.1-B), but the lookup must **not** — a false `404` on a transient outage could push a consumer to re-ingest into a duplicate, so `RedisException` propagates as a structured `503 LOOKUP_BACKEND_UNAVAILABLE` instead. 18.4 chose "refined Option A" (a `SET … NX` reservation on a distinct `ingest-reserve:{dedupKey}` namespace) over the documented trap of overloading the shared `"reserved"` marker, whose meaning differs between the EventStore preflight and a second concurrent REST workflow.

6. **Review caught real bugs before close — not just nits.**
   18.5's review caught a telemetry-integrity bug: the lookup endpoint used the Delete-access event-id pair (`7505`/`7515`), so every lookup audit event mislabeled a read as a delete in the FR67 audit trail; fixed to the canonical case-access pair (`7504`/`7514`). 18.7's review caught leaked tool-call markup that had corrupted the *published* `client-mockability.md` (a HIGH — a consumer-facing contract shipped with stray XML tags) and added an anti-corruption assertion so the guard can't be blind to it again. 18.4's review caught CRLF violations on two new files.

7. **QA gap-fill found genuine holes the dev pass missed.**
   18.6's `bmad-qa-generate-e2e-tests` pass found the `ResolveMemoryUnitId` file/url path was uncovered (both prior tests were `SourceType.Event` only) and added two facts proving file/url sources reuse the workflow instance id. 18.8's QA pass added three Tier-2 in-process HTTP E2E tests over `/events/ingest` because AC2/AC4/AC5 had been proven only at the unit level.

8. **Cross-repo auditability was built in.**
   Every story carries its `MEM-n` origin and a named Parties-side follow-up, and every ask was flipped from `carried-forward` to `resolved` in `deferred-work.md` with an explicit `Evidence:` line, validated against the Story 14.5 schema by `CiTestInventoryTests`. The linkage between the Memories change and the Parties consumer action stays traceable across both repos.

## Challenges

1. **CRLF/LF line endings caused recurring, ad-hoc friction — the exact debt Epic 17 flagged and did not fix.**
   18.4's review raised a MEDIUM for two new files written LF-only against `.editorconfig`'s `[*] end_of_line = crlf`; 18.5 absorbed accepted normalization churn on pre-existing lines; 18.6 made the *inverse* call and kept its docs LF to match every sibling in `docs/dev`. The root cause is a repo-wide mismatch — `.editorconfig` mandates CRLF globally while `docs/` ships LF and there is no root `.gitattributes`. **No durable fix landed**; each story handled it differently. This is Epic 17 Action Item 6 (add a root `.gitattributes`) still open — and this epic is the evidence it bites.

2. **Tracking-metadata drift recurred — File List omissions and stale test counts.**
   18.1 took three MEDIUM review findings, all tracking metadata (File List missing `PublicSurfaceStabilityTests.cs` and `test-summary.md`; a stale 237/+1 count vs the real 239/+3; understated coverage notes), because the QA-automation phase adds tests after the Dev Agent Record is written. Stories 18.2+ tried to track deltas per phase and improved, but the pattern still surfaced. This is Epic 17 Action Items 4 and 5 carried forward — better, not eliminated.

3. **`architecture.md` drifted from live code in several places.**
   The epic repeatedly tripped over stale architecture wording: `MemoryUnitId` described as a "ULID" (it is the workflow `InstanceId` or a fresh GUID, opaque, not time-ordered); "xUnit 2.9.3" (the repo is on `xunit.v3` 3.2.2); a "Controllers/*Controller.cs" route model (routes are minimal-API `app.MapX(...)` literals); and the Server Dapr app-id projected as `memories-server` (the real default is `memories`). "Code is source of truth" was the recurring resolution, and 18.6 neutralized the ULID claim via its contract doc rather than editing `architecture.md`. The architecture doc is now the single largest documentation debt out of this epic.

4. **Substring-based content guards are fooled by prose.**
   `ShouldContain` assertions match anywhere, including narrative text and cross-links. 18.2 accepted the limitation that an append-style rename (a suffix added) slips past. 18.3 hit it twice — the dev hardened the forward route tie to assert the table-row form `` `<VERB> <path>` `` after a bare-substring draft was satisfied by a prose example, and review then hardened the health-probe tie the same way. 18.7's leaked-markup HIGH existed precisely because a presence-only guard couldn't see corruption. The lesson generalized: anchor doc assertions to the table-row form and add explicit anti-corruption checks.

5. **Generation artifacts leaked into committed docs.**
   Both 18.6's `test-summary` and 18.7's *published* `client-mockability.md` ended with stray `</content>` / `</invoke>` tags from the authoring tool. The 18.6 instance was a low-severity summary file; the 18.7 instance corrupted a consumer-facing contract and was caught only in review (the HIGH). A tail-check / anti-corruption assertion is now the mitigation.

6. **Doc-comments and parameter names lied.**
   18.4 found `EventStoreDedupKey.Build` declared a `sourceUri` parameter with a `sha256(sourceUri)` doc comment, but the only call site passes `envelope.Id` — it is `cloudEventId`-derived. Only the interface XML doc and the call site were authoritative. This is the kind of trap the preflight mandate exists to catch.

7. **The sandbox test workaround was rediscovered story by story.**
   Every Epic 18 story re-stated the same dance: `dotnet test` aborts with `SocketException (13)` on a VSTest TCP listener, so tests run via `DiffEngine_Disabled=true dotnet exec <dll>` with an xUnit v3 filter. It is correct and consistently applied, but it is Epic 17 Action Item 4 (record the workaround in contributing guidance) still open, paid as repeated per-story rediscovery.

8. **Deferred items were parked without backlog homes.**
   `MEM-2-ASPIRATE` (full aspirate manifest emission) and `MEM-3-OPENAPI` (OpenAPI/Swagger generation) are open-ended `carried-forward` ledger entries with **no assigned story id**. The real two-thread Redis race test and the Dapr-sidecar smoke test are deferred to an Aspire/Testcontainers lane that does not run in this sandbox. 18.4 left a known token-anchoring edge (a token whose first use falls back to a pre-existing sourceUri unit relies on a 24h reservation key, not a permanent record) for a future hardening story. None of these has a scheduled landing.

## Significant Discoveries

1. **Three of seven consumer asks were partly stale — verification before fixing was the whole game.**
   MEM-1 (project symbols don't resolve / redis-param drift), MEM-4 (`IngestAsync` is `Obsolete`), and MEM-7 (need a mockable `IMemoriesClient`) were each partly incorrect against current `main`: the symbols already resolved, `IngestAsync` was `[Experimental]` not `Obsolete`, and the client was already non-sealed with `virtual` members. The residual real gaps were narrow — a guard test, an atomic dedup + token, a documented seam. A team that "just fixed the tickets" would have done unnecessary and possibly wrong work; the preflight mandate is what turned seven asks into precise, minimal closures.

2. **The permanent source-URI dedup record is the load-bearing object behind three stories.**
   18.4's atomic dedup, 18.5's lookup endpoint, and 18.6's stability contract all hinge on the same `dedup:{tenantId}:{caseId}:{SHA256(sourceUri)}` → `MemoryUnitId` record being TTL-less (`expiry: null`). The stability guarantee is explicitly conditional on that record persisting; the lookup reuses it as the authoritative index; the token (18.4) must *augment*, never *replace*, it. This made the 18.5/18.6 "land together" sequencing note in the charter exactly right, and it is the single fact a downstream consumer most needs to understand.

3. **`MemoryUnitId` is opaque and GUID-derived, not a ULID.**
   It is the workflow `InstanceId` or a fresh `context.NewGuid()` (`ResolveMemoryUnitId` in `IngestionWorkflow.cs`) — no time-ordering, no parseable structure, not derived from `sourceUri`. The architecture doc's "string (ULID)" wording is wrong, and 18.6's contract now states the opacity precisely. Consumers must treat the id as an opaque string and resolve it via the 18.5 lookup rather than reconstructing or assuming its shape.

4. **Content-asserting guards beat prose docs, but only if they assert the right shape.**
   The strongest guards in the epic (18.3's source-derived route tie + count check; 18.6's bidirectional doc↔code ties) catch both omission and phantom entries. The weakest (bare `ShouldContain`) are satisfied by narrative text and blind to corruption. The maturation curve within a single epic — from substring to table-row-form to anti-corruption assertion — is itself the reusable lesson for any future contract-doc work.
