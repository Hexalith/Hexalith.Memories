## Plain-English summary

Story 8.4 writes two tests against a running copy of the whole system. **Test 1** runs a search and verifies every step of the request (CLI command → HTTP call → web server → search logic) stamped its work with the same trace ID. **Test 2** runs one of each operation (search / ingest / traverse / case-access) and verifies the server wrote exactly the expected structured audit log line per operation. The tests need Docker because they use Aspire to boot Redis + FalkorDB + DAPR sidecar + the Memories Server together; they run on the merge-queue lane (not every PR) to keep PR CI fast.

**Effort estimate:** **~3.5–4 working days** end-to-end (revised from ~3 days at Rev 0.5 after Stakeholder Round Table review): 1 day Aspire fixture wiring + in-memory OTLP exporter plumbing (Tasks 0-1 including Task 1.1.5 parse test + Task 1.1.6 shared-singleton + spike fallback), 1 day authoring `AspireEndToEndTraceTests` (Task 2 including span-tree dump), 0.5 day authoring `AuditLogStreamIntegrationTests` (Task 3), 0.5 day Task 7 skip-review-by infra + filing the tracking GitHub issue (external dep), 0.5–1 day docs + ADR-8.4-003 document + CI gating (Tasks 4-6). Adjust if the Aspire fixture build error (`CS0311 on IDaprSidecarResource`, historically surfaced in Story 5.6 Dev Notes) reproduces on the current `Hexalith.Memories.AppHost` — as of 2026-04-20 the AppHost uses `WithDaprSidecar(...)` + `IResourceBuilder<IDaprComponentResource>` cleanly, so the risk is believed resolved; add 0.5-1 day only if Task 0 surfaces a regression.

**What does NOT ship:**

- **Replacing Tier-2 variants.** `TracePropagationNoDockerTests` + `AuditLogStreamTests` + `TelemetrySummaryEndpointTests` stay as the CI-on-every-PR gate; 8.4 is **additive**, running on the Docker-capable lane only.
- **MCP → Server trace propagation.** Story 7.5 Rev 0.3 finding 1c assigns this to Epic 10's MCP story (the MCP protocol introduces the first real DAPR service-invocation hop Memories originates). 8.4 covers CLI → Server via HTTP; the MCP story extends the same fixture pattern for the DAPR-hop variant.
- **Percentile / histogram end-to-end assertions.** Story 7.5 Rev 0.2 deferred p50/p99 aggregation; the Tier-3 fixture does not re-open that scope. Histogram emission IS exercised (`memories.search.duration` is recorded per request), but assertions on the histogram shape are out of scope — the in-memory exporter captures the fact that the metric was emitted, not specific percentile values.
- **Test-side OTLP collector process (unless fallback is chosen).** Do NOT spin up a separate Jaeger / Tempo container. The in-memory exporter runs inside the test process; the Server's OTLP endpoint points at it via an in-process loopback. This keeps the fixture boot time under the existing Epic 6 budget.
- **Authoritative Kubernetes / helm-chart traces.** Production deployment shapes are orthogonal; the Aspire fixture uses Aspire's container orchestration, not Kubernetes. Operator-facing Kubernetes telemetry guidance stays in `docs/dev/telemetry.md` as documentation, not tested behavior.
- **Per-axis trace breakdown inside hybrid search.** Story 7.5 AC #3 clarified that `axis=hybrid` records the whole-request wall-clock — per-axis sub-spans inside a hybrid call are a Phase 1.5 concern. 8.4 asserts trace propagation at the request boundary, not sub-axis granularity.
- **Re-testing Story 7.5's substrate invariants.** `MemoriesActivitySourceTests`, `MemoriesMetricsTests`, `EndpointTelemetryScopeTests`, `RollingCounterStoreTests`, `AccessTelemetryLogTests`, `AccessTelemetryEventSchemaTests`, `TelemetryHealthExclusionTests`, `OpenTelemetryRegistrationTests` all stay green and do NOT need duplication at Tier-3. The fixture-level tests ONLY assert cross-process invariants the Tier-2 variants cannot reach.

**Primary risks:**

1. **Aspire fixture build error regression.** Story 5.6 Dev Notes historically flagged a `CS0311 on IDaprSidecarResource` error on some SDK versions. Current AppHost (`src/Hexalith.Memories.AppHost/Program.cs`, as of 2026-04-20) uses `WithDaprSidecar(sidecar => ...)` cleanly — no direct `IDaprSidecarResource` generic constraint — and siblings 8.1-8.3 have integration tests green. **Mitigation:** Task 0 (pre-flight) verifies the fixture builds and boots; if the error reproduces, the first day's effort is AppHost investigation + fix. Escalate to a separate fix-forward story if >0.5 day of work.
2. **Cross-process OTLP capture is fragile.** The Server container's OTLP exporter must route to an in-process listener in the test. If the chosen approach (env-var-triggered in-memory processor) doesn't survive Aspire's service-discovery rewrites, fall back to a test-side OTLP receiver (in-process gRPC server) at a dynamic localhost port and configure the container to export there via `OTEL_EXPORTER_OTLP_ENDPOINT`. **Mitigation:** Task 1.1 spikes the env-var approach; Task 1.2 documents the fallback path in ADR-8.4-002 so a future contributor can flip without re-inventing.
3. **Trace id collision across parallel test runs.** If two integration tests run in parallel (xUnit parallelism within the `IntegrationTests` assembly), both capture activities into the same in-memory exporter. Tests must filter by test-scoped trace id. **Mitigation:** reuse the `TestRootScope` pattern from `TracePropagationNoDockerTests` (`tests/Hexalith.Memories.Server.Tests/Telemetry/TracePropagationNoDockerTests.cs:61-96`) — either copy/adapt or extract to a new `tests/Hexalith.Memories.IntegrationTests/Telemetry/Infrastructure/` helper file. Alternatively, disable parallelism for the 8.4 test classes via `[Collection("Telemetry Integration")]`.
4. **Audit-log capture from stdout is timing-sensitive.** Container stdout is asynchronous; a test that asserts immediately after a request may race. **Mitigation:** the test uses a polling read with a 5-second timeout against the container's log stream; tolerates multiple log lines before the target event; explicit matching by `EventId` + `traceId`. Use `IAsyncEnumerable` over the stream (no `Thread.Sleep`). The fixture already wires a `TestLogProvider _logProvider`; inspect whether it aggregates Server container stdout or only Aspire resource logs — if only Aspire logs, add a container-stdout capture helper.
5. **Docker CI cost.** Running two Tier-3 test classes on every PR roughly doubles CI minutes vs. Tier-2-only runs. **Mitigation:** ADR-8.4-001 explicitly routes Tier-3 to the merge-queue lane (not per-PR). Per-PR runs stay fast via Tier-2 coverage; release-gate runs exercise Tier-3. Document the lane split in `.github/workflows/` + `docs/dev/telemetry.md`.
6. **Redis / FalkorDB instrumentation may not be registered.** Story 7.5 deferred adding `StackExchange.Redis.Extensions.OpenTelemetry` instrumentation — the substrate assumes it MAY be present, not that it IS. If absent, the "downstream Redis span" assertion silently succeeds (no Redis span found, test still passes the CLI → Server chain). **Mitigation:** the trace-propagation test asserts the CLI → Server chain as the primary invariant; the Redis span assertion is a secondary check that logs a `Skip` trait when the instrumentation is absent. Adding Redis OTEL instrumentation itself is out of scope (separate story, probably in Epic 11 CI hardening).
7. **Env-var parse strictness masks misconfiguration.** `HEXALITH_MEMORIES_TELEMETRY_INMEMORY` is evaluated by exact string match `== "1"`; values like `"true"`, `"on"`, `"yes"`, `"True"` silently leave the collector unregistered. A developer who uses truthy variants thinks they enabled capture when they did not — tests pass vacuously (no captured activities → assertions of "at least one" fail loudly, but assertions that compare counts between captured vs expected may hide zero-vs-zero bugs). **Mitigation:** Task 1.1.5 adds a unit test that iterates the recognized-but-wrong values and asserts the collector stays unregistered; additionally, when the env var is present and non-empty but not `"1"`, emit a one-line `Console.Error` warning (`[telemetry] HEXALITH_MEMORIES_TELEMETRY_INMEMORY=<value> — only "1" activates; ignoring`) so misconfiguration surfaces in test logs.
8. **W3C trace-chain topology brittleness.** AC #1's original framing asserted a specific chain shape (CLI root → HttpClient → AspNetCore → `memories.search`). An OpenTelemetry or AspNetCore instrumentation bump can introduce intermediate spans (routing, middleware, endpoint selection) that break the fixed topology without breaking actual trace propagation. **Mitigation:** AC #1 (as of Rev 0.4) asserts **shared `TraceId` + ancestor-descendant reachability** — i.e., every expected span appears in the collection, all share one `TraceId`, and each expected span's parent chain reaches the CLI root via `Activity.Parent` traversal — rather than a fixed parent-child sequence. On failure, Task 2.3.5 dumps the full captured span tree for triage.
9. **AC #2 soft-skip becoming permanent.** Without a review trigger, the `"Redis OTEL instrumentation not registered"` skip can silently persist for months. **Mitigation:** Task 7 adds a self-expiring assertion — the skip is valid until `2026-07-01`; past that date the test fails red until either (a) Redis OTEL instrumentation is registered (skip converts to a hard assertion), or (b) a tracked GitHub issue explicitly extends the review-by date in source. The skip event must also emit `telemetry.redis.instrumentation.skipped` at `Warning` level so merge-queue logs surface the skip every run.
10. **Log-exporter flush race on AC #4 cross-reference.** The in-memory `LogRecord` exporter (if chosen per ADR-8.4-003) buffers internally; reading immediately after a search call may find the activity but not yet the `AccessTelemetryEvent` log record, causing a flaky `TraceId`/`SpanId` match. **Mitigation:** call `LoggerProvider.ForceFlushAsync(TimeSpan.FromSeconds(2))` **and** `TracerProvider.ForceFlushAsync(TimeSpan.FromSeconds(2))` before the cross-reference assertion reads the collector; document both in Dev Notes and in `InMemorySpanCollector.Reset()` as preconditions.

## Story

As the Memories release manager,
I want end-to-end Tier-3 integration tests that verify distributed traces propagate across CLI → Server → backends AND audit events reach the deployed stack's stdout log stream,
so that I can ship releases with confidence that NFR28 and FR67 hold on real infrastructure — not just on the Tier-2 in-process approximation.

## Acceptance Criteria

1. **Single TraceId end-to-end (NFR28 HTTP-hop gate — see AC #8 for scope).**
   **Given** the `AspireIngestionPipelineFixture` is running with an in-memory OTLP exporter wired to capture both the CLI's emitted spans and the Server container's emitted spans,
   **When** the CLI invokes `memories search query --tenant <provisioned-tenant> --query "<any>"` via the DI entry point (NOT a subprocess) with `HEXALITH_MEMORIES_OTEL_ENDPOINT` set to the fixture's OTLP endpoint,
   **Then** **count-first** — `InMemorySpanCollector.Activities.Count >= 4` MUST pass BEFORE any content-equality assertion (red-team R1 mitigation: an empty collection passes `.All(...)` predicates vacuously, so count gates content)
   **And** the captured span collection contains, at minimum: one CLI root span (`memories.cli.invoke`), one outbound HTTP client span, one AspNetCore server span, and one `memories.search` activity — each looked up by operation-name, not by index
   **And** all of these spans share a single `TraceId`
   **And** the parent chain of each expected span reaches the CLI root via `Activity.Parent` traversal (ancestor-descendant reachability) with: (i) cycle detection — a visited-set fails any chain that revisits a span id; (ii) max-depth ceiling = 16 — chains longer than 16 hops fail with a diagnostic (no legitimate in-process trace exceeds this); (iii) root-termination rule — traversal MUST terminate at the CLI root span (null-parent + name == `memories.cli.invoke`); termination at any other null-parent emits an `orphan span detected: <opName>` diagnostic and fails. The test does **not** mandate a fixed topology or a specific intermediate-span count, so that OTEL/AspNetCore instrumentation bumps that introduce routing/middleware spans do not break the assertion (see Risk 8).

2. **Optional downstream Redis / FalkorDB span attribution.**
   **Given** AC #1's captured span collection,
   **When** `StackExchange.Redis.Extensions.OpenTelemetry` or equivalent Redis OTEL instrumentation is registered at time of test execution,
   **Then** at least one Redis client span appears in the same trace (same `TraceId` as AC #1's AspNetCore span)
   **And** when the instrumentation is NOT registered, the test emits an xUnit `Skip` trait for this specific assertion with reason `"Redis OTEL instrumentation not registered"` — the AC #1 invariant still gates test pass/fail
   **And** the skip event is surfaced via a `telemetry.redis.instrumentation.skipped` log line at `Warning` level on the merge-queue lane so the skip does not silently persist forever — AC #2 is **informational-only** until Redis OTEL instrumentation lands (tracked as a separate Epic 11 item); contributors are expected to convert the skip to a hard assertion once instrumentation registers
   **And** the skip path is **time-bounded** — the skip condition is evaluated against a review-by date constant (`AC2_REDIS_SKIP_REVIEW_BY = 2026-07-01`) enforced by Task 7's self-expiring assertion; past that date, the test fails red with a diagnostic pointing to the tracked GitHub issue unless either the instrumentation has been registered (flipping the skip to a hard assertion) or the review-by date has been explicitly extended in source with a linked tracking issue reference (see Risk 9).

3. **Audit-log capture from stdout (FR67 authoritative gate).**
   **Given** the fixture is running with the Server container's stdout available via the Aspire container API,
   **When** one operation of each instrumented type runs (`search`, `ingest`, `traverse`, `case-access`) against a provisioned tenant,
   **Then** the stdout log stream contains **at least one** structured JSON line per operation that matches the `AccessTelemetryEvent` schema filter (`schemaVersion == 1` AND `eventId` in `7500-7599` AND matching `operationType`) — incidental non-matching log lines (trace-level diagnostics, framework noise) are ignored by the filter, so adding debug logging elsewhere does not break this AC
   **And** the de-duplication guard holds across the per-operation window: no two matching events share the same `(traceId, spanId, operationType, httpStatus)` tuple — `httpStatus` is included so that a legitimate client retry on a 5xx followed by a successful 2xx produces two distinct events (different `httpStatus` → distinct tuple → no false-positive failure), while a genuinely duplicated emission on the SAME attempt (same trace, same span, same status) still fails the guard. Spec-level retries that generate a new `SpanId` per attempt are also naturally distinct. Test authors MUST exercise at least one retry case (5xx → 2xx) in a separate case or as a scenario inside AC #3 to validate the guard tolerates retries — a story finding worth capturing in the test suite itself.
   **And** each matching event has `schemaVersion == 1`, `eventId` in `7500-7599`, non-empty `tenantId`, matching `operationType`, non-empty `traceId` + `spanId`, and a `durationMs >= 0`
   **And** health-endpoint probes (`/health`, `/alive`, `/ready`) produce zero `AccessTelemetryEvent` entries in the same window (regression guard for Story 7.5 AC #5).

4. **TraceId cross-reference between span and audit event.**
   **Given** AC #1's captured `memories.search` activity and AC #3's search `AccessTelemetryEvent`,
   **When** both are compared,
   **Then** `auditEvent.TraceId == searchActivity.TraceId.ToString()` AND `auditEvent.SpanId == searchActivity.SpanId.ToString()` — same invariant Story 7.5 Tier-2 asserts (`AuditLogStreamTests`), now proven end-to-end across the real deployed stack.

5. **Test-side OTLP capture does not affect production behavior.**
   **Given** the in-memory exporter wiring added in Task 1,
   **When** the Server is run without the 8.4 test env var / configuration trigger,
   **Then** no in-memory exporter is registered
   **And** no new `IHostedService` / processor is appended to the production OpenTelemetry pipeline
   **And** Story 7.5's `OpenTelemetryRegistrationTests` continue to pass unchanged.

6. **CI lane gating.**
   **Given** the GitHub Actions workflow matrix,
   **When** a PR is opened,
   **Then** 8.4's tests run only on the merge-queue / release lane (NOT the per-PR lane)
   **And** ADR-8.4-001 documents the lane split with a one-sentence rationale per lane
   **And** `docs/dev/telemetry.md` lists which tier runs on which lane so contributors know where regressions surface.

7. **Documentation.**
   **Given** an operator or developer wants to verify telemetry end-to-end locally,
   **When** they read `docs/dev/telemetry.md`'s new "End-to-end trace verification" section,
   **Then** the doc covers: how to run the Tier-3 tests locally (`dotnet test --filter Category=Integration` with Docker available), what each captured span proves about the deployed stack, the tier split (Tier-2 per-PR vs Tier-3 merge-queue), and how to interpret failures (OTLP wiring vs DAPR hop vs audit pipeline).

8. **NFR28 scope honesty (self-audit on overclaiming).**
   **Given** 8.4's TL;DR originally claimed "authoritative NFR28 gate (distributed trace propagation across DAPR hops),"
   **When** the implementation path is re-examined against what the tests actually prove,
   **Then** 8.4's scope MUST be framed as the **NFR28 HTTP-hop gate** (trace propagation across the CLI → Server HTTP boundary, including the AspNetCore server-side + HttpClient client-side instrumentation and the W3C `traceparent` header transit) — the **DAPR service-invocation hop is out of scope** because Memories Server does NOT originate a DAPR service-invocation call in the CLI → Server → backends path exercised by the fixture
   **And** the TL;DR ("What ships"), "What does NOT ship," and Dev Notes ("Implementation contracts for 8.4") all reference this scope explicitly and consistently
   **And** the authoritative DAPR-hop gate is called out as deferred to Epic 10's MCP story (the first originator of a DAPR service-invocation hop) with a direct cross-link.

### Implementation contracts for 8.4

- **Tier-2 tests are canonical.** If a Tier-3 test fails in a way a Tier-2 test would have caught, the fix lives at Tier-2 and the Tier-3 test stays as the gate. Do NOT let Tier-3 drift into substrate-testing territory.
- **No subprocess CLI invocations.** Story 7.1 anti-pattern #8 holds: the CLI is invoked via DI, in-process, inside the test's assembly.
- **Fixture sharing.** Reuse `AspireIngestionPipelineFixture` as an xUnit `IClassFixture` or collection fixture; do NOT boot a fresh Aspire environment per test class (cost prohibitive). Telemetry collector state is reset per test via a public `Reset()` helper on the in-memory capture mechanism.
- **Token / secret hygiene.** Do NOT log `HEXALITH_MEMORIES_OTEL_ENDPOINT` if it contains credentials (e.g. Honeycomb API key in query string) — the Tier-3 test uses a loopback endpoint so this is unlikely, but the documentation should note the production caveat.
- **Test-scope env var hygiene.** Every test that sets `HEXALITH_MEMORIES_OTEL_ENDPOINT` or `HEXALITH_MEMORIES_TELEMETRY_INMEMORY` MUST restore the previous value (or clear) in the `Dispose` / finally block. Static env-var state bleeds across parallel tests otherwise.
- **Sampler invariant.** The `TracerProvider` used by both CLI and Server DI containers in the fixture MUST use `AlwaysOnSampler`. Head-based sampling (`TraceIdRatioBasedSampler` < 1.0) can silently drop traces and make AC #1 flaky. Validate in fixture init — assert `TracerProvider.GetSampler()` or inspect the sampler type via reflection at test startup and fail loudly if anything other than `AlwaysOnSampler` is configured.
- **Force-flush both pipelines.** Tests that assert AC #4 (TraceId/SpanId cross-reference between activity and `AccessTelemetryEvent`) MUST call `LoggerProvider.ForceFlushAsync(TimeSpan.FromSeconds(2))` AND `TracerProvider.ForceFlushAsync(TimeSpan.FromSeconds(2))` before reading the collectors. OpenTelemetry buffers `LogRecord` separately from `Activity`; flushing only the tracer leaves a race where the activity is captured but the correlated log record is still in-flight (Risk 10).
- **Iteration speed — amortize fixture boot.** Aspire fixture cold boot is ~30–60s. Two test classes sharing `[Collection("Telemetry Integration")]` + `IClassFixture<AspireIngestionPipelineFixture>` amortize the boot across all test methods. For single-class dev iteration, use `dotnet test --filter FullyQualifiedName~AspireEndToEndTraceTests` (or `~AuditLogStreamIntegrationTests`) to avoid booting the fixture twice. Document the iteration workflow in `docs/dev/telemetry.md` Task 5 so first-time contributors don't fight fixture re-boots.
- **Count-first, content-second assertion convention.** Any assertion over a captured collection (`InMemorySpanCollector.Activities`, `AccessTelemetryEvent` list, log-line list) MUST validate `Count >= expectedMinimum` BEFORE any predicate that could pass vacuously on an empty collection. LINQ `.All(...)` returns `true` on empty; `.Any(...)` returns `false`; neither detects "capture never happened." This is a Story 8.4 red-team finding (R1) worth codifying as a project-wide test convention — propagate to any future integration test that uses in-memory capture collectors.

### Rejected alternatives (documented so future contributors don't re-litigate)

- **Raw `ActivityListener` at assembly-init.** Rejected: bypasses the OpenTelemetry SDK's exporter chain entirely. The test would observe activities at the `System.Diagnostics` layer but prove nothing about OTEL registration, samplers, processors, or exporters. 8.4's purpose is to prove the **end-to-end OTEL pipeline** works in a deployed shape — a test that side-channels around the pipeline fails to meet the NFR28 HTTP-hop intent.
- **Subprocess CLI invocation (`dotnet run --project ... -- search ...`).** Rejected: Story 7.1 anti-pattern #8. The CLI's `TracerProvider` lives in the subprocess; its spans are exported via OTLP to the subprocess's configured endpoint. The test cannot share in-memory collectors across process boundaries without pivoting to an OTLP receiver (Task 1.2 fallback), which adds complexity and a port/dependency without proving anything the in-process DI path doesn't already prove for the HTTP hop. If DAPR-hop coverage is ever added (Epic 10 MCP story), re-evaluate — subprocess CLI + OTLP receiver may become the right shape for exercising process-boundary trace propagation.
- **OTLP gRPC receiver as the primary capture path.** Kept as **fallback only** per Task 1.2. Rejected as primary because: (a) `host.docker.internal` DNS resolution is flaky on Linux CI runners; (b) adds `Grpc.AspNetCore.Server` dependency not currently in `Directory.Packages.props`; (c) dynamic-port collision risk under CI parallelism; (d) proves OTLP wire format but doesn't prove anything in-memory-exporter+DI wiring doesn't already prove for the HTTP hop. Documented in ADR-8.4-002 addendum.
- **Production-visible `InMemorySpanCollector` in `src/Hexalith.Memories.Telemetry/`.** Rejected (Winston, party-mode 2026-04-20, ADR-8.4-002 option A). Static mutable collector surface in a consumer-facing package is a foot-gun for plugin authors across the Hexalith ecosystem, even with `[Experimental("HXL008")]` + `[EditorBrowsable(Never)]`. Test-only placement keeps blast radius bounded.

### ADR-8.4-003 — Audit-event capture path per test

> **Status:** Accepted (2026-04-20, Rev 0.5 elicitation pass) — will be promoted to `docs/dev/telemetry.md` as a sibling of ADR-8.4-001 and ADR-8.4-002 by Task 5.1. Recorded here in-story so the implementation doesn't block on the doc write.

**Context.** Story 8.4 captures `AccessTelemetryEvent` records in two different tests with two different purposes:

1. `AspireEndToEndTraceTests.CliSearch_AuditEvent_TraceIdMatchesSpan` (AC #4) — asserts the `TraceId` / `SpanId` on the audit event match the captured `memories.search` activity. The test proves the **in-process correlation invariant** between the tracing pipeline and the logging pipeline; it does NOT need to prove the log reaches stdout.
2. `AuditLogStreamIntegrationTests` (AC #3) — asserts one matching JSON line per operation appears on the Server container's stdout, parseable as `AccessTelemetryEvent`. The test proves the **real operator pipeline** — Server container writes → stdout → Aspire log stream → (production) SIEM / log aggregator ingestion point. This is the FR67 gate.

These two tests answer different questions and have different reliability profiles. Rev 0.3 left the choice as "pick the simpler capture that works with Task 1 outcome" — ambiguous, and a future contributor unable to re-derive the reasoning was likely to converge on one approach for both.

**Decision.** Pin the capture path per test:

| Test                                             | Capture path                                                                                                                                                                                    | Why                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CliSearch_AuditEvent_TraceIdMatchesSpan`        | **In-memory log exporter** (`OpenTelemetry.Exporter.InMemory.AddInMemoryExporter(ICollection<LogRecord>)` on the logging pipeline, captured into a fixture-scoped `ConcurrentQueue<LogRecord>`) | In-process, deterministic, no container-stdout timing. Test is about the correlation invariant between two in-process pipelines; container boundary is irrelevant. Pairs naturally with Task 1.1's in-memory span collector so both tracing and logging use the same "capture-via-in-memory-exporter" pattern. Requires dual `ForceFlushAsync` (Risk 10 mitigation). |
| `AuditLogStreamIntegrationTests.*` (AC #3 cases) | **Container stdout via Aspire log stream** (`AspireIngestionPipelineFixture._logProvider` or a container-stdout reader helper per Task 3.1)                                                     | FR67 is an operator-pipeline gate — "does the log reach operations?" — which REQUIRES reading the actual container's stdout, not an in-process capture. An in-memory log exporter would pass the test while the container's `ILoggerFactory` could be silently misconfigured and production operators receive nothing.                                               |

**Alternatives considered:**

- _Use container-stdout for BOTH tests._ Rejected: the AC #4 cross-reference assertion then inherits stdout's timing fragility (Risk 10) and 10s-polling-loop (Task 3.6) unnecessarily — the AC #4 test doesn't need to prove stdout delivery, so it shouldn't pay stdout's cost in flakiness.
- _Use in-memory log exporter for BOTH tests._ Rejected: strip-away gate — a container misconfig that silently drops stdout passes all tests. This is exactly the scenario FR67 is meant to catch.
- _Use both capture paths in both tests._ Rejected: doubled assertions without doubled signal. If in-memory captures and stdout doesn't, AC #3 tells us that already; if stdout captures and in-memory doesn't, the pipeline-correlation invariant is broken in a way AC #4 covers.

**Consequences:**

- `AspireEndToEndTraceTests` depends on the in-memory log exporter wiring added by Task 1 (same Option B test-only placement as the span collector) — registered in the Server's DI at fixture init via the env-var-triggered branch.
- `AuditLogStreamIntegrationTests` depends on the container-stdout reader helper built in Task 3.1 and the parameterized timeout in Task 3.6.
- A future change that wants to replace stdout delivery (e.g., OTLP logs to a receiver) MUST update both ADR-8.4-003 and the AC #3 tests; the test pins the _shape_ of the operator pipeline, so re-shaping the pipeline is a visible change.
- Task 5.1 (docs) promotes this record to `docs/dev/telemetry.md` alongside ADR-8.4-001 / ADR-8.4-002. Until Task 5.1 lands, this in-story section is authoritative.
