## What Went Well

- The CLI was introduced with a coherent command shape instead of ad hoc commands. `memories` exposes the expected groups and keeps unfinished areas explicit through stubs.
- The endpoint-resolution contract became concrete and testable: flags, environment, user config, and default resolution are visible through `memories config show`.
- Output formats were treated as a contract, not presentation glue. Story 7.2 added formatter infrastructure, a schema-versioned JSON envelope, table output, and golden tests for 7.1 compatibility.
- Explain output preserved the product trust boundary. The CLI surfaces composite and per-axis scores while keeping the relevance caveat visible.
- Error handling moved from raw plumbing failures to a typed, actionable surface. Story 7.3 split domain and plumbing failures, added recovery suggestions, and extended JSON mode with an `error` envelope.
- Empty states became useful instead of blank. Search and tenant-list outputs gained next-action guidance while preserving script-friendly JSON and table behavior.
- Story 7.4 turned onboarding into a guided flow with explicit prerequisites, health probing, sample tenant/case setup, sample ingestion, validation search, and dry-run support.
- Story 7.5 connected developer operations to observability: traces, metrics, per-tenant access telemetry, and a CLI-friendly telemetry summary surface.
- Review discipline was strong. Each story contains explicit review findings and remediation notes, including decision records for scope boundaries and bridge behavior.

## Challenges

- Story 7.1 had to make a framework choice under prerelease package constraints. The team accepted `System.CommandLine` beta usage and contained the warning surface rather than blocking the epic.
- Scope pressure recurred. Several stories had to state what did not ship, especially full command implementations, rich quickstart cleanup, and telemetry storage beyond structured logs.
- The CLI contract grew quickly. Output formatters, JSON envelopes, error envelopes, and telemetry summary payloads introduced multiple schema surfaces that must be protected from drift.
- Some parsing and transport edge cases remain deferred: non-integer parser errors, subpath endpoint handling, formatter cancellation, encoded path segment IDs, and non-finite scores.
- Quickstart exposed server-contract reality. `CreateTenantAsync`, `CreateCaseAsync`, and `IngestAsync` support the wizard, but workflow-id and polling semantics diverged from early story wording. The implementation is more honest than the first spec, but the spec needs reconciliation.
- Several quickstart edge cases remain low-risk but named: dual-stack port checks, stable case selection after repeated failed runs, raw probe-error suggestions, and client-side ingest content-size guard.
- Telemetry proof needed a follow-on. Story 7.5 had substrate coverage, then Epic 8 stories supplied stronger Tier-2 and Tier-3 evidence for trace and audit behavior.

## Key Insights

1. A developer tool needs contracts as much as code. CLI output, errors, exit codes, and JSON envelopes are public API.
2. Bridge behavior must have a single owner. Story 7.1 and 7.2 temporary messages were explicitly replaced by richer 7.3 handling, avoiding duplicate or contradictory UX.
3. Quickstart should isolate failure origin. The useful part is not that it runs a happy path; it tells the developer which subsystem failed and what to try next.
4. Telemetry claims need topology evidence. Unit and substrate tests are necessary, but trace propagation and audit logs are only truly credible when exercised through the deployed shape.
5. Documentation is a runtime support surface for a CLI product. Config, formatting, quickstart, telemetry, and experimental API docs reduce support load and prevent ambiguous usage.

## Significant Discovery Check

No Epic 7 discovery requires changing the direction of Epic 8. Epic 8 was the correct follow-on and is already complete.

The significant carry-forward is narrower: Epic 7 introduced public CLI contracts that future work must treat as compatibility surfaces. The biggest risk is not missing functionality; it is accidental drift in command output, JSON envelopes, exit codes, and telemetry schema.

Amelia (Developer): "Epic update required: no."

Winston (System Architect): "Contract-drift prevention required: yes. That is the real carry-forward."

## Commitments

- Treat CLI output and exit behavior as public API.
- Keep JSON schemas additive unless a deliberate compatibility break is recorded.
- Replace bridge UX in the story that owns the final behavior.
- Keep quickstart support APIs marked experimental until first-class CLI commands consume them.
- Require executable evidence for telemetry and audit claims.
- Keep deferred work visible instead of burying it in story notes.
