# Story 5.3: Tenant Isolation Verification

Status: done

## Story

As an operator,
I want to run automated tenant isolation checks,
so that I can verify zero cross-tenant data leakage with confidence.

## Acceptance Criteria

1. **Given** two tenants (A and B) each with indexed memory units, **when** I run `tenant verify` on tenant A (FR40), **then** automated checks confirm:
    - Search from tenant A context returns zero results from tenant B across all axes (syntactic, semantic, graph)
    - Ingestion into tenant A is not visible from tenant B's context
    - Graph traversal from tenant A returns zero nodes from tenant B

2. **Given** identical graph structures created in tenant A and tenant B, **when** traversal is executed from tenant A, **then** zero nodes from tenant B appear even if edge IDs collide (NFR8)

3. **Given** malformed, empty, or swapped tenant IDs, **when** used in search, ingestion, or graph traversal requests, **then** the system rejects them with clear error messages — never falls through to a default tenant or cross-tenant access

4. **Given** a verification run completes, **when** results are returned, **then** they include per-check pass/fail status with details for any failures

### Architecture Compliance

- **NFR8 (Hard Gate):** This story implements the verification side of the zero cross-tenant data leakage gate. The verification must cover all three axes: syntactic (RediSearch), semantic (Redis Vector), graph (FalkorDB).
- **Physical isolation model:** RediSearch/Redis Vector use tenant-namespaced indexes (`{tenantId}:memories:idx`, `{tenantId}:memories:vec`). FalkorDB uses **separate databases per tenant** (not label/namespace separation). This means graph isolation is at the connection level, not the query level.
- **D9 (`IGraphQueryBuilder`):** All Cypher data queries MUST go through `IGraphQueryBuilder` — no raw Cypher string construction. However, `GRAPH.LIST` is a Redis infrastructure command (not a Cypher query) and is executed directly via `IConnectionMultiplexer` — this does not violate D9.
- **D1 (FalkorDB):** FalkorDB isolation is database-level. Graph nodes do NOT have a `tenantId` property — there is no need for one within a physically isolated graph. Isolation verification must be structural: confirm separate databases exist via `GRAPH.LIST`, not by searching for foreign `tenantId` values on nodes.

### Verification Strategy

The `TenantIsolationVerifier` is a **diagnostic tool that confirms architectural guarantees hold** — it does not enforce isolation at runtime. Isolation is enforced by the architecture itself (physically separate indexes and databases). If the verifier ever reports a failure, it means the architecture has a bug. Do NOT over-engineer this as middleware, a guard, or a continuous enforcement mechanism.

The verifier does **proactive cross-tenant leakage detection**, not just "are my indexes there" checks. The verification must:

1. **Find all other tenants** via `TenantRegistryService.ListTenantsAsync`
2. **For each other tenant**, check that:
    - No data from the target tenant appears in their indexes
    - No data from them appears in the target tenant's indexes
3. **Test connection-path isolation** by attempting `GRAPH.QUERY {otherTenantId}` on the tenant's FalkorDB connection — must fail or return empty
4. **Detect orphaned infrastructure** by comparing `GRAPH.LIST` against the tenant registry — flag unregistered databases
5. **Validate input boundaries** by attempting operations with known-bad tenant IDs
6. **Report per-check results** with timing for operator visibility

This is distinct from `VerifyTenantActivity` (which just confirms indexes exist post-provisioning).

**Scope boundary:** This story verifies **data isolation outcomes** — that data ends up in the correct tenant's indexes after ingestion. It does NOT verify that the ingestion API rejects cross-tenant write requests (that's endpoint-level enforcement in Story 5-4). AC #1's "ingestion into tenant A is not visible from tenant B's context" is validated by checking index contents, not by testing API rejection behavior.

### Edge Cases

- **Single tenant:** If only one tenant exists, cross-tenant checks cannot run. Report as `"Skipped — no other tenants to check against"` rather than silently passing. Index existence, input validation, and orphaned database checks still run.
- **Empty tenant:** A tenant with zero memory units will pass all cross-checks vacuously. Include `Details: "Tenant has zero indexed memory units — isolation checks are vacuously true"` so the operator knows the check was not meaningfully exercised.

### Known MVP Limitations

- **Scalability:** Cross-tenant checks are O(n) per tenant verified (checking against all other tenants). For the MVP target of 10 tenants (NFR12), this is acceptable. For deployments with 100+ tenants, a sampling strategy or tenant-pair limit should be added in a future enhancement.
- **Unauthenticated endpoint:** `POST /api/tenants/{tenantId}/verify` has no authentication (D8 defers `TenantAuthorizationMiddleware` to Phase 1.5). Any caller can trigger verification on any tenant and enumerate all tenant IDs via cross-check results. Acceptable for MVP since the API is not externally exposed, but must be addressed in Phase 1.5.
