### B. Spec-to-implementation reconciliation and Production-live code

**B1 — A configuration key silently disables the Dapr app-token check in Production.** *Verified; all 3 lenses flagged
it.*

- Commit `32fc400e` (2026-09-08, "Isolate Dapr application-token checks from process environment") was a
  test-isolation fix landed with access-telemetry integration test support.
- It made `DaprApplicationTokenMiddleware.ResolveExpectedAppApiToken` (`:107-115`) honor
  `Hexalith:Dapr:ApplicationTokenOverride` in **every** environment. A present but empty value makes the expected token
  blank, and the middleware then calls `next()` without checking (`:47-52`).
- `DaprTokenStartupValidator.cs:24-25` still checks only the `APP_API_TOKEN` environment variable. So a single
  `Hexalith__Dapr__ApplicationTokenOverride=` passes the Production fail-closed startup guard and turns off the check on
  every non-probe route.
- The middleware also walks the whole configuration tree (`AsEnumerable()`, `:79-92`) on every request.
- No test covers Production with the override (`DaprTokenStartupValidatorTests.cs:25,35,45`).

**Instance:** fix now (item 1). **Prevention:** a test-only seam added to shared security middleware needs an
environment guard and a Production negative test in the same change.

**B2 — The A41 accepted-debt record understates what Production telemetry carries.** *Verified.*

- The scope reset made JSON-console/OTLP the only Production access-telemetry route. DW-17's risk statement and the
  runbook (`docs/operations/access-telemetry-lifecycle.md`, "Production access-telemetry retention") describe it as
  carrying "the tenant, user and operation fields of `AccessTelemetryEvent`".
- In fact the search event's typed state carries the raw `query` and `subject` (`SearchEndpoints.cs:129,135`). The ADR
  records this (`adr-27.1-001…md:52-54`), and so does open DW-578 (decision 2026-09-01 "Sanitize before fan-out"), but
  neither DW-17, DW-730 nor the runbook mentions DW-578.
- The built-in JSON console renders `@AuditEvent` through record `ToString()`, so the values are not recoverable there
  (ADR `:49-50`). A destructuring provider an operator adds after following the runbook's routing recipe would serialize
  them.

So this is a disclosure inaccuracy, not a confirmed leak. **Instance:** fix now (item 4). **Prevention:** an
accepted-debt record must list the open DW entries in its own scope.

**B3 — The "disabled" Production overlay still deploys lifecycle infrastructure.** *Verified by rendering the
overlay; adversarial and edge-case lenses.*

- The render includes the `access-telemetry-postgresql` StatefulSet at `replicas: 1`, requesting 4 CPU and 8Gi, with a
  400Gi `data` PVC and a PodDisruptionBudget with `minAvailable: 1`.
- The `access-telemetry-secrets` (`secretstores.hashicorp.vault`) and `access-telemetry-config`
  (`configuration.redis`) Dapr components are scoped to the Server app-id `memories`, with no `ignoreErrors`. The Server
  sidecar's startup therefore depends on the disabled feature's bootstrap secret and KV entries.
- DW-17 compensating control 2 says only "lifecycle `replicas: 0`". That is true for the two Deployments, not for the
  StatefulSet.
- Every release attaches this render as `artifacts/deployment/hexalith-memories-production.yaml` (`.releaserc.json`).

**Instance:** fix now (item 2).

**B4 — One OpenBao token is shared across the Server, lifecycle and clock sidecars.** *Verified for the manifests;
the OpenBao policy scope is plausible only.*

- `access-telemetry-secrets` uses one `vaultToken` from `openbao-access-telemetry-bootstrap` and one KV prefix
  (`hexalith/memories/access-telemetry`), scoped to all three apps.
- The rendered Role `memories-dapr-secret-reader` (bound to SA `memories`) can `get` that secret.
- The clock reads `access-telemetry-clock-key` through the same component; its `allowedSecrets` filters only
  sidecar-mediated reads.
- This is wider than the writer authority in the ADR table (`adr…:157`; reconciliation boundary item 4).

**Instance:** remove the Server's `get` on the secret now with item 2. Per-app tokens go to the DW-730 pre-enablement
register (item 6).

**B6 — Disabling the lifecycle also halts purge, contrary to the ADR's rollback design.** *Verified.*

- The ADR rollback row says to "Disable the provider while the Dapr lifecycle service and actor continue expiring
  retained records".
- `AccessTelemetryLifecycleActor.PurgeAsync` (`:307-325`) returns early when `IsPurgeEnabled` (`:371-379`) reads

- The lifecycle Deployment binds that key to the same ConfigMap value as the Server
  (`access-telemetry-deployments.yaml:69-73`), so the documented rollback switch stops expiry. That is the
  unbounded-retention failure A41 exists to prevent.
- The change arrived in `450445a6` (2026-10-11, "build: sync local changes via /pushall"), with no story or spec.
  `ExistingReminder_Disabled_PreservesDueRecordUntilReenabled` asserts the new behavior.

No retained Production records exist today. **Instance:** defer as a blocking pre-enablement defect (item 6), and
record the contradiction in the ADR (item 5).

### C. Enabled-path defects (pre-enablement register)

**C1 — Defects that only matter once lifecycle writes are enabled.** *Plausible (lens or agent reports, not each
re-verified).* They need a home that the DW-730 reopen trigger will surface:

- One transient absent `retentionSeconds` read after the first validation becomes a permanent terminal state
  (`AccessTelemetryLifecycleBootstrapService.cs:44-79`).
- In the delivery worker, `RemoveWhere` / `PeekBatch` run outside the guarded try, so a fault can stop the host under
  `StopHost` (`AccessTelemetryDeliveryWorker.cs:58-84`; three lenses).
- The logger's catch-all is never exercised by a test (`AccessTelemetryLifecycleLogger.cs:141`).
- Future clock skew marks the whole processor Unhealthy and poisons later batches (`AccessTelemetryLifecycleProcessor`
  `:102-110`; reconciliation item 2).
- The first failing record rejects the rest of the batch (actor `:164-168`).
- `ClockRefreshInterval` and `ClockEvidenceLifetime` are validated but unused, so every batch makes its own attest call.
- The retention configuration store uses the Server's own `redis-secret`, so the writer can rewrite its own retention.
- The validator keys Production rules on the literal name `Production`.
- A non-base64 `AttestationVerificationKey` passes validation.
- The Dapr `HttpClient` timeout (100 s default) exceeds the 30 s writer lease.
- Qualification accounting, gate and runner code is registered on the Production path
  (`MemoriesServerServiceCollectionExtensions.cs:544-548`).
- Records left after the 5 s shutdown flush are dropped without being counted.
- Health states, the `expired` state and the purge-cohort checkpoint diverge from the ADR (reconciliation items 6, 7
  and 9). The physical-reclamation evidence endpoint sits inside the app API (item 10).
- B6, B10 and the B4 per-app tokens also belong in this register.
