## What Went Well

1. The axes were implemented incrementally.
   Story 2.1 established the common search contracts and BM25 endpoint. Story 2.2 added semantic KNN behind the same endpoint. Story 2.3 added graph traversal and graph-scoped inner search without forcing a premature generic abstraction.

2. Tenant and case isolation were treated as first-class search concerns.
   Syntactic, semantic, and graph stories added tenant isolation coverage. Story 2.1 also hardened RediSearch query and CaseId injection scenarios.

3. Score normalization became a small, testable core.
   Story 2.4 created pure normalization functions for BM25, cosine similarity, and graph proximity, then put corpus statistics behind a DAPR actor. This gave fusion a defensible contract instead of mixing raw axis scores.

4. Hybrid search degraded explicitly.
   Story 2.5 captured unavailable axes, treated prerequisite lookup failures as degraded axis failures, preserved cancellation, and avoided pre-fusion axis pagination. That made partial results visible instead of silently wrong.

5. Explain mode made the search result inspectable.
   Story 2.6 added `SearchExplanation` and `AxisExplanation`, wired `explain=true` through all endpoint branches, and fixed hybrid explanations so they describe axes that actually executed.

6. The benchmark suite found real product issues.
   Story 2.7 exposed the fusion re-normalization bias and the weak BM25 behavior for natural-language prompts. The fixes improved production search semantics, not only test fixtures.

7. Review findings were usually resolved into stronger invariants.
   The story records show patches for endpoint error payloads, enrichment completeness, graph pagination semantics, corpus-stat handling, degradation metadata, benchmark leakage, deterministic traversal, and stale-only axis behavior.

## Challenges

1. Benchmark correctness required multiple hardening passes.
   The first benchmark implementation needed fixes to avoid answer-key-derived semantic vectors, graph traversal through the case hub, non-production corpus stats, and weak smoke validation. The final result is stronger because review challenged the measurement itself.

2. Fusion semantics were more subtle than expected.
   The benchmark revealed that treating missing active-axis scores as absent rather than zero diluted multi-axis wins and over-rewarded single-axis documents. Zero-imputation inside fusion fixed the thesis gate while preserving public null semantics for axes that did not return a unit.

3. Natural-language BM25 behavior remains a policy area.
   Story 2.7 accepted OR-based token matching for sentence-style queries, but two review patches remain unresolved in the story file: the natural-language detection threshold cliff and stopword dilution. These are design decisions, not simple patches.

4. Pagination metadata is still incomplete.
   Story 2.6 deferred returning `offset` and `maxResults` in search response envelopes. This is now tracked in `deferred-work.md` and affects both `SearchResult` and `HybridSearchResult`.

5. CaseId validation is still not fully canonical.
   Epic 2 improved query escaping and injection prevention, but the broader CaseId format rule from the Epic 1 retro remains only partially addressed. Later case and metadata search stories also record related validation concerns.

6. Some tests validate MVP-scale behavior rather than full target conditions.
   Story 2.2 records that the semantic latency smoke test used a smaller seeded corpus than the formal acceptance target. This is acceptable as a smoke check, but it should not be mistaken for full performance evidence.

## Key Lessons

1. A benchmark is production code if it drives product direction.
   The benchmark suite needed the same review rigor as runtime code because it decided whether the three-axis thesis passed.

2. Explainability is not just a UI feature.
   Per-axis metadata helped make degraded, skipped, and fused results understandable. That is essential for trust in hybrid retrieval.

3. Missing-axis semantics must be explicit.
   There is a meaningful difference between "axis not requested," "axis unavailable," "axis returned no hits," and "axis returned stale-only hits." Epic 2 improved this distinction.

4. Query policy belongs in named rules, not heuristics hidden in code.
   Natural-language BM25 behavior should have a documented retrieval policy so future changes do not accidentally retune the product.

5. Case filtering spans product, security, and storage concerns.
   CaseId handling affects RediSearch TAG filters, Redis keys, graph edges, and later case ownership. It needs one canonical rule.

## Epic 3 Preview

Epic 3 is "Case Management & Memory Organization." It builds directly on Epic 2 search results by adding case creation, case status, membership, case-scoped and cross-case search, deletion, and annotations.

Dependencies from Epic 2:

- The `/api/search` route already accepts case-aware search inputs.
- Syntactic and semantic services already understand CaseId filters.
- Graph search already relies on `Case -[CONTAINS]-> MemoryUnit` relationships.
- Hybrid search and explain mode need to preserve case attribution once Epic 3 adds richer case metadata.
- Metadata filters in Story 3.4 will extend the same endpoint surface that Epic 2 hardened.

Preparation needs for Epic 3:

- Define the canonical CaseId format before adding more case operations.
- Ensure case existence checks happen before search returns ambiguous empty results.
- Keep all axes aligned on case filtering semantics.
- Decide how case attribution appears in both single-axis and hybrid response contracts.
- Ensure deletion stories remove all Redis, vector, graph, activity, membership, and dedup-related state consistently.

## Significant Discovery

Epic update recommended: yes, narrowly.

Reason: Epic 2 validated the three-axis thesis, but it also exposed search behavior decisions that should be explicit before future search and case work depends on them.

Recommended planning updates:

1. Document the natural-language BM25 retrieval policy, including threshold and stopword behavior.
2. Update search response contracts to include pagination slice metadata.
3. Establish a single CaseId validation rule before expanding case operations.
4. Add a note that benchmark-driven changes to production search semantics are allowed only when the benchmark measurement itself is reviewed.
5. Keep the Gate 1 result as passed at 87.5% hybrid win rate, while recording BQ-07 as the remaining graph-favored adversarial calibration query.
