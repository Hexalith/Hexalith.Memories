## What Went Well

1. The CI surface became explicit and stable.

   The repository now has stable check names for `build`, `test-unit-contract`, and `integration-fast`. That gives branch protection concrete handles instead of vague "CI should pass" language.

2. Test selection moved to shared inventories.

   `tools/test-projects.unit-contract.txt`, `tools/test-projects.integration-fast.txt`, and related scripts reduced hand-maintained drift between PowerShell, Bash, and workflow YAML. `CiTestInventoryTests` gives that contract an executable guard.

3. The integration lane became meaningful.

   Story 11.1 did not accept a broad command as proof. It mapped ingestion, search axes, tenant isolation, telemetry, and MCP coverage to concrete integration tests and added a verifier for required surfaces.

4. Package publication became deliberate.

   Story 11.2 reconciled the stale PRD package list with actual project reality. The approved package set is seven packages: `Contracts`, `Client.Rest`, `Redis`, `Cli`, `Mcp`, `EventStore`, and `Telemetry`.

5. Release packaging was hardened during review.

   The build-once, pack-many design in `tools/pack-release.ps1` removed a real diamond-dependency metadata risk. Package validation now checks package identity case-sensitively and parses NuGet bracket ranges strictly.

6. The bundled review caught cross-story drift.

   Reviewing 11.1 and 11.2 together surfaced issues that lived between story boundaries: action-version divergence, release-test inventory drift, release workflow permissions, artifact upload tolerance, and shared script behavior.

7. External maintainer work became visible.

   The `External Action Pending` header on Story 11.1 makes branch protection status honest. The same pattern now informs Epic 12 Story 12.1 for branch protection and `NUGET_API_KEY`.

## Challenges

1. Story file-scope discipline was enforced by review, not tooling.

   Story 11.2 warned against runtime `.cs` changes unless package boundaries required them. The bundled work still included runtime stabilization changes, and D5 had to force explicit anchoring after the fact. The work was useful, but the guardrail was manual.

2. Pre-existing test failures had accumulated under script-only execution.

   Epic 11 found inherited red tests while creating the first reliable automated signal. Three were fixed; `EmbeddingInputContentKindTests.ContentKind_PropagatesToEmbeddingApiCallsMetricTag` remains tracked as S11-FA.

3. Tolerant defaults repeatedly hid failure.

   The review found several variants of the same shape: process-substitution exit-code swallowing, artifact upload ignoring missing files, partial-publish self-healing without a strong alert, and per-row zero-count verifier behavior. These are governance issues, not isolated syntax mistakes.

4. Sibling files drifted quickly.

   `release.yml` and `ci.yml` had different action major versions. `test-release.ps1` drifted from the shared test inventory. Package validation used a case-insensitive comparison where case matters permanently once packages are published.

5. "Done" and "externally enforced" are different states.

   Story 11.1 can document branch protection completely, but only a repository maintainer can apply it in GitHub settings. Story status needed a way to show that distinction without pretending code could enforce it.

6. The first release still has not proven the pipeline end to end.

   Epic 11 built the mechanism. Epic 12 is where the mechanism must be exercised against a real release event with branch protection and NuGet credentials in place.

## Key Insights

1. CI is a repository truth signal, not just convenience automation.

   The project had strong local practices, but baseline failures still accumulated when the authoritative green signal lived outside repository state. Epic 11 converts that into a visible, reviewable contract.

2. Infrastructure stories need adversarial review across shared files.

   When two stories share workflows, scripts, and contributor docs, reviewing them separately misses the behavior between them. The bundled review approach should remain the default for coupled infrastructure changes.

3. Tolerance needs a written policy.

   "Ignore missing artifacts," "skip duplicates," "default to everything," and "accept zero executed tests" can all be useful in narrow contexts. Without explicit proof and alerting, they create green-but-broken pipelines.

4. External-action dependencies need first-class status.

   Branch protection and `NUGET_API_KEY` are not repository edits, but they are still release blockers. The `External Action Pending` pattern should be reused for any acceptance criterion whose final enforcement lives outside the repo.

5. Epic 12 is not feature expansion.

   The current next epic exists to prove the release path, operationalize Epic 11 lessons, and clean up the strongest process risks before Phase 2 or a maintenance pivot is decided.

## Team Agreements

- Coupled infrastructure stories should be reviewed as a bundled diff when they share workflows, scripts, or contributor documentation.
- `External Action Pending` is the standard marker for acceptance criteria whose final enforcement happens outside repository files.
- Story file scope is a contract. Deviations need explicit completion-note anchoring or a `Scope-Override:` style explanation.
- Tolerant defaults must either be justified by idempotency proof, paired with an alert, or rejected during review.
- Release-readiness work should prove behavior from the actual pipeline rather than relying on documentation alone.
