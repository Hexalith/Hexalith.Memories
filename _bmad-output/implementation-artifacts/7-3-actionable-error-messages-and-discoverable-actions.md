# Story 7.3: Actionable Error Messages & Discoverable Actions

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## TL;DR

**What ships:** the **actionable-error and discoverable-action surface** for the `memories` CLI (FR56, FR57). Replaces 7.1's single "plumbing-everything-is-exit-2" failure path with a tiered model that (a) maps every server `ErrorResponse.Code` to a CLI-side **recovery suggestion** when the server's own `Suggestion` field is missing or generic, (b) splits domain errors (`TENANT_NOT_FOUND`, `CASE_NOT_FOUND`, `MEMORY_UNIT_NOT_FOUND`, `INVALID_INPUT`, etc.) onto **exit code 1** while keeping plumbing errors (transport failure, bad URI, TLS) on **exit code 2** — finally activating the `CliExitCodes.DomainError` slot 7.1 reserved, (c) prints contextual **next-action nudges** in empty states (zero search results, zero tenants, zero cases), and (d) wraps every error in the JSON envelope's new `error` slot with shape `{ "code", "message", "suggestion" }` per ADR-7.2-001's additive policy. Also rewrites 7.2's bridge degradation notice (`HybridSearchResult` `Degraded == true`) into the full FR56 surface — per-axis recovery suggestions instead of a bare "axes unavailable" line.

In practice this story adds five things to the repo:

1. **Error-translation table** in `src/Hexalith.Memories.Cli/Errors/ErrorMessageCatalog.cs`:
    - One static `IReadOnlyDictionary<string, ErrorTranslation>` keyed by server error code.
    - Each entry: `(string CliMessage, string CliSuggestion, int ExitCode)`. **`CliMessage` is null when the server's `Message` is already the right human surface** — the catalog only overrides when the CLI can do better than the server's text.
    - Codes covered (drawn from server grep — see References): `TENANT_NOT_FOUND` (exit 1, suggest `memories tenant list`), `CASE_NOT_FOUND` (exit 1, suggest `memories case list --tenant <id>`), `MEMORY_UNIT_NOT_FOUND` / `MEMORY_UNIT_NOT_INDEXED` (exit 1), `CASE_MISMATCH` (exit 1), `INVALID_TENANT_ID` / `INVALID_INPUT` / `INVALID_REQUEST` / `INVALID_CONFIG` / `INVALID_AXIS` / `INVALID_URL` / `INVALID_DIRECTORY_PATH` / `INVALID_SOURCE_TYPE` / `INVALID_DIMENSIONS` / `INVALID_CONFIDENCE` / `INVALID_EDGE_TYPE` / `INVALID_MEMBER_TYPE` / `INVALID_MEMBER_INPUT` / `INVALID_REQUEST_BODY` (exit 1), `MISSING_*` family (exit 1), `MEMBER_NOT_FOUND` / `MEMBER_LIMIT_EXCEEDED` / `EDGE_NOT_FOUND` / `BATCH_NOT_FOUND` / `BATCH_TOO_LARGE` / `DELETION_STATUS_NOT_FOUND` / `PROVISIONING_STATUS_NOT_FOUND` (exit 1), `NESTED_ANNOTATION_NOT_ALLOWED` / `RE_INGESTION_IN_PROGRESS` / `DIRECTORY_INGESTION_DISABLED` (exit 1), `TENANT_DELETING` / `TENANT_PROVISIONING` / `TENANT_FAILED` / `TENANT_UNAVAILABLE` (exit 1, suggest waiting + `memories tenant status`), `DAPR_UNAVAILABLE` / `BACKEND_UNAVAILABLE` / `GRAPH_UNAVAILABLE` / `ALL_BACKENDS_UNAVAILABLE` / `BATCH_TRACKING_UNAVAILABLE` / `BATCH_SCHEDULING_FAILED` (exit 2, server-side infrastructure plumbing), `HTTP_*` synthetic codes from `ErrorResponseDecoder` (exit 2 — the server didn't return a proper error envelope).
    - **Unknown codes** (anything not in the table) fall through to a default `(null, "Run with --verbose for diagnostic detail.", ExitCode = 1)` — defaults to **domain error** because the server returned a structured `ErrorResponse`. Pure plumbing always lands in exit code 2 via `CliCommandExecutor`'s typed exception catches, never via this catalog.

2. **`CliCommandExecutor` rewrite** in `src/Hexalith.Memories.Cli/Execution/CliCommandExecutor.cs`:
    - The single `MemoriesRemoteException` catch (`CliCommandExecutor.cs:104-112`) now consults `ErrorMessageCatalog` and emits the resolved `(message, suggestion, exitCode)` instead of the current `"Memories Server at {endpoint} returned an error: {Code} - {Message}"` line.
    - The transport-failure catches (`HttpRequestException`, `SocketException`, `AuthenticationException`, `TaskCanceledException`-as-timeout, `UriFormatException`) **expand** to include the full FR56 connection-failure message: `"Cannot connect to Memories Server at {endpoint}. Is the service running? Try: dotnet run --project Hexalith.Memories.AppHost"` (exact phrasing from epics.md AC #1 below). Confirmed AppHost project name: `src/Hexalith.Memories.AppHost/Hexalith.Memories.AppHost.csproj`.
    - The `Unexpected error` outermost catch keeps exit code 2 — anything we can't classify is plumbing, not domain.
    - All error output continues to go through `_console.Error` (stderr); stdout remains reserved for command success output.
    - **JSON-error mode hand-off:** when `_console.Format == OutputFormat.Json`, the executor emits the error as a JSON envelope on **stdout** instead of a plain-text line on stderr — per AC #4 below. This keeps `memories ... --format json 2>/dev/null | jq` workable for scripts that route stderr away.

3. **JSON envelope `error` slot** in `src/Hexalith.Memories.Cli/Output/Json/CliOutputEnvelope.cs`:
    - The envelope record gains a fourth optional field: `CliErrorPayload? Error`. With `JsonIgnoreCondition.WhenWritingNull` already set on `CliJsonContext`, success responses still emit only `{ schemaVersion, command, data }` — the `error` field is invisible unless set. Per ADR-7.2-001 deprecation policy this is **additive** → stays on `schemaVersion = 1`.
    - New record `CliErrorPayload(string Code, string Message, string Suggestion)`. Identical shape to the FR56-mandated structure `{"code", "message", "suggestion"}` and matches `Hexalith.Memories.Contracts.V1.ErrorResponse` field-for-field. **Do not** reuse `ErrorResponse` directly — the envelope payload is a CLI-projection (translated message + suggestion), not the raw server payload; reusing creates ambiguity about which layer owns the wording.
    - When `Error` is non-null, `Data` must be `default`/`null` for that envelope; the source-gen context handles the optionality. JSON-mode error responses look like `{ "schemaVersion": 1, "command": "search query", "error": { "code": "TENANT_NOT_FOUND", "message": "...", "suggestion": "Run 'memories tenant list' to see available tenants." } }`.
    - Add new entry to `CliJsonContext.cs:25` source-generation list: `[JsonSerializable(typeof(CliErrorPayload))]` so AOT-safe serialization keeps working.

4. **Empty-state nudges** in the existing per-format formatters (FR57). All formatters live in `src/Hexalith.Memories.Cli/Output/Formatters/` and ship in 7.2:
    - `HybridSearchResultHumanFormatter` — when `Results.Count == 0`, print the **PRD-mandated** empty-state line verbatim (`prd.md:364`): `"No results. This tenant has no memory units yet. Get started: 'memories ingest <file>' to add your first document, or configure a DAPR subscription to auto-index events. Run 'memories quickstart' for a guided setup."` **However**, this exact message is correct **only when the tenant truly has no memory units**. The CLI cannot tell whether the empty result is "no memory units in tenant" vs "no matches for this query" from a single search response alone. **Resolution:** print a softer query-specific nudge by default (`"No results matched the query. Try broader terms, omit --case to widen scope, or run 'memories search inspect' on a known id to confirm indexing."`) and reserve the PRD-verbatim "tenant has no memory units yet" line for the case where `--query` was empty AND `--axis graph` (i.e., no query at all → the tenant must be empty for nothing to come back). See AC #2 below for the precise decision tree.
    - `SearchResultHumanFormatter` (single-axis) — same empty-state nudge logic as hybrid.
    - `TenantListHumanFormatter` — when `value.Count == 0`, the formatter's existing 7.2 line `"No tenants found."` is **kept byte-for-byte** (preserves ADR-7.2-002). The handler **appends a second line** AFTER the formatter writes: `"Get started: 'memories tenant create --id <id> --display-name <name>' to provision your first tenant, or run 'memories quickstart' for a guided setup."` Final output is two lines: line 1 (`No tenants found.`) preserves 7.2 contract for any consumer's `grep -q "No tenants"` check; line 2 delivers FR57 nudge. **Zero 7.2 test churn** — `TenantListFormatterTests` empty-result assertion stays unchanged (Revision 0.3 fix — see Risk #4 resolution below).
    - **Table formatters** keep their 7.2 behavior (header + separator only, no nudge text) — table format is interactive-only per 7.2 docs, and adding stderr nudges to a stdout table breaks alignment for piped consumers. The nudge appears on **stderr** for table format. AC #2 below pins this exact split.
    - **JSON formatters** keep their 7.2 behavior — empty-result JSON envelopes already serialize as `{ "data": { "results": [] } }`, which is stable and parseable. Empty-state nudges in JSON would force scripts to grep the envelope for advice text — worse UX. JSON consumers detect emptiness by `data.results.length === 0`.

5. **Degradation notice rewrite** in `HybridSearchResultHumanFormatter` and `HybridSearchResultTableFormatter`. The 7.2 Task 6.6a single-line bridge (`"Note: search degraded — axes unavailable: ..."`) is **deleted** and replaced with the full FR56 actionable surface:
    - For each axis in `UnavailableAxes`, look up `ErrorMessageCatalog` for an axis-specific guidance entry (axes mapped to per-backend codes: `syntactic` → `BACKEND_UNAVAILABLE` (Redis Stack), `semantic` → `BACKEND_UNAVAILABLE` (Redis Vector), `graph` → `GRAPH_UNAVAILABLE` (FalkorDB)).
    - Emit a single multi-line block on **stderr** before any results: `"Warning: search degraded — partial results only.\n  - <axis> unavailable: <suggestion from catalog>\n  ..."`. Results still print on stdout — degradation is informational, not an error → exit code remains 0 if any results came back.
    - Per 7.2 Task 6.6a explicit note: this story **must delete** the bridge line in the same PR. Anti-pattern #5 below pins it.

- `memories tenant create` and `memories case list` commands — referenced in catalog suggestions for `TENANT_NOT_FOUND` / `CASE_NOT_FOUND`. Same "verify before referencing" rule. `tenant create` will be wired in a later 7.x story; until then suggest `memories tenant list` (which exists since 7.1) or fall back to the server's own suggestion.

- `--explain` rendering changes — owned by 7.2 (caveat verbatim, per-axis normalization). 7.3 does not touch the explain block or its caveat.
- New server endpoints. 7.3 consumes the existing `ErrorResponse` shape from every endpoint as-is. No server diff.

- Renaming or removing any existing JSON field. ADR-7.2-001 forbids it without bumping `schemaVersion`. Adding `error` is purely additive → safe under v1.

**Primary risks:**

1. **Empty-state nudge wording drift from PRD verbatim.** The PRD literally specifies (`prd.md:364`) the "No results. This tenant has no memory units yet..." string. Epics.md AC #2 quotes it. **However**, the PRD wording assumes empty tenant; for empty-query results the wording is wrong (would mislead a user who has 1000 memory units but a typo'd query). Resolution: print PRD-verbatim text only when the empty-result condition truly implies an empty tenant (no `--query`, OR a query plus zero results AND we can verify tenant emptiness). The conservative interpretation — verbatim only when there is no query AND no graph seed — is encoded in AC #2's decision tree. Test must assert PRD-verbatim text when applicable AND assert softer wording for typo case.
2. **Exit-code split breaks 7.2 integration tests.** 7.2's `CliSearchIntegrationTests` and any 7.1 test that asserts `exitCode == 2` for a server-reported error (e.g., 404 case-not-found) will break the moment domain errors flip to exit code 1. **Audit before merging:** grep all `Cli.Tests` and `IntegrationTests` for assertions on `exitCode`, `Plumbing`, or literal `2` near a non-transport error path; update each to `DomainError` (1) where the underlying failure is domain. Don't blanket-replace — transport errors stay 2.
3. **Unknown server error codes default to exit 1, not 2.** A new server error code added in a future story (e.g., Epic 8's `INDEX_INTEGRITY_ERROR`) will land in the catalog's "unknown" bucket and exit 1. This is the **right** default — structured `ErrorResponse` from server = domain — but means the dev agent of the future story must decide whether their new code is genuinely a domain error or a plumbing concern, and add an explicit catalog entry if the latter. Documented in the catalog file's class-level XML doc as a contributor note.
4. **~~Breaking 7.2's "No tenants found." string.~~** **RESOLVED in Revision 0.3** via append-not-replace: the formatter's `"No tenants found."` line is kept verbatim; the handler appends a second nudge line after the formatter writes. Final output is two lines — line 1 preserves the 7.2 contract for any `grep -q "No tenants"` consumer; line 2 delivers FR57. ADR-7.2-002 byte-for-byte parity holds. **Zero 7.2 test churn** — `TenantListFormatterTests` empty-result assertion is unchanged. `ConfigShowGoldenFileTests` (the actual ADR-7.2-002 backstop) was already unaffected. The original Risk #4 was avoidable; the append-pattern dissolves it.
5. **Adding `error` to the envelope tempts schema-version drift.** Per ADR-7.2-001 this is additive → safe under v1. The dev agent must NOT take the opportunity to rename `data` to `payload` or switch `command` to a structured object "while we're here" — that would force `schemaVersion = 2`. Anti-pattern #6 below pins it.
6. **Suggestion text references commands that don't exist yet.** Pre-`tenant create`, pre-`case list`, pre-`tenant status` — every catalog suggestion that names a command must be verified against `RootCommandFactory.CommandGroups` and `RootCommandFactory.Build` at implementation time. A suggestion that says "Run `memories case list`" when `case` is still a `NotImplementedCommand` stub leaves the user dead-ended (which is exactly what FR57 forbids). Use the verify-or-fallback rule from "What does NOT ship" point 3 above.

## Story

As a developer,
I want error messages that tell me what went wrong and how to fix it, and helpful guidance at every state,
so that I never feel stuck or confused when using the system.

## Acceptance Criteria

1. **Connection-failure error includes the AppHost recovery hint.**
   **Given** the Memories Server is not running (no process bound to the configured `--endpoint`),
   **When** I run any CLI command (e.g., `memories tenant list`),
   **Then** stderr contains exactly: `"Cannot connect to Memories Server at <endpoint>. Is the service running? Try: dotnet run --project Hexalith.Memories.AppHost"` (PRD/epics-mandated wording)
   **And** the exit code is `2` (plumbing — `CliExitCodes.Plumbing`)
   **And** the message replaces the 7.1 `"Cannot reach Memories Server at <endpoint>. Check that the service is running."` line for `HttpRequestException`, `SocketException`, and the equivalent `TaskCanceledException`-as-timeout path.

2. **Empty-state in search returns context-aware nudge text (FR57).**
   **Given** a successful search request (HTTP 200) that returns zero results,
   **When** I run `memories search query --tenant <id>` with `--format human` and the response satisfies the empty-tenant condition (no `--query` provided AND no `--graph-start-node-id`, i.e., a "give me anything you have" probe),
   **Then** stdout contains the PRD-verbatim line (`prd.md:364`): `"No results. This tenant has no memory units yet. Get started: 'memories ingest <file>' to add your first document, or configure a DAPR subscription to auto-index events. Run 'memories quickstart' for a guided setup."`
   **And** exit code is `0` (empty results are success, not error).

    **Given** the same empty result but a `--query` was provided (i.e., the user typed something),
    **When** the response is rendered,
    **Then** stdout contains the **hybrid nudge** (Revision 0.4 — Feynman finding): `"No results. Either your search terms didn't match anything OR this tenant has no memory units yet. To find out: try broader query terms, omit --case to widen scope, run 'memories search inspect --tenant <id> --case <id> --id <memoryUnitId>' on a known id to confirm indexing, or run 'memories ingest <file>' to add data. Run 'memories quickstart' for a guided setup."`
    **And** exit code is `0`.

    **Why hybrid wording:** the original "softer query-miss nudge" presumed the tenant was non-empty (since the user typed a query). That presumption is unverifiable from a single search response — the tenant might genuinely be empty AND the user typed a hopeful query. A nudge that asserts "your query didn't match" is wrong in the empty-tenant case; a nudge that says "tenant is empty" is wrong in the typo case. The hybrid wording covers both possibilities honestly and lists actions that resolve either condition. Strictly more truthful than either single-presumption variant.

    **Given** `--format json`,
    **When** the response is rendered,
    **Then** stdout contains the 7.2 success envelope `{ "schemaVersion": 1, "command": "search query", "data": { "results": [], ... } }` with **no** nudge text injected — empty-state advice for JSON consumers comes from `data.results.length === 0` inspection by the script, per ADR-7.3-002 below.

    **Given** `--format table`,
    **When** the response is rendered,
    **Then** stdout contains only the 7.2 header + separator (table layout intact for piped tools)
    **And** the appropriate human-format nudge is written to **stderr** (so interactive users still see it; piped consumers can `2>/dev/null`).

3. **Tenant-related errors include error code, message, and recovery suggestion (FR56).**
   **Given** a server response with `ErrorResponse.Code == "TENANT_NOT_FOUND"`,
   **When** the CLI translates the error in human format,
   **Then** stderr contains a multi-line block: `"Error: TENANT_NOT_FOUND\n  <message from server (sanitized)>\n  Suggestion: Run 'memories tenant list' to see available tenants."`
   **And** exit code is `1` (`CliExitCodes.DomainError`)
   **And** the catalog-resolved `Suggestion` overrides the server's `ErrorResponse.Suggestion` only when the catalog entry's `CliSuggestion` is non-null; otherwise the server's suggestion is used verbatim.

    **Given** the same response in `--format json`,
    **When** the CLI translates the error,
    **Then** **stdout** contains exactly one JSON document `{ "schemaVersion": 1, "command": "<name>", "error": { "code": "TENANT_NOT_FOUND", "message": "...", "suggestion": "Run 'memories tenant list' to see available tenants." } }`
    **And** stderr is empty
    **And** exit code is `1`.

4. **Every error condition in `--format json` mode is delivered via the envelope's `error` slot.**
   **Given** any CLI command and any error condition (transport, server-reported, validation),
   **When** I run with `--format json`,
   **Then** the JSON document on stdout matches the schema `{ "schemaVersion": 1, "command": "<name>", "error": { "code": "<CODE>", "message": "<text>", "suggestion": "<text>" } }`
   **And** the envelope contains no `data` field (suppressed via `JsonIgnoreCondition.WhenWritingNull`)
   **And** the JSON parses with `System.Text.Json` default options
   **And** stderr is empty (errors go to stdout in JSON mode so a single `| jq '.error'` works regardless of redirection)
   **And** for transport-layer failures (no server response, hence no `Code`), the synthetic code is one of `CONNECTION_REFUSED`, `REQUEST_TIMEOUT`, `TLS_ERROR`, `INVALID_ENDPOINT`, or `UNEXPECTED_ERROR` — per the synthetic-code table in ADR-7.3-001.

5. **Discoverable next actions are provided contextually for every system state (FR57).**
   **Given** any non-success state (empty result, error response, degraded response),
   **When** the CLI displays output,
   **Then** the message includes at least one concrete next action expressed as a `memories ...` command (or, for the AppHost connection-failure case, a `dotnet run --project ...` command)
   **And** the next-action command is one of: a 7.1/7.2-wired command, a Story 7.4-pending command (`memories quickstart`), or a verified-existing command in the current codebase (no broken or non-existent command references — see Risk #6)
   **And** no error or empty-state output is a "dead end" (no message ends without a next-action hint).

6. **Server degradation (`HybridSearchResult.Degraded == true`) emits per-axis recovery suggestions (FR56 + FR66).**
   **Given** a hybrid search response with `Degraded == true` and `UnavailableAxes` containing one or more axis names (e.g., `["graph"]` or `["syntactic", "semantic"]`),
   **When** the CLI renders the result in human or table format,
   **Then** stderr contains a multi-line block before any results: `"Warning: search degraded — partial results only.\n  - <axis>: <catalog-resolved suggestion>\n  ..."` (one bullet per unavailable axis)
   **And** the suggestions are: graph → `"Retry the request; graph auto-recovers when FalkorDB reconnects. Check infrastructure status."` (mirrors `GRAPH_UNAVAILABLE` server suggestion at `SearchEndpointDegradationResponses.cs:87`); syntactic/semantic → `"Backend recovers automatically; retry shortly. Check Redis Stack connectivity."`
   **And** results still print on stdout, exit code is `0` (degradation with partial results = success, not failure)
   **And** the 7.2 single-line bridge `"Note: search degraded — axes unavailable: <list>"` is **deleted** from `HybridSearchResultHumanFormatter` and `HybridSearchResultTableFormatter` in the same PR.

    **Given** a server response with HTTP 503 + `ErrorResponse.Code == "ALL_BACKENDS_UNAVAILABLE"` (every axis failed → no results possible),
    **When** the CLI translates the error,
    **Then** stderr contains the standard FR56 multi-line block (per AC #3) with the catalog-resolved suggestion `"All backends unavailable. Check infrastructure status (Redis Stack, FalkorDB). The service auto-recovers when backends reconnect; retry the request."`
    **And** exit code is `2` (plumbing — total infrastructure failure, distinct from per-axis degradation).

7. **Domain errors exit `1`; plumbing errors exit `2`; cancellation exits `130`; success exits `0`.**
   **Given** the catalog is consulted for every `MemoriesRemoteException`,
   **When** the resolved `ExitCode` is `1`,
   **Then** the process terminates with exit code `1` (`CliExitCodes.DomainError`).

    **Given** any of the typed transport exceptions (`HttpRequestException`, `SocketException`, `TaskCanceledException`-as-timeout, `AuthenticationException`, `UriFormatException`, the outermost `Exception` catch),
    **When** the executor handles them,
    **Then** the process terminates with exit code `2` (`CliExitCodes.Plumbing`).

    **Given** server-side infrastructure plumbing errors (`DAPR_UNAVAILABLE`, `BACKEND_UNAVAILABLE`, `GRAPH_UNAVAILABLE`, `ALL_BACKENDS_UNAVAILABLE`, `BATCH_TRACKING_UNAVAILABLE`, `BATCH_SCHEDULING_FAILED`, `HTTP_*` synthetic codes from `ErrorResponseDecoder.cs:46`),
    **When** the catalog resolves them,
    **Then** the process terminates with exit code `2` (still plumbing — "the system can't run", not "the user did something wrong").

    **Given** `Ctrl-C` / SIGINT,
    **When** the executor catches `OperationCanceledException` with `ct.IsCancellationRequested == true`,
    **Then** the process terminates with exit code `130` (`CliExitCodes.Cancelled` — unchanged from 7.1).

8. **Catalog mapping is complete for every server error code emitted today.**
   **Given** the inventory of server `ErrorResponse.Code` literals (37 unique codes — see References for the full list grepped from `src/Hexalith.Memories.Server/`),
   **When** the catalog is loaded at app startup,
   **Then** every known code has an explicit entry mapping `(server code → CliMessage?, CliSuggestion, ExitCode)` — no silent fall-through to the "unknown" default for any code that exists in the server today
   **And** the catalog initialization includes a `static` consistency check (compile-time best-effort: a `[Theory]` test that loads every `*ErrorResponse(\"<CODE>\"` literal grepped from server source and asserts the catalog contains that code) — drift detection between server additions and CLI catalog
   **And** unknown-code fall-through (for future server additions before this catalog catches up) defaults to `(message: server's verbatim, suggestion: server's verbatim or "Run with --verbose for diagnostic detail.", exitCode: 1)`.

9. **Tests cover the full error matrix (per-format × per-error-class) and the empty-state decision tree.**
   **Given** the consolidated `tests/Hexalith.Memories.Cli.Tests/` project (Story 7.1 Task 5.1),
   **When** `dotnet test` runs,
   **Then** it includes:
    - one assertion per server error code in the catalog that the CLI translation matches `(message, suggestion, exitCode)` (data-driven `[Theory]`),
    - one connection-failure regression test that asserts the AppHost-hint message exactly (AC #1),
    - one empty-search test per format (human / json / table) for the **empty-tenant** condition (AC #2 PRD-verbatim line),
    - one empty-search test per format for the **typo-query** condition (AC #2 softer line),
    - one empty-search test asserting JSON-mode does NOT inject nudge text (AC #2 JSON branch),
    - one empty-search test asserting table-mode writes nudge to stderr, not stdout (AC #2 table branch),
    - one degradation test asserting the multi-line per-axis block is on stderr and replaces the 7.2 bridge line (AC #6),
    - one JSON-error envelope test per error class asserting `{ schemaVersion, command, error: { code, message, suggestion } }` shape and that `data` is absent (AC #4),
    - one exit-code test per error class asserting `1` (domain), `2` (plumbing), `0` (degradation with partial results), `130` (Ctrl-C — reuse 7.1 fixture)
      **And** the catalog drift test from AC #8 runs in CI as part of the standard suite.

10. **One integration test proves the live error path end-to-end.**
    **Given** the existing `AspireIngestionPipelineFixture` (per 7.1 Task 7.2 / 7.2 Task 10.1),
    **When** `CliErrorMessagesIntegrationTests` runs,
    **Then** it issues `memories search inspect --tenant nonexistent-tenant --case anything --id anything` against the live stack (one `MemoriesClient.GetMemoryUnitAsync` call, no subprocess spawn — per 7.1 anti-pattern #8 / 7.2 Task 10.3) and asserts: server returned `ErrorResponse.Code == "TENANT_NOT_FOUND"` (or `INVALID_TENANT_ID` if the fixture rejects the input upstream), CLI translated message contains `"TENANT_NOT_FOUND"` (or the upstream code), suggestion contains `"memories tenant list"`, exit-code surface is **the catalog-resolved exit code** (`1` for either code per the catalog) — assert against the catalog's value rather than hardcoding `1`, so future catalog tuning doesn't silently break this test
    **And** the test is marked `[Trait("Category", "Integration")]` matching 7.2's pattern (`tests/Hexalith.Memories.IntegrationTests/Cli/CliSearchIntegrationTests.cs:[Trait]`) so dev agents without Docker can filter it out via `dotnet test --filter "Category!=Integration"`.

Document this in the record's class-level XML doc as a hard contract. Enforce via a parameterless static factory pattern OR a constructor-level `Debug.Assert((Data is null) != (Error is null))` (preferred — runtime-checkable in DEBUG builds, zero RELEASE cost). The Roslyn-checkable single-shape design relies on this invariant; pin it.

### New architectural decisions (locked in this story)

**ADR-7.3-001 — Synthetic CLI error codes for transport failures.**

- **Decision:** Transport-level failures (no server response, hence no `ErrorResponse.Code`) get one of five synthetic codes assigned by `CliCommandExecutor`: `CONNECTION_REFUSED` (HttpRequestException, SocketException), `REQUEST_TIMEOUT` (TaskCanceledException-as-timeout), `TLS_ERROR` (AuthenticationException), `INVALID_ENDPOINT` (UriFormatException), `UNEXPECTED_ERROR` (outermost generic catch). Plus `HTTP_<status>` synthetic codes already emitted by `ErrorResponseDecoder.cs:46` for non-JSON 4xx/5xx responses.
- **Rationale:** Without synthetic codes, JSON-mode error envelopes would have no `code` field for transport failures — breaking the AC #4 contract. Synthetic codes give script consumers a stable identifier to switch on (`if (env.error.code === "CONNECTION_REFUSED") retry()`).
- **Naming convention:** `UPPER_SNAKE_CASE`, no namespace prefix (server uses the same convention). Distinguishable from server codes by context (transport-only) and listed exhaustively in `docs/dev/cli-output-formats.md` (Task 10.1).
- **Reconsider at:** If a server code ever collides with a synthetic code (extremely unlikely — server codes are domain-shaped like `TENANT_NOT_FOUND`, synthetic codes are transport-shaped like `CONNECTION_REFUSED`), namespace synthetic codes with a `CLI_` prefix.

**ADR-7.3-002 — JSON-mode errors go to stdout, not stderr.**

- **Decision:** When `--format json` is in effect, error envelopes are written to `console.Out` (stdout). Stderr remains empty for JSON-mode errors. Human and table modes keep the 7.1 convention of writing errors to stderr.
- **Rationale:** The "errors to stderr" convention exists because _unstructured_ output has no other way to separate success-data from error-information — stderr IS the structural channel. JSON mode has its own structural channel: the envelope's `error` slot. Putting the error there AND on stderr would be redundant out-of-band signaling — duplicating what the envelope already conveys. The correct mental model: `--format json` is an opt-in to structured output where channel separation is encoded in the document itself, so stdout becomes the single canonical channel. Stderr separation makes sense for human/table output (one channel for the answer, one for diagnostics); it makes no sense when the "answer" is a JSON document that already has named slots for both states.
- **Trade-off:** A user running `memories ... --format json > out.json` and getting an error gets the error envelope written to `out.json` — not what they'd want from a Unix-shell perspective. Acceptable: their script can either check exit code first (`$?`) or parse `out.json` and detect the `error` key. The exit code is still set correctly per AC #7, so shell error handling (`set -e` or `if [ $? -ne 0 ]`) still works.
- **Recommended script patterns** (document in `docs/dev/cli-output-formats.md` Task 10.1 — closes a `set -o pipefail` + `jq` failure-mode confusion surfaced in the 0.2 review):
    1. **Exit-code-first** (recommended): `memories ... --format json | jq '.data' || { echo "command failed"; exit 1; }`. Check `$?` before parsing — works regardless of which envelope shape (success vs error) was emitted.
    2. **Presence-detection in jq**: `memories ... --format json | jq -e '.data // (.error | error)'` — `jq -e` exits non-zero when the predicate is null; `.data // (.error | error)` returns `data` if present, otherwise raises a jq error containing the `error` envelope. One-line, pipefail-safe.
    3. **Anti-pattern**: `memories ... --format json | jq '.data[]' > out.txt` with `set -o pipefail` — on error, jq sees `.error` only, `.data[]` returns null/iterates nothing, and pipefail surfaces the CLI exit code (`1`) as if it were a parse failure. Confusing failure mode. Use pattern 1 or 2 instead.
- **Reconsider at:** If this convention surprises real users in practice (telemetry from Story 7.5 might surface this), the alternative is to add `--errors-to-stderr` opt-in flag while keeping stdout as the default for JSON errors.
- **Reversibility plan (Revision 0.4 — Shark Tank/Daymond+Mark synthesis):** this contract is shipped without telemetry to validate the choice; the design assumes JSON consumers want stdout+structural-channel separation. If Phase 1.5 telemetry from Story 7.5 contradicts that assumption (e.g., >30% of `--format json` invocations follow the `2>&1 | jq` pattern, suggesting users expected stderr), the contract is reversible without a forced `schemaVersion` bump. Reversal path: (1) add `--errors-to-stderr` opt-in flag to `CliGlobalOptions` (additive — does not change the default for any existing user); (2) once telemetry shows the opt-in is the dominant pattern, flip the default in a coordinated CLI minor-version bump; (3) only if the JSON envelope itself needs to change (e.g., adding an `errorChannel: "stderr" | "stdout"` discovery field) does `schemaVersion` bump per ADR-7.2-001's deprecation window. Document this reversibility path here so future-7.5 (the telemetry owner) doesn't have to reconstruct the original design intent. **Mark Cuban's principle wins now (no premature flagging); Daymond's rigor is preserved (the path is documented so course-correction is cheap when data arrives).**

**ADR-7.3-003 — Domain vs plumbing exit code split.**

- **Decision:** Server-reported `ErrorResponse` (any 4xx with a parseable error body) → exit code `1` (`CliExitCodes.DomainError`). Transport-level failure (no response, bad URI, TLS) OR server-side infrastructure plumbing codes (`DAPR_UNAVAILABLE`, `BACKEND_UNAVAILABLE`, `GRAPH_UNAVAILABLE`, `ALL_BACKENDS_UNAVAILABLE`, `BATCH_TRACKING_UNAVAILABLE`, `BATCH_SCHEDULING_FAILED`, `HTTP_*` synthetic codes) → exit code `2` (`CliExitCodes.Plumbing`). Cancellation → `130`. Success → `0`.
- **Rationale:** The 7.1 + 7.2 baseline emitted `2` for everything-not-success — a CI script couldn't distinguish "the user typo'd a tenant id" from "the network is down." Exit `1` for domain lets CI scripts retry on `2` (transient) but fail-fast on `1` (user input wrong). The `CliExitCodes.DomainError` constant has been reserved since 7.1 (`CliExitCodes.cs:18`) — this story finally activates it.
- **Edge case:** Server-side plumbing codes (`*_UNAVAILABLE`) come down the wire as a `MemoriesRemoteException` (so technically "server-reported"), but they signal "the system can't run" not "the user did something wrong" — so they exit `2`, not `1`. The catalog encodes this distinction explicitly (`ExitCode = 2` for those entries) rather than inferring it from HTTP status (503 vs 4xx).

**ADR-7.3-004 — `ErrorMessageCatalog` is a static class, not a DI service.**

- **Decision:** `ErrorMessageCatalog` is a `public static class` exposing a `public static IReadOnlyDictionary<string, ErrorTranslation> Translations` and a `public static ErrorTranslation Resolve(string code)`. It is NOT registered with DI; there is no `IErrorMessageCatalog` interface; `CliCommandExecutor` and other consumers call the static directly.
- **Rationale:** The catalog has zero state mutation, zero per-tenant configuration, zero swap-out scenarios for production, zero per-environment variation. DI exists to enable runtime-swappable behavior, configuration-driven composition, and per-scope state — none of which apply here. Adding `IErrorMessageCatalog` would cost ~60 LOC (interface, registration, constructor injection in 4+ classes, mock setup in every executor test) and buy zero capability the project will use. The drift test (Task 7.2) calls the static directly; testability is not improved by an interface for code that has no swappable behavior.
- **Consequence:** The `ErrorMessageCatalog` is treated as a constant lookup table — closer to `Math.PI` than to `IConfiguration`. This is the minority pattern in a DI-heavy codebase (most services in `CliServices.cs` are DI-registered), so the choice is non-obvious. **Do NOT refactor this to DI** without a concrete need that doesn't exist today (e.g., per-tenant error catalogs, runtime catalog swapping for A/B testing, or a future MCP server that needs a different translation set). If such a need ever arises, the refactor is mechanical: extract the interface, register the static instance as a singleton implementation, inject. Until then, static is correct.
- **Reconsider at:** Phase 1.5 if MCP requires its own per-protocol error translation, OR if catalog content needs to vary per tenant (low probability), OR if the CLI ever ships a Spectre.Console-like per-environment plugin model.
- **Expectation-setting:** Per-code exit-code classifications in the catalog are **policy decisions tuned in this story**, not a factual mapping derived from server semantics. Edge cases like `RE_INGESTION_IN_PROGRESS` (user asked twice → domain `1`? or server-side concurrency → plumbing `2`?), `MEMBER_LIMIT_EXCEEDED` (user did wrong thing → `1`? or quota-as-infra → `2`?), `BATCH_TOO_LARGE` (input validation → `1`? or capacity → `2`?) are judgment calls. **Expect churn in early Phase 1.5** as operators run real CI scripts and file complaints ("my retry-on-`2` loop spins forever on a `MEMBER_LIMIT_EXCEEDED`"). Pre-warning Story 7.5 + Epic 8 reviewers: catalog tuning is a maintenance activity, not a frozen contract. The catalog drift test (Task 7.2) catches missing codes; it does NOT catch suboptimal exit-code assignments — those need user feedback.
- **Reconsider at:** If a future ecosystem convention (like `sysexits.h`) becomes relevant — but Hexalith isn't a Unix system tool, so adopting `EX_USAGE` (64) etc. would be over-correction. Keep the simple 0/1/2/130 model.

### Trust boundaries (carried forward from 7.2)

The CLI is a **display layer** over server-provided data. Story 7.3 formatters and error translators render `ErrorResponse.Message` (and the catalog's translation thereof) **with token redaction applied** (`SanitizeText` in `CliCommandExecutor`). What is and isn't the CLI's responsibility:

- **CLI-owned (7.3 specific):** Token-sanitization in error messages AND suggestions must work in all three formats — Task 7.7 extends the 7.1 `TokenRedactionTests` containment assertion to cover both fields rendered by `WriteFormattedError`. Catalog suggestions are static text — no user-injected input flows into them — so injection isn't a concern. Server-sourced suggestions (when `ErrorTranslation.CliSuggestion == null` and the catalog falls through to the server's `ErrorResponse.Suggestion`) ARE sanitized via `SanitizeText` symmetrically with messages (Task 3.1 Revision 0.4 fix).
- **NOT CLI-owned:** Server-side error message AND suggestion content. If the server returns `ErrorResponse.Message = "Database connection failed: Server=db.internal; User=root; Pwd=hunter2"` (it shouldn't), the CLI sanitizes only the configured `ApiToken`, not the body. Server-side message hygiene is the server team's problem, not 7.3's. Any DLP concerns about error message or suggestion content should be filed against server stories.
- **`ErrorResponse.Suggestion` content responsibility (Revision 0.4 — Security/Auditor finding):** the server MUST NOT include user-controlled or PII data in `ErrorResponse.Suggestion`. The CLI renders suggestion text verbatim (after `SanitizeText` for token scrubbing), and JSON-mode errors land on stdout where they may be captured by CI log scrapers, deploy pipelines, and long-term log storage. Examples of forbidden server-side patterns: echoing a malformed email back in `INVALID_INPUT.suggestion` ("Email 'jdoe@example.com' is malformed"), echoing query text in `INVALID_INPUT.suggestion` ("Query '<sensitive search>' must be non-empty"), embedding tenant-specific identifiers that map to customer accounts. Server stories owning each error code MUST review their `Suggestion` text for PII before adding it. The CLI cannot defensively strip PII because it cannot distinguish "tenant id" (safe) from "tenant id mapping to customer name" (PII) without server-side semantic context. Document this expectation in this story so server stories landing post-7.3 know the contract.

### Architecture guardrails (carried forward from 7.2)

- **Capability alignment, not feature parity** — CLI is the reference; MCP (Phase 1.5) will expose its own error semantics via the MCP protocol's structured-error mechanism. Do not generalize the CLI catalog into a "shared error surface" for MCP — MCP speaks its own protocol.
- **MVP REST is CLI routing only (D5)** — no new server endpoints, no new error envelope shape on the server. 7.3 consumes existing `ErrorResponse` as-is.
- **One-way dependency direction** — `Cli → Client.Rest → Contracts`. `ErrorMessageCatalog` lives in `Cli` (it's a CLI-projection of server codes — not part of the contract). `Client.Rest` continues to throw `MemoriesRemoteException` carrying the raw `ErrorResponse`; the catalog translates it.
- **DAPR is not a CLI concern** — no `AddDaprClient()`, no `DaprClient.GetSecretAsync()`. Same rule as 7.1/7.2.
- **Phase Compatibility Requirement** — `--format json` error envelopes are part of the public CLI contract starting 7.3. Any future story that emits a CLI error must use `WriteFormattedError` — not bypass the executor with a raw `console.Error.WriteLine`. Anti-pattern #7 below pins it.

### Anti-patterns to avoid (7.3-specific, layered on top of 7.1's 18 + 7.2's 8)

1. **Raw `console.Error.WriteLine` in command handlers for server-error paths.** Once `WriteFormattedError` exists, every server-error message MUST go through it — bypassing it gives inconsistent output across formats and breaks the AC #4 JSON-error contract. The per-command stderr lines for **handler-level validation** (`"--tenant is required."`, `"--max-results exceeds CLI ceiling"`) are a different surface — those are pre-network user-input errors, not server errors, and stay as raw stderr lines (exit code 2, plumbing). Don't conflate the two.
2. **Adding `severity`, `httpStatus`, `stack`, `traceId`, `details`, `nestedErrors` to `CliErrorPayload`.** Each is an envelope expansion that lands with the story that needs it (7.5 may add `traceId` per ADR-7.2-001). The 7.3 envelope is exactly `{ code, message, suggestion }` per FR56 + the JSON structure literally specified in epics.md AC #4.
3. **Translating server messages into "friendlier" prose that loses information.** Catalog `CliMessage` overrides exist to **add** detail (e.g., name a specific recovery command), not to remove or paraphrase the server's own message. If a server message says `"Tenant 'bu-compliance' does not exist."`, the CLI must not translate to `"Tenant not found."` (loses the tenant id). Use `CliMessage = null` (default) for any code where the server's message is already adequate.
4. **Reordering envelope fields.** ADR-7.2-001 doesn't strictly forbid field reordering (JSON is unordered), but `WriteIndented = true` produces a predictable serialization order matching the record's primary constructor. Keep the order `(SchemaVersion, Command, Data, Error)` — flipping to `(SchemaVersion, Command, Error, Data)` would make 7.2 test snapshots churn for no reason.
5. **Keeping the 7.2 bridge degradation line "for backwards compatibility."** 7.2 Task 6.6a explicitly named the line a single-owner bridge that 7.3 must delete. Leaving it AND adding the new multi-line block produces double output. Delete the bridge — both formatters — in the same PR (Tasks 5.1 + 5.2).
6. **Bumping `schemaVersion` to 2 because "we're adding a new field."** Adding `error` (with `WhenWritingNull` so existing success envelopes don't change) is **additive** per ADR-7.2-001's contract. v1 stays v1. The first v2 bump is gated on a rename or removal — 7.3 doesn't qualify.
7. **Calling `WriteVerbose` AFTER `WriteFormattedError` writes a JSON envelope to stdout.** Verbose output goes to stderr and is unstructured — fine for human/table modes (interleaving is meaningful). For JSON mode, the verbose block on stderr still works — JSON consumers redirect stderr away. **But:** order matters. Write the JSON envelope to stdout BEFORE calling `WriteVerbose` so a JSON consumer's `jq` doesn't race against verbose stderr lines bleeding into a redirected stdout (shouldn't happen with separate streams, but ordering is the conservative choice).
8. **Putting `error` in the envelope for empty results.** Empty results are not errors — `data.results: []` is the success shape per 7.2 AC #6. Never populate `error` for an HTTP 200 response. The empty-state nudge (AC #2) is informational, not error-state.
