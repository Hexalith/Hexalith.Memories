# Adversarial Review — Hexalith.Memories

## Verdict

Refuse to sign this PRD as a go/no-go instrument. The core bet is declared with a kill switch that cannot fail as written, an MVP that never touches the product’s advertised causal/zero-code/MCP story, and a “Greenfield” classification that already inventories nine published NuGet packages. The document is excellent at sounding decisive — 80%, hard gates, physical isolation, zero mapping code — and systematically unwilling to specify the comparisons, edge sources, identity model, or relevance protocol that would make those words expensive. A skeptical engineer would treat it as a positioning memo stapled to an in-flight codebase, not as a decision artifact.

## Findings

### critical The 80% hybrid kill switch is unfalsifiable as specified

- **Location:** Success Criteria § Measurable Outcomes (Three-Axis Kill Switch); Innovation § Validation Approach; FR25; NFR24–NFR26
- **Trigger:** The protocol selects 5–10 queries *that require all three axes*, scores hybrid vs each single axis with NDCG@10, calls 80% a hard line, and never defines a delta, a corpus, a graded-relevance scale, or a two-axis control.
- **Consequence:** This is not a scientific gate. Queries “requiring all three axes” are constructed so that BM25 alone, vectors alone, and graph alone are each incomplete — hybrid then “wins” by construction. N=5 makes 80% equal four lucky items; one noisy label flips the company. NDCG@10 is computed *from* ground-truth labels, yet the PRD also wants “human review where automated score and reviewer judgment diverge” and a fallback “automated A/B protocol if reviewers unavailable” — which means the authors do not know what their scorer is. Ground truth is locked by Jerome plus two reviewers *before queries are written*, so the query set can be reverse-engineered to the labels. Inter-rater ≥80% is unnamed (raw agreement vs κ). “Measurably better” has no minimum ΔNDCG. The industry baseline — BM25+vector, already shipping in Elasticsearch, Vespa, Weaviate, Azure AI Search — is never the control. You will either rubber-stamp the thesis or panic-kill it on five anecdotes, and the PRD authorizes both.
- **Fix:** Replace the protocol with: (1) a frozen corpus and a query set sampled from realistic developer/agent tasks, *not* filtered to “needs graph”; (2) graded labels on a published scale, collected after queries exist; (3) primary comparison hybrid vs BM25+semantic (the real alternative), with single-axis as diagnostics; (4) a pre-registered ΔNDCG@10 and a binomial/bootstrap test with N justified in advance (order of 50+ topics, not 5–10); (5) kill criteria that name what dies (graph-in-fusion, graph-as-product, or the three-axis positioning) instead of “re-evaluate.” Delete the A/B fallback that lets the gate run without independent labels.

### critical MVP proves a retrieval toy, not the product thesis

- **Location:** Executive Summary; § MVP Strategy & Philosophy; § MVP Feature Set (Phase 1); Phase 1.5; Journey 1; MVP Go/No-Go Gate
- **Trigger:** The product is sold as a causal memory server for LLM agents with zero-code EventStore indexing; Phase 1 is CLI ingest/search on files, and MCP plus EventStore are a “fast-follow” that is also a *soft* go/no-go gate.
- **Consequence:** You can pass every hard gate — hybrid NDCG theater, no cross-tenant leaks on a lab Redis, a 30-minute file ingest — and still have proven none of: agents getting better answers, CausationId becoming a queryable story, `dotnet add package` auto-indexing an event stream, or “why did this happen?” The hero narrative (Journey 1: 14 minutes from EventStore docs to causal `--explain`) is explicitly *out of MVP*. MCP is listed as a soft gate you are allowed to fail (2-of-3). Causal completeness is also soft. So the launch bar is “a CLI search demo with a case flag.” That is an IR spike, not Hexalith.Memories. Open-source adopters and EventStore users who read the executive summary will evaluate a product you have scheduled not to ship. If Phase 1.5 slips — and a solo developer stuffing EventStore auto-discovery, dual embedding, MCP, and CLI expansion into four weeks after 22–32 stories is how you slip — the document’s mitigation is to *pull MCP into MVP*, which destroys the “proof of thesis first” philosophy it pretends to hold.
- **Fix:** State in one sentence what thesis MVP is allowed to prove: algorithm only. Then either (a) demote EventStore/MCP/causal narrative out of the executive summary and success table until Phase 1.5, with an explicit “do not market these until gated,” or (b) put EventStore causal indexing *or* MCP agent evaluation on the hard-gate list and cut something else. Make Phase 1.5 slip a product delay, not an MVP scope accordion. Add a go/no-go that an LLM agent task succeeds on held-out queries within token budget — or stop claiming the LLM Agent persona is a success criterion of this phase.

### critical Phase 1 has no honest graph to fuse

- **Location:** MVP Feature Set #3–#4; Causal Intelligence (edge taxonomy); FR16–FR17, FR33, FR46–FR50, FR59–FR61; Journey 9
- **Trigger:** Hybrid fusion is the thesis and an MVP hard gate, but the edges that make a graph axis more than a folder tree (`caused_by`, `correlated_with`) are EventStore metadata scheduled for Phase 1.5, and file ingest never specifies how non-trivial edges appear.
- **Consequence:** On day one the graph contains `contains` (case membership) and maybe hand-waved `references`. Graph proximity weighting then either (a) reranks by “same case,” which BM25+filter already does, or (b) uses AI-inferred edges with default confidence 0.5 that no FR defines how to extract, threshold, or evaluate. You cannot run “queries requiring all three axes” against a graph that does not encode causality. The fusion spike is then tuning two search engines plus a hierarchy, while the README still claims three-axis causal intelligence. Journey 9 even has Alex publish a test event to a DAPR topic in the MVP empty-state climax — a capability the feature table excluded. Implementers will invent an edge story to make the benchmark pass. That is p-hacking, not validation.
- **Fix:** Specify the Phase 1 edge inventory as a closed list: how each type is created (explicit link, ingest-time extractor, none), with examples. If causal edges are absent, forbid “three-axis” and “queries requiring all three axes” until EventStore lands; validate BM25 vs vector vs BM25+vector in Phase 1, and treat graph-in-fusion as a Phase 1.5 kill switch on a corpus that actually has CausationId chains. Remove DAPR event publish from Journey 9 or move the journey to Phase 1.5.

### critical The document classifies a shipping system as Greenfield

- **Location:** Project Classification (`projectContext: Greenfield`); Technical Architecture § Package Distribution (“Current release inventory: 9 published NuGet packages”); Implementation Sequencing
- **Trigger:** Front matter says greenfield. The architecture chapter inventories nine published packages, non-packable services, `tools/release-packages.json` as source of truth, and a compatibility-only Redis package “retained for existing package consumers.”
- **Consequence:** Nobody can tell requirement from retrospective. FRs read as a wish list; the package table reads as as-built. A chain-top PRD already in implementation that will not mark must-keep vs must-change vs already-shipped will be used to justify both “don’t touch that, it’s specified” and “we can slip it, it’s still greenfield.” Reviewers cannot audit drift. The “start concrete, extract later” sermon collides with packages that already exist. This is how you get a 74-FR encyclopedia that does not constrain the next sprint.
- **Fix:** Reclassify as brownfield / in-progress. Add a status column on every epic/FR/NFR: `shipped`, `partial`, `not started`, with the commit or package version that proves it. Split “current topology we must not break” from “net-new MVP remaining work.” Kill the Greenfield tag until it is true.

### high Competitive landscape is a straw man; “no competitor offers this” is load-bearing theater

- **Location:** What Makes This Special; Innovation § Market Context; competitive table; Key differentiators borrowed from the brief
- **Trigger:** The table compares Memories to Mem0, Zep, LangChain Memory, Elasticsearch, and “Qdrant + custom glue,” then claims unique three-axis fusion, unique team-scoped memory, and a moat of “integration depth.” Team discussions, memory diffing, and “brief me on this case” are Phase 2.
- **Consequence:** Decision-makers will believe there is no alternative and that shipping cases+CLI is enough to occupy a category. The omitted field is the actual market: GraphRAG / Microsoft GraphRAG, Neo4j LLM graphs, LlamaIndex PropertyGraphIndex, Elasticsearch/OpenSearch hybrid (BM25+vector, increasingly with graph), Vespa, Weaviate hybrid + multi-tenancy, Azure AI Search. “No existing system ships syntactic + semantic + graph fused with a documented deterministic algorithm” is an advertising sentence, not a surveyed claim — and even if fusion-as-product were novel, novelty of ranking math is not a moat. “No competitor offers” collaborative case memory is false in the broad knowledge-base sense (Notion, Confluence, case systems) and premature in the product sense: the PRD itself deferred the features that sentence lists. The integrated-system moat argument (“replicating this is multi-month”) is what every duct-tape vendor says; it is not evidence. Load-bearing strategy (beachhead, positioning, 12-month stars) sits on uncited uniqueness.
- **Fix:** Rebuild the table against hybrid-search and GraphRAG incumbents. Mark each Memories differentiator as `shipped in MVP`, `Phase 2`, or `EventStore-only`. Replace “no competitor offers this” with a falsifiable claim: named capability, named competitors checked, date of check. If the remaining unique slice is “CausationId → FalkorDB on DAPR for Hexalith,” say that and size the market accordingly — the brief already rated small EventStore TAM as high likelihood.

### high “Zero mapping code / zero configuration” is already retracted in the same PRD

- **Location:** Executive Summary; What Makes This Special; Journey 1–2; FR59–FR62; Innovation § Zero-Code Event Memory; Risk Mitigation (non-EventStore)
- **Trigger:** Marketing says zero mapping, zero configuration, auto-discovery for any DAPR publisher. Journey 2 requires registering `ClaimSubmittedV2` handlers. The innovation fallback admits “low-code with a thin adapter” for everyone but EventStore. MVP does not ship the EventStore package at all.
- **Consequence:** The onboarding criterion, the beachhead aha, and FR61 are selling a property the debug journey proves false the moment a schema evolves — which is the first week of any event-sourced system. “Auto-discover event types” (FR59) is one line with no rule: reflection over known assemblies, CloudEvent type URIs, a schema registry, or hope? Journey 2’s scope note even points at “MVP Feature #3 (EventStore Integration),” but MVP Feature #3 is Three-Axis Search. The document was edited to defer EventStore and the journeys were not. Adopters will open issues the README promised could not exist. The DAPR-generic kill switch (“if integration requires custom code beyond subscription config, the pattern isn’t generic”) is already failed by the handler narrative, and the PRD’s response is to quietly narrow the claim after using the wide claim in the executive summary.
- **Fix:** Put the honest contract in the executive summary: EventStore happy path is subscription + conventions; schema changes require handler registration; non-EventStore is an adapter. Define auto-discovery mechanically. Move FR59–FR62 to Phase 1.5 explicitly. Fix Journey 2’s feature cross-reference. Delete “zero configuration” or list the exact config files and secret stores (it is not zero: `appsettings.json`, DAPR components, OpenBao, embedding keys, Aspire AppHost).

### high The kill switch does not kill

- **Location:** Executive Summary (“product direction must be re-evaluated”); Measurable Outcomes (“re-evaluate the graph axis investment”); Innovation § Risk Mitigation (fallback to two-axis, keep graph for causal traversal, reposition as “team memory with intelligent search”)
- **Trigger:** Three wordings, three severities, one outcome: keep building.
- **Consequence:** Leadership thinks there is a hard stop. Engineering has already pre-authorized the pivot that preserves FalkorDB, actors, tenant-isolated graphs, and the case model — i.e. almost the entire MVP cost. If hybrid loses, you do not kill the thesis; you write a blog post. That is not a kill switch. It is a slogan that lets the R&D investment proceed with moral cover. Combined with finding 1, failure is both unlikely to be detected and costless if detected.
- **Fix:** Write a single kill-switch paragraph that names sunk-cost actions: stop fusion R&D, remove graph from default `axes=hybrid`, freeze FalkorDB as causal-only or cut it, change README positioning *before* Phase 1.5, and halt MCP/EventStore expansion until the fallback product is re-scoped and re-estimated. If the real intent is “never kill, only reposition,” delete kill-switch language so nobody plans against a lie.

### high The “cannot retrofit” foundation is also the first budget cut

- **Location:** MVP Strategy (“cases and multi-tenancy from day one — architectural decisions that can’t be retrofitted”); Resource Risks (“Cases and tenant isolation deferred to fast-follow”); Hard gates (zero cross-tenant leaks)
- **Trigger:** The same document says isolation/cases are load-bearing architecture *and* optional if the solo developer gets tired.
- **Consequence:** When 22–32 stories collide with fusion R&D, the PRD authorizes dropping the thing it called non-retrofittable, while the go/no-go still lists zero leaks as a hard gate. You will either ship a single-tenant prototype and call it multi-tenant, or spend the isolation budget and miss the thesis spike. Implementers get to pick. That is not a strategy. It is a permission slip for whichever fire is closest.
- **Fix:** Choose. If physical isolation is a hard gate, remove it from the “absolute minimum” cut list and cut CLI polish / extra FRs instead. If the true MVP is Engine+Search+CLI+Benchmarks, drop isolation from hard gates and from enterprise marketing until it exists. Record the retrofit cost you are currently pretending is infinite.

### high “Physically isolated per-tenant indexes” is logical namespacing in a shared Redis

- **Location:** Executive Summary; Journey 5; FR38; NFR8; Compliance Boundary
- **Trigger:** Journey 5 provisions “physically separate Redis indexes — RediSearch, vector, and FalkorDB graph — all namespaced and isolated.” Isolation tests are application-layer tenant-ID checks. Per-user identity is explicitly out of MVP.
- **Consequence:** Enterprise security and a skeptical operator will not green-light this. Separate index names on one Redis/FalkorDB process is not physical isolation (not separate processes, volumes, credentials, or failure domains). A shared embedding API key is already admitted as a noisy-neighbor channel. Cross-tenant leaks via `FT.SEARCH` on the wrong index, a stolen DAPR token, or a key collision are in-scope; NFR8 only exercises the API. Compliance text then uses this costume as a “prerequisite for downstream compliance.” Kenji’s journey even invents `memories tenant switch` and audit logs that the MVP CLI command list does not include. Operators who need tenant-level blast radius will refuse, and the README will have over-claimed.
- **Fix:** Define isolation tiers: (L1) namespaced indexes, shared cluster, API enforcement; (L2) per-tenant Redis/FalkorDB instances; (L3) separate networks/credentials. Tag MVP as L1. Strike “physical” and “enterprise-grade isolation” unless L2 is in scope with a provisioner that actually creates separate data stores. Align Journey 5 commands with the MVP CLI list. Put shared-key and shared-process residual risk in the go/no-go, not only in an operator-guide footnote.

### high The worst FRs are slogans; FR13 is the exhibit

- **Location:** Functional Requirements, especially FR13; also FR43, FR53, FR59, FR74; missing phase tags on FR46–FR62 / FR54
- **Trigger:** Seventy-four one-line capabilities. FR13 is the purest evasion: “handles partial backend write failures with defined recovery behavior (rollback **or** retry).”
- **Consequence:** FR13 authorizes both destroying in-flight writes and leaving them to retry — opposite products. Implementers will pick one per backend and call it done; testers have no expected observable. That is the pattern for the rest of the list: FR43 (“data inconsistency” + “explicit operator acknowledgment”) has no inconsistency definition and no acknowledgment protocol; FR53 demands *all* retrieval/ingestion via CLI while the MVP CLI cut list forbids `status`, `traverse`, `handlers`, members, and batch directories; FR59 is “auto-discover” with no mechanism; FR74 “repair” does not say whether repair may drop vectors, invent edges, or block search. EventStore and MCP FRs sit in the same unphased pile as ingest-a-file. A chain-top implementation will treat FR count as coverage and ship 74 half-behaviors. A skeptical engineer asked to green-light “FR1–FR74 done” has nothing to fail a story against.
- **Fix:** Do not rewrite all 74 in this pass — rewrite the dangerous ones first. FR13 must pick *one* consistency model (e.g. “indexing is atomic across three backends or the unit stays `failed` and is not searchable on any axis; no silent two-of-three”) plus an observable CLI/API state. Phase-tag every FR (`MVP` / `P1.5` / `P2`). Split FR53 into the MVP command set vs later. Give FR74 repair invariants (no cross-tenant repair, no silent deletion without `ingested_by` audit, dry-run required). Ban “or” in recovery FRs.

### high The 30-minute onboarding hard gate clocks a path that does not exist in Phase 1

- **Location:** Executive Summary; User Success (Alex); NFR31; Journey 1; Technical Architecture (MVP CLI uses a minimal HTTP adapter; reusable client packages are not MVP); Embedding Provider (Google + OpenBao)
- **Trigger:** The clock starts at `dotnet add package`. MVP has no EventStore zero-code flow, no reusable Client package, and a runtime of Aspire + DAPR sidecars + Redis Stack + FalkorDB + OpenBao-backed secrets + a Google embedding key.
- **Consequence:** NFR31’s “clean machine with Docker” walkthrough cannot match Journey 1 and cannot match `dotnet add package`. Either you time a lie (EventStore path), or you time `docker compose`/`dotnet run --project AppHost` plus `memories ingest`, which is a different product promise. Google API keys and OpenBao are not in the 30-minute story. Solo-dev “README is not a story” means the only hard UX gate has no implementation budget. Alex the beachhead (EventStore user) never sits in the MVP funnel. You will pass the gate with a scripted happy path on a pre-warmed machine and call DX done.
- **Fix:** Write the Phase 1 stopwatch procedure as a numbered script: machine state, required secrets, excluded steps, pass/fail. Start the clock at the command you actually ship (`dotnet tool install` / `dotnet run --project AppHost`), not `dotnet add package`. Move the EventStore 30-minute claim to a Phase 1.5 hard gate. If OpenBao/Google are required, they are on the clock — or the MVP embedding path must include a deterministic fake/local embedder for onboarding so the gate is not “did the reviewer already have GCP.”

### high Case members, `ingested_by`, and tenant mismatch exist; a user identity model does not

- **Location:** Service Communication Model (“Per-user identity — Not in MVP”); FR28–FR29, FR36, FR65, FR67; Journeys 4–5; Trust & Transparency (insider threat detection)
- **Trigger:** The PRD simultaneously postpones per-user identity and specifies add/remove case members, mandatory `ingested_by`, activity feeds, tenant-switch errors, and audit telemetry.
- **Consequence:** These FRs will be implemented as free-text strings (`--user tomas`) with no authentication binding. Isolation becomes “the caller passed the right tenant id.” Insider-threat language is satire. Journey 4’s Monday briefing is Phase 2/MCP theater sitting on an identity hole. Operators and open-source adopters in any regulated shop will refuse to green-light “enterprise isolation” that cannot name a principal. `ingested_by` as a mandatory MVP field without a principal store is a forged column.
- **Fix:** Either add a minimal principal model to MVP (authenticated subject from ingress/DAPR token, stored on ingest, used for member checks) or remove FR28–FR29, member journeys, insider-threat claims, and “audit” until identity exists. If `ingested_by` stays, define the issuer and forbid client-supplied impersonation.

### medium Confidence is defined as calibrated truth and as “not accuracy” in the same chapter

- **Location:** Compliance Boundary (Interpretation layer: “0.8 must reflect actual ~80% reliability”); AI Reliability (critical distinction: scores are relevance, not factual accuracy); Growth-phase calibration; FR63–FR64
- **Trigger:** Two incompatible contracts for the same number, with calibration deferred, while `--explain`, MCP, and Priya’s 0.95 causal-chain confidence are sold as trust.
- **Consequence:** Applications will treat 0.95 as “the denial reason is true.” The PRD already knows this is wrong and still writes Priya’s stomach unknotting because confidence was 0.95. Edge default 1.0 for `caused_by` is “the EventStore field existed,” not “the real world caused this.” Untestable Interpretation-layer duty, real product liability. The Evidence Packet then spreads the confusion to CLI, MCP, and future UI identically — consistent wrongness.
- **Fix:** One semantics table: relevance composite vs metadata-origin confidence vs edge-existence confidence, each with a sentence of what it is *not*. Remove “0.8 ≈ 80% reliability” from MVP or make calibration an MVP acceptance test. Put the relevance-not-truth caveat in the Evidence Packet schema, not only in docs. Downgrade Journey 8’s 0.95 beat so it cannot be read as factual warranty.

Require a no-network embedding path for tests and first-run.

### medium Latency, freshness, and “atomic three-backend index” NFRs disagree with the journeys

- **Location:** LLM Agent success (<200ms cached, <2s cold); NFR1–NFR4, NFR6; Async Ingestion (`indexing` = “Atomic write across all three backends”); NFR18 (degraded when one backend dies); FR6, FR13
- **Trigger:** Agent success wants 200ms; hybrid p95 is 1s at 10K units; graph traversal p95 is 2s; event freshness <5s is P1.5; MVP still claims “fully searchable across all axes after ingestion completes” with no freshness NFR for files.
- **Consequence:** You can pass NFR3 and fail the persona table. Atomic triple-write vs “serve partial axes” is unresolved — the same incident is either a transaction or a degraded response. Cold vs cached is undefined (which cache?). 10K units/tenant is the only load point; Journey 6’s 2M units is Phase 3 fan fiction with no curve connecting them. Performance gates will be “tested on a laptop with 10K docs” and then production will look like Kenji’s Redis graph. None of this is a kill switch, so it will not stop the launch.
- **Fix:** Collapse to one latency budget per surface (CLI interactive, MCP agent, bulk). Define cache. Pick atomic-index XOR degraded-read and write it into FR13/NFR18 together. Add MVP freshness for file ingest (e.g. searchable on all *available* axes within T, or status shows `embedding`). Remove 200ms from persona success or make it a cached-path NFR with a cache design. Put 100K/1M as explicit non-goals for Phase 1.
