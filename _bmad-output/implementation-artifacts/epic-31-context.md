# Epic 31 Context: OpenBao Secrets Platform and Runtime Secret-Store Migration

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Make the deployed OpenBao `hexalith-keys` platform independently reviewable through accurate configuration documentation, measured operating limitations, and security evaluation, then migrate the deployed runtime Dapr `secretstore` from Kubernetes Secrets to `hashicorp.vault` so runtime secret resolution crosses one reviewed boundary and every remaining Kubernetes Secret is justified. This epic formalizes an already-running cluster platform rather than standing one up. It belongs to Operational Readiness / Secret Management Platform, requires explicit sprint selection, and supplies no MVP product-readiness credit; platform documentation, runtime migration, and Production qualification each require separate evidence.

## Stories

- Story 31.1: OpenBao Platform Hardening and Documentation
- Story 31.2: Runtime Dapr Secret-Store Migration to `hashicorp.vault`

## Requirements & Constraints

- **Exclusive Dapr/OpenBao secret boundary:** Product services retrieve embedding-provider, application, and data-plane credentials exclusively through the Dapr Secrets API backed by OpenBao—never via configuration fallback, ordinary environment variables, direct provider SDKs, or user secrets. Secret values (including unseal/recovery keys and root/operator tokens) must never enter source control, configuration, workflow history, logs, telemetry, public contracts, CLI output, documentation, evidence artifacts, or test snapshots.
- **Bootstrap minimum and remaining Kubernetes Secrets:** Deployments supply only documented minimum bootstrap material (required OpenBao tokens and CA certificates) outside Dapr; local bootstrap or seeding inputs cannot act as runtime secret providers. Every remaining Kubernetes Secret must be justified as unavoidable OpenBao bootstrap material or a direct pod input Dapr cannot inject (replacing direct pod inputs requires a separately approved Agent Injector or CSI design). Direct Kubernetes Secret injection of shared Redis/FalkorDB credentials is an alignment gap, not an approved second application-secret path.
- **Measured availability and accepted limitations:** Document availability as measured rather than inferred from manifests. Co-located OpenBao pods/Raft voters on one Kubernetes node leave that node as the whole failure domain; voter count and HA mode must match live observations and never imply node/site resilience or production-HA. Retain the static file-based seal (unseal key in a Kubernetes Secret beside data) and namespace-wide port 8200 ingress as explicit limitations—each with owner, consequence, compensating controls, and reopen trigger—never described as hardened or production-HA.
- **Platform disposition and version separation:** On 2026-11-22, Jérôme Piquot (`jpiquot`) closed Story 31.1 by sole-owner risk acceptance for C4b, C5b and C7. No independent countersignatures were obtained. EVAL-01 remains open with Platform Operations. The July C7 waiver expired on 2026-10-26. Documentation checkpoints C1–C3, C4a, C5a, and C6 are complete and guard-asserted. Keep repository-adopted inputs (OpenBao `2.6.4` / chart `0.29.6`), measured cluster observations (`2.6.2` / chart label `0.29.5` on November 16; three Ready pods on one node; unmeasured Raft voting/failover), and the retained `2.6.0` CA-only smoke client distinct. Pins, status smoke runs, and dated risk acceptances never qualify Production; exact deployed bytes require reconciled inputs and current rerunnable security evidence.
- **Checkpoint evidence and negative proofs:** Every checkpoint records an accountable owner, exact evidence command or artifact, review state, and completion state. Evidence must prove live scoped Dapr reads, cross-prefix and non-scoped denial, restart recovery, provider-neutral product code (no OpenBao SDK, HTTP client, endpoint, or credential), and secret-safe logs, telemetry, CLI output, and snapshots. A disposable lane substituting Kubernetes stores for Vault cannot certify the deployed OpenBao path.

## Technical Decisions

- **Scoped component and policy isolation:** Keep bootstrap, application, data-plane, and operator scopes separate and least-privileged. Separate Dapr components bind distinct OpenBao prefixes under dedicated read-only policies—`secretstore` (`secret/hexalith/memories/runtime`) for Memories Server and embedding/LLM secrets, and `access-telemetry-secrets` (`secret/hexalith/memories/access-telemetry`) for access-telemetry services—with cross-prefix reads failing closed.
- **Runtime migration and reserved `eventstore` scope:** Migrate deployed runtime `secretstore` to `secretstores.hashicorp.vault` with `memories` and reserved `eventstore` scopes. Prove `memories` via a live scoped read. Because no deployed Kubernetes workload carries app-id `eventstore` (EventStore is linked as a library/submodule), prove `eventstore` structurally via declared presence plus demonstrated denial from a non-scoped app-id; do not fabricate a workload. Deploying an `eventstore` app-id workload reopens the live-read requirement.
- **Rotation bound and Production isolation:** Revoke superseded credentials at the provider within 60 seconds of committed rotation, preventing connections or clients established under them from outliving that bound; consumers unable to prove freshness fail closed. Production qualification also requires per-tenant backend principals and current isolation evidence; dated risk acceptance supplies no qualification credit.
- **Manifest-to-live reconciliation:** Platform documentation records manifest/live divergences as owned gaps; reproducing the live Helm release from reconciled manifests is separate Platform Operations work outside Story 31.1's checkpoints, preserving its owner and reopen evidence obligation.
