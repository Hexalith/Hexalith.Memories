## What Went Well

1. **The execution order protected the architecture.**
   Story 23.9 ran before Story 23.1, so chunking consumed a real batch API instead of creating provider-specific shortcuts.

2. **Workflow boundaries got cleaner.**
   Claim-check payloads, durable provider retry handling, non-URL source retention, and captured workflow config all moved side effects and mutable data out of orchestration.

3. **Tenant and memory-unit identity stayed stable.**
   Chunking changed raw semantic vector cardinality, but did not create new memory units, graph nodes, dedup identities, source lookup identities, or case activity identities.

4. **Review found important edge cases before closeout.**
   Review fixes covered whitespace-only chunk windows, graph-scoped semantic dedupe, duplicate-path payload cleanup, event dedup-scoped source payloads, actor first-use persistence, directory cancellation cleanup, and missing chunk readiness tests.

5. **Epic 22 retrieval invariants were carried forward.**
   Semantic pagination, graph scope, case attribution, NL axis behavior, scoped key validation, and post-filter recall were explicitly preserved while ingestion output changed.

## Challenges

1. **File List and evidence hygiene still needed review correction.**
   Several Epic 23 reviews fixed omitted files, stale test-summary artifacts, or incomplete File Lists. The review loop caught the issue, but the pre-review process did not reliably prevent it.

2. **Validation lanes remain split.**
   Focused server and contract validation were strong, but Story 23.7 still records the AppHost/EventStore.Aspire build blocker and unavailable RedisStack/Docker proof for integration tests.

3. **The workflow payload model became more nuanced.**
   Story 23.4 discovered that event source payloads may be scoped to the deterministic EventStore dedup workflow id while the failure record uses the generated memory-unit id. That was fixed, but it is now a critical invariant for future ingestion work.

4. **Hot-path optimizations introduced cache and readiness semantics that must stay visible.**
   Tenant embedding config caching and tenant index readiness caching have different safety rules. Future work must not blur those cache boundaries.

5. **Some story automation paths were unstable.**
   Story 23.8 needed direct fallback after child story/review sessions failed to produce source artifacts. The result is valid, but orchestration reliability remains a process concern.

## Team Agreements

- Provider behavior belongs behind provider strategies; workflows and activities should not regain provider-specific request or parse logic.
- Workflows orchestrate only; payload I/O, provider calls, state reads, and index readiness checks stay in activities or services.
- Base `MemoryUnitId` remains the domain identity. Chunk sequence belongs to raw semantic vector storage only.
- Tenant index creation belongs to tenant provisioning. Ingestion may verify readiness but must not create missing indexes on demand.
- Focused validation is acceptable when full-stack validation is blocked, but the blocker must be named precisely and not disguised as proof.
