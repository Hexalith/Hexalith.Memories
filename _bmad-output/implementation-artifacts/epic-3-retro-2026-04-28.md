## What Went Well

1. Case identity became a real domain concept.
   Story 3.1 added the `Case` contract, creation/list/get endpoints, FalkorDB case nodes, and strict single-case ownership semantics. The team kept tenant ID trust at the route boundary and added AOT-safe JSON coverage early.

2. Case activity was added without blocking core workflows.
   Story 3.2 used Redis Streams for case activity and treated activity recording as best-effort. That avoided making observational logging a hard dependency for ingestion or search success.

3. Member operations used the right idempotency primitive.
   Story 3.3 used Redis `HSETNX` for idempotent member add, capped member growth, recorded member activity, and added concurrency coverage. Review patches hardened corrupt JSON, cap behavior, missing `memberType`, and duplicate activity risks.

4. Case-aware search aligned product behavior with the case model.
   Story 3.4 added case attribution, case grouping, source type filtering, metadata query support, and case existence validation before search. It also fixed the graph axis case filtering gap, which was the biggest search correctness risk in the story.

5. Deletion became visible and retriable.
   Story 3.5 set `CaseStatus.Deleting` before cleanup, deleted memory units across all three backends, deleted case member/activity keys, and used graph-driven memory-unit discovery. Review patches improved retry safety and coverage for wrong-case deletion, non-empty cleanup, and `CASE_DELETING` behavior.

6. Annotations reused the ingestion pipeline instead of creating a parallel path.
   Story 3.6 modeled annotations as memory units with server-generated `_system.` metadata, an `ANNOTATES` edge, search `annotationsCount`, listing endpoints, and cascade deletion. Review patches corrected annotation identity, status assumptions, listing behavior, dedup collisions, and missing validation.

7. The test surface grew with the risk.
   Each story added contract serialization tests, validator tests, service tests, and integration coverage where backend behavior mattered. The most important coverage areas were idempotency, case search scoping, deletion cleanup, graph query parameterization, and annotation cascade behavior.

## Challenges

1. Case behavior spread across many layers.
   Epic 3 touched contracts, Redis hashes, Redis Streams, FalkorDB graph nodes, search results, ingestion workflow activity recording, deletion paths, and Minimal API endpoints. That breadth made review essential because a local fix could miss another layer.

2. Atomicity stayed intentionally imperfect.
   Case creation still writes Redis and FalkorDB as separate operations. Deletion is status-guarded and retryable, but not fully orchestrated. The system is transparent about partial state, but it still relies on follow-up hardening for production-grade lifecycle guarantees.

3. CaseId validation improved but remains uneven.
   Story 3.3 added case ID validation for member paths, and Story 3.4 added case existence validation for search. `deferred-work.md` still records a broader CaseId validation gap, including endpoint paths that construct keys or graph queries without one canonical guard.

4. Deletion exposed dedup lifecycle debt.
   Memory-unit deletion removes RediSearch, vector, and graph state, but dedup keys can persist. Re-ingestion of identical content can return a stale memory-unit ID if the dedup record points to data that has been deleted.

5. Ingestion does not yet honor `CaseStatus.Deleting`.
   Story 3.5 exposes the `Deleting` status and blocks memory-unit deletion against a deleting case, but ingestion validation does not yet reject ingestion into a deleting case. This can create orphaned memory units during a concurrent delete.

6. Some activity and annotation behavior is best-effort by design.
   Activity streams can miss events under backend failure, and annotation creation has accepted MVP race limits. These are defensible tradeoffs, but they should remain visible instead of becoming assumed guarantees.

## Key Lessons

1. Case scoping is a correctness feature, not a convenience filter.
   If one search axis ignores case scope, cross-case search and case-scoped search both become untrustworthy. Story 3.4's graph-axis fix was therefore a product correctness fix, not a minor backend patch.

2. Best-effort side effects need explicit contracts.
   Activity recording is useful, but it must never determine ingestion or search success. The story files documented this clearly, and the workflow resilience tests protected the contract.

3. Retry safety depends on preserving the discovery handle.
   Story 3.5 review showed that deleting graph nodes too early can remove the only reliable way to discover remaining memory units during retry. Deletion order matters.

4. Annotation identity must be deterministic across graph and workflow state.
   Story 3.6 initially risked creating a stub/edge ID that differed from the workflow-generated memory-unit ID. The patch reinforced a larger rule: graph identity and workflow identity must be the same object, not parallel guesses.

5. Review findings were high-value design feedback.
   Epic 3 reviews caught real system failures: wrong Redis key scans, corrupt member records, under-filled filtered pages, retry-unsafe deletion, annotation dedup collision, and missing annotation ownership checks.

## Significant Discovery

Epic update required: yes, narrowly, for follow-up planning rather than for Epic 4 itself.

Epic 3 did not invalidate Epic 4's direction. The opposite happened: Epic 4 already applied several Epic 3 learnings. The significant discovery is that case lifecycle and graph lifecycle are now tightly coupled enough to deserve explicit follow-up work.

Planning updates recommended:

1. Treat CaseId validation as a shared boundary rule, not a per-endpoint detail.
2. Add ingestion rejection for cases in `Deleting` status before any further lifecycle work assumes deletion is isolated.
3. Resolve dedup key behavior for deleted memory units before deletion is presented as complete lifecycle cleanup.
4. Record that structural edges (`CONTAINS`, `ANNOTATES`) are graph infrastructure and should stay out of default causal traversal unless explicitly requested.
5. Keep deletion retry-safety tests close to any future graph or lifecycle refactor.

## Team Agreements

- Treat case lifecycle as cross-backend behavior, not simple CRUD.
- Keep activity logging best-effort and never let it break ingestion, search, or deletion.
- Require retry-safety review for any code that deletes graph nodes used as discovery handles.
- Keep structural graph edges out of default causal traversal unless the caller explicitly requests them.
- Do not add new case-related endpoints without applying the canonical CaseId guard once it exists.
