## What Went Well

- Story 10.1 created a separate `Hexalith.Memories.Mcp` project with the four FR54 tools: `search_memory`, `ingest_content`, `traverse_relations`, and `get_case_info`.
- The service boundary held. MCP runs as its own Aspire/DAPR resource with app-id `memories-mcp` and delegates through `MemoriesClient` over DAPR service invocation instead of reaching Redis, FalkorDB, or secret stores directly.
- The tool schemas became explicit LLM contracts. Parameters have descriptions, required fields are covered by tests, graph traversal stays on `traverse_relations`, and `search_memory` exposes only syntactic, semantic, and hybrid axes.
- Error handling improved during review. Tool methods now return protocol-level `CallToolResult` objects for success and error paths, and generic error mapping avoids stack traces and input echo.
- Health-check design improved during close-out. `MemoriesServerUpstreamHealthCheck` keeps rolling-window state while resolving scoped `MemoriesClient` instances per probe.
- Story 10.2 replaced the 10.1 client-side budget clamp with server-side response shaping. Search and traversal responses now expose omitted counts, estimated token totals, omitted reasons, axes used, degradation metadata, and traversal primary-path integrity.
- MCP ingress authentication landed with JWT bearer validation, endpoint authorization, SDK authorization filters, and per-tool tenant-claim checks before any DAPR call.
- The 10.1 unauthenticated-startup guard was removed once 10.2 made authentication mandatory, avoiding a stale safety mechanism after its purpose expired.
- The team captured architectural rationale in ADRs instead of leaving security choices implicit: auth-shape copy, token-budget placement, JWT selection, and MVP auth granularity.
- Validation evidence is concrete: `Hexalith.Memories.Mcp.Tests` passed after auth work, focused Server token-budget tests passed, integration project build passed, and the final solution build passed with zero warnings and zero errors in the recorded story evidence.

## Challenges

- MCP combined protocol design, transport wiring, tool schema generation, DAPR topology, contract evolution, token-budget behavior, and security hardening in a compact surface.
- ModelContextProtocol SDK behavior shaped implementation details. The team had to adapt to schema-generation enum casing, `MapMcp()` routing defaults, and the available authorization-filter surface.
- The 10.1 forward-reference guard was useful but came with lifecycle cost. It prevented unauthenticated shipping in the intermediate story, then had to be deleted deliberately in 10.2.
- Token-budget compliance remains heuristic, even after moving truncation to the server. The current estimator is practical, but non-ASCII content can be over-pruned until tokenizer-accurate accounting is justified.
- Tier-3 trace proof did not fully close. The prerequisite auth fixture exists, but MCP-to-Server parent/child span verification still needs an exporter path through the MCP process.
- MCP auth solved the LLM ingress boundary, not the broader Memories Server auth gap discovered in Epic 9. Server endpoint authorization remains a cross-cutting security story.
- AppHost token propagation still depends on process-level environment side effects from the DAPR hosting toolkit, which is acceptable as a known limitation but not ideal.
- Review discovered several "almost right" behaviors: hybrid `AxesUsed`, expired bearer minting, and credential-key audit guards all needed patching before close-out.

## Key Insights

1. MCP is a product surface, not just a protocol adapter. Tool names, descriptions, error text, omitted-result signals, and degradation fields are now user-facing contracts for LLM clients.
2. Additive service boundaries worked. The memory engine did not need rearchitecture; MCP fit beside Server in Aspire and used DAPR service invocation as designed.
3. Security must be layered by boundary. MCP bearer auth protects external LLM ingress; DAPR API tokens protect internal service calls; Server auth remains a separate unresolved boundary.
4. Budget-aware retrieval needs explanation fields, not just truncation. `omitted_count`, `omitted_reason`, `axes_used`, and `primary_path_intact` let agents caveat answers honestly.
5. Forward-reference guards are useful when a follow-up story closes a known risk, but they should be designed with explicit removal criteria.
6. Topology-sensitive claims need executable proof. Unit and WebApplicationFactory coverage are strong, but distributed traces across real DAPR hops need their own lane.

## Significant Discovery Check

No Epic 10 discovery invalidates Epic 12. Epic 12 remains the correct next operational focus.

Significant discoveries that affect release hardening:

- MCP ingress is authenticated, but Memories Server endpoint auth remains open outside the MCP boundary.
- Trace propagation across the real MCP-to-Server DAPR hop still needs executable topology evidence.
- Token-budget behavior is structurally correct but estimator-based.
- Authentication was copied by shape from EventStore rather than shared by reference, which keeps product boundaries clean but creates drift risk.
- The MCP SDK still has reflection-heavy schema generation, so AOT publishing remains a future compatibility concern.

## Commitments

- Treat MCP tool schemas, tool names, descriptions, and error shapes as public contracts.
- Keep MCP isolated from backend stores and Server internals.
- Do not equate MCP bearer authentication with full Server authorization.
- Keep token-budget caveat fields visible to LLM clients.
- Keep DAPR topology claims backed by executable evidence or explicit deferrals.
- Make release documentation state the MCP operational assumptions plainly.
